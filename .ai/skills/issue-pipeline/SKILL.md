# Issue 処理パイプライン（implement → PR → review → merge → close）

設計経緯や判断理由は [rationale](../../rationale/issue-pipeline.md)、障害・復旧手順は [troubleshooting](../../troubleshooting/issue-pipeline.md) を必要なときだけ参照する。

複数のオープン GitHub Issue を1件ずつ完結させる repo 運用オーケストレータ。主文脈は処置順・オーナー判断・進捗管理に専念し、実装・レビューは利用可能な専用担当へ委譲する。

## 役割分担

- **主文脈＝対話オーナー**：処置順、オーナー判断、先送り可否、スコープ拡張の起票判断を担う。
- **実装・レビュー担当＝非対話ファンアウト**：ユーザーへ直接質問せず、曖昧・矛盾・情報不足は STOP して原案＋比較＋理由付き推奨を返す。順序やオーナー判断を担当側で決めない。
- PF によって担当の権限境界と起動方式は異なる。機械ゲートがある PF はそれを使い、ない PF は wrapper に定める運用規律を守る。

## ① 処置順の原案 → オーナー承認

着手前に、主文脈はローカルの既定ブランチを `pull` で最新へ更新する。以降の Issue 本文・依存・構成の確認と、後続で切るブランチの base を、古いローカル状態に対して行わないため。

1. オープン Issue の本文、依存（`depends on` / `blocked by`）、相互参照、同一ファイル群の競合を確認する。重い横断調査は read-only の調査担当へ委譲できるが、推奨順は主文脈が決める。
2. 各 Issue と Issue 集合の構成が妥当な単位に切られているかを、順序の検討とは独立に確認する。判定基準は `.ai/skills/gh-create-issue/SKILL.md` §3（材料は集約・軸1／軸2）・§4（成果は分割・`type:tracking` ＋ sub-issues への展開）を参照し、「材料（検討のインプット）」「成果（実行のアウトプット）」の概念を本 skill 側で再定義しない。次の2方向を**対称に**見る。
   - **分割漏れ**：1つの Issue が独立して完了判定できる複数の成果を抱えていないか。抱えているなら `type:tracking` ＋ sub-issues へ展開してから着手する。
   - **集約漏れ**：1つの設計判断に効く検討材料が複数の Issue に散っていないか。散っているなら検討を1箇所へ寄せてから着手する。
   検出しても Issue の分割・統合を自分で実行しない。構成の変更は Issue 本文・relation の破壊的変更であり、`.ai/skills/gh-create-issue/SKILL.md` §1 の write 境界（作成の明示依頼は既存 Issue の破壊的変更への包括許可ではない）が及ぶ。分割漏れ・集約漏れそれぞれについて、原案・比較・理由付き推奨を添えてオーナー判断を仰ぐ（PR7 の様式）。
3. 依存を有向グラフ化し、順序必須と並列可を分け、ブロッカーを先に置く。
4. 依存グラフ要約、推奨順、並列可否、リスク見立て、根拠、メリット／デメリットに加え、構成の妥当性の判定結果（分割漏れ・集約漏れの有無と、あれば是正の推奨）を提示してから、オーナーの承認または修正を得る。承認前に処置を始めない。

## ② 1 Issue を完結

前の Issue が merge と close を完了してから次へ進む。各 Issue は次の順序を崩さない。

### ②-a 実装

- 実装担当を dispatch する前に、PF の Issue-start 契約（存在する場合）で Issue、repository、branch、base を再束縛する。契約エラーは別経路へ迂回せず fail-close する。
- Issue-start 契約が ALLOW を返した直後、実装担当を dispatch する前に、Project の `Status` を `In progress` にする。BLOCK なら着手しないので `In progress` にはせず、`Blocked` を立てるのは同期ツール（`project_status_sync`）に委ねる。同期ツールは `In progress` / `In review` を書き込み対象から外しているため、着手中の Issue が cron に巻き戻されることはない。
- **`Status` の書き込みは主文脈が行い、実装担当には行わせない**。実装担当は isolated な作業ツリーで動く狭い権限のロールであり、Projects への書き込みをその allowlist へ足すのは実装ロールへの権限拡大になる。主文脈は既に GitHub 操作とオーケストレーションを担っている。
- dispatch には Issue 番号、関連ノード、作業スコープなどタスク固有情報だけを渡す。恒常的な共有契約は各 PF の常設設定またはこの共通本文を参照させる。
- 戻り値は変更ファイル、テスト結果、PR（ある場合）、スコープ外指摘を含むハンドオフとする。STOP は主文脈が受けてオーナーへ打ち上げる。**戻り値の絶対パスが読めない場合は、main 作業ツリーの `tmp/_handoff/collected/` 配下の回収済みコピーを確認する**（isolated worktree は回収後に削除されうるため。詳細手順は各 PF の troubleshooting を参照）。
- **実装担当が STOP を返したら、`Status` を `Ready` へ戻してからオーナーへ打ち上げる**。戻さないと STOP した Issue が `In progress` のまま滞留し、同期ツールも（`In progress` を対象外にしているため）その滞留を解消できない。

### ②-b 初回レビュー

- 初回レビューのモデル層／推論予算はリスク信号で選ぶ。共有資産、広域変更、前例のない判断、権限境界、曖昧な仕様があれば判断ボトルネックとして高い側を選び、根拠を1行残す。具体的な設定キーと写像は各 PF wrapper に置く。
- レビュー担当は各 finding の実害、根拠、期待値、再確認方法、処置要否、処置担当を構造化して返す。構造化 finding は `harm`/`harm_detail`/`severity`/`scope`/`locus`/`summary`/`evidence`/`expected`/`recheck`/`status` をキーとして返す。レビューコメントには AI 対応であることと具体的な変更・根拠を残す。
- **スコープ外の指摘も同じ finding の列に入れる**。別のセクション・チャットでの列挙へ逃がさない。スコープ内外は `scope: in | out` の申告として記録するだけで、`harm` の判定・記録台帳・clean 判定のいずれの免除にもならない。レビュー担当の `scope` は申告であって確定ではなく、主文脈・オーナーが覆せる。
- **レビュー結果（初回・再レビューとも）を審査中の当該 PR へコメント投稿するのは、主文脈が毎回のオーナー確認なしに行う既定動作である。** レビュー担当は非対話で外部投稿できないため、返ってきた構造化 finding を主文脈が当該 PR へ AI 帰属明記でコメントする。これは既に能動レビュー中の当該成果物へ AI 帰属の記録を残すだけで、その PR を超える新たな外部露出を作らないため、`.ai/guidance/common.md`（PF 共通 guidance）「作業分離・判断境界」の「外部への投稿は実行前に確認」の対象外として扱う。**対象外はこの一件に限る**——マージ、PR 本文の書き換え、別 PR・別 Issue・別リポジトリ・その他外部サービスへの投稿は従来どおり実行前のチャット確認が要る。
- 承認・却下・clean を偽らない。未解消 finding があれば処置ループへ進む。

### ②-c 是正 → 再レビュー

- 是正は初回実装担当ではなく、レビュー指摘を受ける是正担当へ差し戻す。レビュー結果を先に記録し、是正担当は診断してから変更する。
- **レビュー結果を記録するとき、実装担当・是正担当のハンドオフに載った `out_of_scope_findings` も同じ finding の列へ写して記録する**。レビュー担当の指摘だけを記録して実装側のスコープ外指摘を記録しないと、同じ迂回経路が半分残る。記録の実行は主文脈が行う（当事者ロールには行わせない）。
- **オーナーが決めた `disposition` と、主文脈が覆した `scope` は、主文脈が取り込みレポートへ書き足してから記録する。** レビュー担当は `disposition` を書かない契約（処置方針はオーナー専権）であり、実装担当・是正担当のハンドオフにも `disposition` 系のキーは無い。したがって決定を台帳へ入れる担い手は主文脈だけである。手順は次のとおり。
  1. レビュー担当が返した finding レポートを受け取る（`disposition` は未記載）。
  2. `harm: real` の finding についてオーナーの処置方針（`fix-here` / `deferred` / `waived`）を仰ぐ。`deferred` なら行き先 Issue、`waived` なら許可者と理由もオーナーから得る。
  3. 主文脈がその決定を、当該 finding のブロックへ `disposition:` とその付随キー（`deferred_to` / `waived_by` / `waived_reason`）として書き足す。`scope` を覆すと決めた場合は `scope` の値も同じ場所で書き換える。
  4. 書き足したレポートを記録台帳へ取り込む（当事者ロールには取り込みを行わせない）。
- **決定は毎ラウンド再掲する。** 取り込みは前ラウンドで未解消だった finding の全件再掲を要求し、`scope` / `disposition` 系の値は毎ラウンドのレポートで上書きされる。前ラウンドで `deferred` と決めた finding を次ラウンドのレポートで無記載のまま再掲すると、その決定は未決定へ戻り、verdict が実害あり残存へ戻ってオーナー STOP が繰り返される。再掲時は前ラウンドの `disposition` をそのまま書き写す（オーナーが方針を変えた場合だけ新しい値にする）。書き忘れが fail-close 側（未決定＝clean を妨げる）へ倒れるのは意図した設計であり、黙って据え置かれるより安全という判断である。
- 再レビューは既定のレビュー設定で行う。ラウンド上限で打ち切らず、実害と無進捗を基準に続行・停止を判定する。
- **clean の条件は「未解消 finding が0件」ではなく「clean を妨げる未解消 finding が0件」**である（次節）。clean ならマージ経路へ進む。残る finding が実害なしだけでも握りつぶさず、起票案＋理由付き推奨を添えてオーナー判断を仰ぐ。

### ②-d マージ → クローズ

- clean 判定後に、マージ権限を持つ担当が merge する。
- merge は merge commit 方式（`gh pr merge --merge`）で行い、`--squash` は使わない。
- `Closes #N` で自動クローズされない場合は主文脈がクローズする。merge と close を確認してから次の Issue に進む。

## スコープ・先送り・矛盾

- 現 PR のスコープを超える対応は別 Issue に切り出し、現 PR に混ぜない。
- 先送り、繰り越し、対応不要は AI が独断で決めない。背景、検討結果、メリット／デメリット、推奨を示してオーナーの明示判断を得る。
- 既存決定と両立しない事実は勝手に解決しない。必要なら Q/FND 等の正式な記録を先に起票し、推奨を添えて停止する。

## 実害の定義とエスカレーション

`harm` は `real` または `none` とする。次のいずれかに該当する finding は `real` とする。

1. 仕様・設計との不一致、テスト退行、期待値の誤り。
2. fail-close、機械ゲート、検証、権限境界の迂回。
3. 正本・履歴・データの破損、契約違反、秘密・無認可コスト。
4. 後工程の誤読、名前と実体の不一致、トレーサビリティ断絶、正本の分岐、暗黙の前提、観測不能、再現性の欠如。

上記に該当しない純粋な語順・整形の好みや、根拠のない推測は `none` とする。迷ったら `real` 側に倒し、理由を `harm_detail` に書く。

**スコープ外（`scope: out`）は実害判定の免除ではない。** スコープの内外は「誰がいつ直すか」の話であって「実害があるか」の話ではないため、判定軸を混ぜない。スコープ外と分類した指摘も `harm` を必ず付け、同じ finding の列へ記録する。

**実害ありの指摘には処置方針（`disposition`）の記録を要求する。** `harm: real` の finding は `scope` の値にかかわらず、次のいずれかが記録されるまで未処置とみなす。

- `fix-here` — 当該 PR で直す。直って `status: resolved` になるまで clean を妨げる。
- `deferred` — 別 Issue へ申し送る。**行き先の Issue（`deferred_to`）を必須**とする。リンクのない申し送りは行き先不明になるため認めない。
- `waived` — オーナーが明示的に処置不要を許可する。**許可者と理由を必須**とする（「対応不要」を AI が独断で決めない、に対する**記録の強制**。許可者本人であることまでは機械検証していないため、運用規律との併用が前提）。

**実害ありで処置方針が未決定の finding が1件でも残る間は clean にしない。** 属性を足すだけでは「判断が要ることに誰かが気づく」必要が残るため、判定は機械側（記録台帳の verdict）に置く。`deferred` と `waived` は clean を妨げなくなるが、**`status` は `open` のまま残す**——`deferred` を `resolved` にすると「別 Issue へ移したと書くだけで指摘が消える」経路ができ、同じ穴が形を変えて再発する。

**この解除力は `harm: real` の finding にだけ与える。** `harm: none` の finding に `disposition` を書いても記録が残るだけで verdict は動かない。実害なしの指摘に `deferred` と行き先を 2 行書くだけで clean にできると、下記の「未解消がすべて実害なしになった」STOP を AI が単独で消せてしまうためである。

次の場合は主文脈が STOP してオーナーへ打ち上げる。

- clean を妨げる未解消 finding が残り、それがすべて `harm: none` になった（記録台帳の verdict が `no-harm-only`）。**この verdict は「台帳の未解消が全件実害なし」を意味しない**——オーナーが申し送り（`deferred`）／処置不要（`waived`）と決めた `harm: real` の finding は `status: open` のまま別に残りうる。打ち上げるときは、残っている実害ありの finding とその処置方針も併せて示す。
- `harm: real` の finding に処置方針（`fix-here` / `deferred` / `waived`）が未決定のまま残っている。処置方針の決定はオーナー判断であり、AI が単独で `waived` を選ばない。
- 記録台帳が無進捗と判定した（clean を妨げる同一 finding が3ラウンド連続で未解消）。**申し送り（`deferred`）／処置不要（`waived`）と決めた finding はこの計数から外れる**——誰も直さないと決めたものを数えると打ち上げが毎回鳴り、本物の無進捗が偽陽性に紛れて見落とされる。判定は台帳側に置き、条文からこの条件を再実装しない。
- 診断・記録の類似飽和から転換しても解消できない。
- 是正担当が `status: stop`（矛盾・情報不足）を返した。

## 共通指示の配り方

恒常契約（決定点で前提・背景・メリット／デメリット・選択肢・推奨を添える、曖昧は STOP、スコープ外は起票提案）は PF の常設定義から適用する。dispatch prompt は毎回タスク固有情報だけにし、PF 専用の実行機構／権限／起動方式は各 wrapper に置く。重い調査の結果は素案であり、正本への無検証採用や確定著作に使わない。

## 初回レビューのリスク信号

レビューは Bloom Lv5 の評価とする。判断ボトルネック側の信号が1つでも強ければ大きい推論予算、すべて網羅性側なら既定の推論予算とする。

| 信号 | 既定の推論予算寄り（網羅性） | 大きい推論予算寄り（判断） |
|---|---|---|
| ブラストレディアス | 局所（1〜数ファイル） | 共有資産・コーパス横断・多数の参照伝搬 |
| 変更規模 | 小・定型追加 | 構造改変・広域リファクタ |
| パターンの新規性 | 既存パターン踏襲 | 前例なし・新規構造・設計判断 |
| 対象の性質 | プローズ・資産テキスト | 権限境界・グラフ構造・型 |
| 可逆性 | 容易に差し戻せる | 不可逆・広範囲に波及 |
| 仕様の明確さ | 受入基準が一意 | 曖昧・利害 trade-off・解釈の余地 |

迷ったら大きい推論予算側に倒し、選定根拠を1行残す。レート制限やセッション上限を理由に降格しない。再レビューは既定の推論予算とし、初回のリスク信号で降格しない。

## done

- 推奨順を依存グラフ＋根拠付きで提示し、構成の妥当性（分割漏れ・集約漏れ）の判定結果も添えて、オーナー承認を得ている。
- 各 Issue が implement→PR→review→merge→close を1件ずつ完結している。
- 初回レビューのモデル層／推論予算と根拠、レビュー finding、是正・再レビュー結果が記録されている。
- スコープ外対応は別 Issue、先送り・据え置きはオーナー明示判断になっている。
- スコープ外の指摘も finding として同じ列に記録され、実害ありの指摘は処置方針（`fix-here` / `deferred` / `waived`）が決まってから merge している。
- 主文脈は実装・レビューを代行せず、タスク管理・進捗報告・意思決定に専念している。
