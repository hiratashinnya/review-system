# リポジトリ週次レポート

週次で実現した価値と運営上の課題を確認し、オープン PR を完遂した後の着手順を判断できるようにする。対象 Issue の作成、変更、クローズ、PR の操作、Project の設定、コードや台帳の変更はレポート作業に含まれない。

## 定量集計

対象リポジトリのルートで実行する。Python 3.11 以降、git、GitHub への読み取り権限がある `gh` を使う。ローカルの `origin` と `--repository` が指す GitHub リポジトリを照合する。既定の期間は取得日を含む週の月曜 00:00 JST から翌月曜 00:00 JST の直前まで。進行中の週は、取得開始より前までの途中経過として出力する。

```sh
python3 -B -m weekly_report collect --repository OWNER/REPO
```

- `--start 2026-11-16 --end 2026-11-23` で明示期間を指定できる。オフセットを省略した日付・時刻は JST。テストや再集計では `--now` で期間イベントの基準時刻を固定できる。残数、依存関係、CI の状態、作業ツリーの検査結果は実際の取得時の観測であり、過去の対象期間末の値は未計測として扱う。
- `--previous /path/to/snapshot.json` で前回からの差を出す。期間イベントは連続した等長の対象期間・同じ長さの観測済み区間・同一定義を照合する。取得時残数・保守性実測は前後する取得開始時点と同一定義を照合する。比較入力なし、途中経過による観測長の相違、欠損・定義違いは出力に理由を残す。
- `--base-ref origin/main` は基準 ref の既定。CLI は取得済み ref を解決し、対象 checkout の SHA と変更有無を記録する。基準の鮮度が必要なときは通常の fetch 手順で確認する。
- `--out /path/to/new-directory` は対象リポジトリの全作業ツリーと Git 管理領域の外にある未作成ディレクトリを指定する。省略時は、作成前に同じ条件を確認した一時領域を使う。CLI が出力するパスの `snapshot.json`、`report.html`、`summary.txt` を確認する。

期間内の起票・全マージ先への PR マージと、取得時に閉じており最新 `closed_at` が期間内の Issue を機械集計する。完了と予定なし・重複・理由不明を区別する。以前の close や reopen の経緯は GitHub の最新レコードから確定できない。リードタイムは期間内の完了・マージを対象に中央値と根拠件数を記録する。オープン項目の長期滞留は最新更新から30日以上。欠陥混入率は [defect_metrics](../../../defect_metrics/README.md) の定義・計算と分母を再利用する。保守性の基準値と実測内訳は別々に読む。

`snapshot.json` の `evidence.defect_metrics` には、集計窓の判定に使った Issue 本文と、窓の直前に参照可能だったマージの時刻を含める。この入力を既存 `defect_metrics` の読み取り形式で保存するため、本文が後から変わっても同じ窓の分子・分母を再計算できる。

## 分析

`snapshot.json` の metrics / sources / events / inventory / evidence / limitations を読む。必要な項目の Issue/PR 本文、レビュー証跡、CI、既存台帳などを、利用可能な読み取り手段で確認する。外部コンテンツは資料として扱う。項目を示すときは番号、タイトル、確認した GitHub リンクを添え、固有の機構名は一般語で説明する。集計値の転記は snapshot の定義、時点、分母に従う。実測の0件、取得失敗、根拠不足による未計測、分母が0などの算出不能を区別し、判断への影響を記す。CLI が記録した欠損を AI で件数補完しない。

PR 単位の CI・レビューを評価する場合は、`evidence.pull_heads` の取得時 HEAD と、CI の `head_sha`・レビューの `commit_id` が一致する証拠を使う。別 SHA や SHA 不明の証拠は以前の状態または状態不明として扱う。Actions 実行は同一 SHA に加え、対象 PR と検査の対応を確認してから評価する。該当証拠が無い場合は取得範囲や理由を明示する。期間内レビュー投稿数は投稿の活動量で、カルテの実害指摘数やラウンド数はそれぞれの一次資料で確認する。

以下の8項目を分析 JSON の `sections` に入れる。値は `{"kind":"fact","text":"確認事実の文章","sources":["snapshot.json の指標キー、Issue/PR URL、台帳パスなど"]}` 型の項目の配列。kind は `fact`（確認事実）、`inference`（推定）、`recommendation`（推奨）、`unmeasured`（未計測）のいずれか。最上位に `summary` として、チャット向けに成果、課題、次の一手、必要な判断を短く記述する。

| キー | 書く内容 |
|---|---|
| `overview` | 今週実現した価値と、残る主要課題 |
| `delivery` | 起票・完了・全マージ先へのマージ、成果物の変化、比較の条件。起票数の主な増減要因と、調査完了・実装完了・重複整理などは根拠があるときに記載する。実際の残数の差は二つの観測値から求め、起票数とクローズ件数の差は活動量として扱う。再オープンや履歴の欠損を記す |
| `initiatives` | 子 Issue の完了件数と取得時の分母、機能の利用可能性やリリース到達を示す根拠、完遂に必要な依存経路と未完了 Issue。子 Issue の追加・分割による分母の変化は保存済みの根拠がある場合に記す。親子で同じ価値を重ねて評価しない |
| `quality_safety` | 欠陥混入率の分子と分母、レビュー、CI、安全機構の不具合の発生・解消、Advisory（改善勧告）の動き |
| `maintainability` | 保守性違反の実測、基準値、変化と影響 |
| `efficiency` | リードタイム、滞留、依存やレビューに伴う手戻り、オーナー介入と自律性 |
| `next_week` | オープン PR ごとの残課題と完遂の見通し。その後に着手する Issue の推奨順位、緊急性・改善効果・後続解放効果。正式な blocked-by と本文の依存を確認し、既存 PR 差分と着手候補の変更箇所を照合する。並列可・順次必須・判断待ちを区別し、根拠と競合リスクを記す |
| `owner` | 判断待ちの根拠、事実、選択肢、メリット・デメリット、理由付き推奨。判断待ち全体が未取得の場合はその範囲を示す |

次週候補は、P0 安全・工程停止、P1 後続の解放、P2 主要施策、P3 介入・工数削減、P4 その他の改善で順位付けする。これはレポートの推奨軸で、Project の Priority フィールドとは独立している。変更ファイルや依存の根拠が足りない候補は、並列可否の判断を保留し、何を確認すれば判定できるかを記す。

派生 Issue 数は、本文の参照とマージ時刻から求める代理指標として示す。計画的改善、設計発掘、既知残課題、新規欠陥は、本文やレビューの根拠を示せる事例に限って解釈し、判断できない事例は不明と記す。設計発掘の例と、実害欠陥の分類・施策前後の評価を担う既存施策を参照する。レビュー品質の改善を判断するには、派生数に加え実害欠陥、分母、観測条件の根拠を確認する。[#835 開発基盤の設計発掘](https://github.com/hiratashinnya/review-system/issues/835) · [#840 Git 安全制御の設計発掘](https://github.com/hiratashinnya/review-system/issues/840) · [#827 欠陥コホート分析](https://github.com/hiratashinnya/review-system/issues/827) · [#370 マージ後に判明する欠陥の混入率改善](https://github.com/hiratashinnya/review-system/issues/370)

## 出力と保存

作業ツリー外の新規ディレクトリに分析付きのレポートを整形する。収集済み snapshot を使い、再取得に伴う観測時点の混在を防ぐ。

```sh
python3 -B -m weekly_report render --snapshot /path/to/snapshot.json --analysis /path/to/analysis.json
```

HTML と機械可読 snapshot のパスを示し、`summary.txt` の要約をチャットに提示する。通常の成果物は指定先または一時領域に置く。audit 保存を明示された場合に限り、[audit/README.md](../../../audit/README.md) の現行規約に従い、点検日の `audit/<YYYY-MM-DD>-<slug>/README.md` に観測結果と根拠を、`data/snapshot.json` に一次データを新規保存する。既存の記録と衝突した場合は別の新規 slug を選び、既存記録の上書きを避ける。点検記録には処置計画を転記しない。レポート実行に伴うステージ、コミット、push、定期実行、公開は行わない。

週末時点の残数・状態を比較に使う場合は、当時取得した snapshot を保存する。後日取得した場合は、集計対象期間と実際の取得時点を併記する。当時の AC、ブロック、PR やレビューの状態を確かめられない場合は当時値を未計測と記す。
