# レビュー finding の実害判定

`harm` は `real` または `none` とする。次のいずれかに該当する finding は `real` とする。

1. 仕様・設計との不一致、テスト退行、期待値の誤り。
2. fail-close、機械ゲート、検証、権限境界の迂回。
3. 正本・履歴・データの破損、契約違反、秘密・無認可コスト。
4. 後工程の誤読、名前と実体の不一致、トレーサビリティ断絶、正本の分岐、暗黙の前提、観測不能、再現性の欠如。

上記に該当しない純粋な語順・整形の好みや、根拠のない推測は `none` とする。迷ったら `real` 側に倒し、理由を `harm_detail` に書く。

**スコープ外（`scope: out`）は実害判定の免除ではない。** スコープ外と分類した指摘も `harm` を必ず付け、同じ finding の列へ記録する。

**harm_detail に書くのは実害だけ**：harm_detail は「放置すると何が壊れるか」という観測可能な実害だけを書く欄で、「対応不要と判断した理由」「オーナー確認済み」「本 PR の差分範囲外」「新規発生ではない」のような処置方針・判断経緯を書く欄ではない。決まったオーナー判断は disposition / deferred_to / waived_reason に記録されるもので、レビュー担当が書く欄ではない。処置方針・判断経緯を示す語が実害の記述として避けられないときは、まず実害そのものの言い換えを試し、それでも残るなら `karte/allowlist.py` へ理由付きで登録する。実害なしは対応不要を意味せず、処置方針の決定はオーナーの責務である。scope は申告であり、覆す権限はオーナーにある。

| harm | scope | 判定例と根拠 |
| --- | --- | --- |
| real | in | 対象変更でデータが失われる。正本・データの破損という実害がある。 |
| real | out | 対象外の権限検査を迂回できる。対象外でも権限境界の迂回という実害がある。 |
| none | in | 対象変更の語順の好みだけで意味や挙動に差がない。実害の根拠がない。 |
| none | out | 対象外の整形の好みだけで意味や挙動に差がない。実害の根拠がない。 |

将来の finding-triager は実装時にこの正本をコンテキストに供給し、同じ基準を使用する。レビュー原本と triage の判断成果物は別に保持し、オーナーの権限を侵さない。
