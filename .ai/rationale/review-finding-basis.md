# Issue #830 — finding の実運用根拠を後段へ引き渡す

## オーナー決定と設計理由（2026-11-15）

論理的には成立しても実運用では到達不能な指摘や、善意の誤操作防止に対して悪意ある攻撃者を当然の前提とする指摘でレビューが収束しない事象を問題とした。

**採用: 案B。** reviewer の finding を削らず、実運用での到達経路・前提脅威の根拠を入力し、後段の triager が理由付きの棄却候補を集約提示する。棄却・評価は Issue #832、レビュー工程への結線は #784/#785 側の責務であり、本変更では行わない。

**却下:** 根拠を示せない finding の抑止（欠陥見落としの危険）／到達性を理由に reviewer の harm を弱める案A（実害判定の意味が混ざる）／PR #816 への同梱（独立した小PRを優先）。

## 規範と互換性

2欄の名称・最小記載要件・表記・旧形式の扱いの正本は [review-finding-basis](../guidance/review-finding-basis.md)。既存の `harm_detail` は放置時の実害のみを記す独立欄のまま。

従来のレポートと進行中のKarteは未知キーを持たないため、パーサは欄欠落を許す。新規 reviewer 契約では2欄の明記を要求する。明記された空欄とリストは不正として拒否し、未記載の旧形式は空文字のまま保持する。台帳は2欄をrender/parseし、従来形式の再取り込みで既に保存した根拠を破棄しない。

## 他ロールの適用判定

- `pr-reviewer` の PR 差分レビューと TestDesign（2a）レビュー: 同一 finding schema を使うため適用する。
- `plan-reviewer`: 規約上 pr-reviewer と同じ finding schema で返すため適用する。設計・計画だけの段階では実行経路が未検証である旨を明記し、分からなければ `根拠なし` とする。
- `finding-triager`: 本Issueで reviewer としての出力契約を追加しない。後段の入力として2欄が届くことを維持する。評価は #832。
- その他の工程ロール: 同じ structured finding を出す契約が確認できないため、今回は変更しない。

## 効果測定（稼働後）

`#784/#785` の稼働以降、finding 1件単位で (1) 2欄の記載率、(2) `根拠なし` 率、(3) triagerの棄却候補件数と理由の内訳、(4) owner判断件数、(5) 修正→再レビューのラウンド数、(6) 誤棄却候補件数を継続観測する。適用前後比較にはレビュー対象の規模・件数とphaseを併記し、単純な件数低下を欠陥検出力の改善とみなさない。本Issueでは実測値を主張しない。
