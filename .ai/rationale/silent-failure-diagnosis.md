# silent-failure-diagnosis — 設計経緯・却下案・既知の制約（rationale・非規範）

> **これは規範ではない。** 正本は `.ai/skills/silent-failure-diagnosis/SKILL.md`（共通本文）であり、本文はこの共有リファレンスの設計背景・却下案・PR #260 からの変更点・既知の制約を保管する。

Claude Code (AI) が Issue #605（親 tracking＝#575）で新設した。close 済み PR #260 の再実装である。

## 発端

2026-07-27〜28 の agy 調査で、「agy は Windows 側で実行されるから WSL のリポジトリを読めない」という根本原因を一度断定し、追調査で覆した（実際は読めた）。同じ誤診を繰り返さないために、ツール非依存の観測規律として資産化したのが PR #260 である。PR #260 は4ツリー直書きなど現行の `.ai` 正本構成と合わず、方針変更により close された。要点は Issue #291 のコメント（2026-10-05）に記録されている。

各一般則の由来（PR #260 本文の記録）：

| # | 一般則 | 由来した実際の躓き |
|---|---|---|
| D1 | 出力を評価する前に、入力を読んだかを確かめる | agy がリポジトリを一度も開かず、scratch で作業して回答した |
| D2 | 総合判定を鵜呑みにしない | `Overall: PROBLEMS FOUND` は実害なし（偽陽性）、`OK` でも到達性は未検査（偽陰性） |
| D3 | 単発の結果から因果を断定しない | UNC パスの1回の失敗から「UNC 非対応」と誤って断定した |
| D4 | 比較対象の版・更新時刻の同一性 | 調査中に agy が 1.1.1→1.1.7 に自動更新され、異なるバイナリを比較していた |
| D5 | 永続ログ・履歴の時系列で回帰境界を絞る | 会話 DB の日付比較で「7/11 までは動いていた」と判明し、原理的不能説を潰せた |
| D6 | 本番の起動経路を特定してから直す | パッケージ版とローカルクローンがあり、直す先を間違えると反映されない |
| D7 | upstream の修正が自分の要件を満たすとは限らない | upstream の修正は権限ゲートの全開放だった |
| D8 | 目的を最小権限で達する解を選ぶ | ワークスペース追加の指定だけで足り、危険フラグは不要だった |

2026-10-11 の agy 1.2.1 調査（Issue #575 本文「実測結果」）で、headless 実行が権限要求を自動拒否しても終了コード 0・`status: SUCCESS` のまま前置き1行を返すことを実測した。これは本スキルが扱う「静かな失敗」の典型例なので、D2 の事例として取り込んだ。

## PR #260 からの変更点

### 1. 配置：`.ai` 正本＋薄い wrapper（4ツリー直書きをやめた）

PR #260 は `.claude/skills/` と `.agents/skills/` に本文をそれぞれ直書きしていた。Issue #408・#448・#539 の方針に合わせ、共通本文を `.ai/skills/silent-failure-diagnosis/SKILL.md` に1つだけ置き、`.claude/skills/`（Claude）と `.agents/skills/`（Codex の repo-skill）は共通本文を指す wrapper にした。`user-invocable: false` は Claude の loader metadata なので Claude wrapper にだけ置き、Codex wrapper は持たない（`spec-principles` の Codex 版と同じ規約）。

### 2. Copilot は非移植（2026-10-12 にオーナーが再確定）

Copilot へは展開せず、`.github/copilot-instructions.md` へも本文をインライン展開しない。Copilot から参照できない状態を意図として受け入れる。したがって Issue #605 の受け入れ基準1「各 PF の入口が接続」の対象 PF は Claude Code と Codex（repo-skill）であり、Copilot を含まない。

- **現時点の判断**：2026-10-12、オーナーが PR #615 レビュー round 1 の F-605-02 に対し、Copilot 非移植を今回あらためて確定した（チャット内の判断）。
- **元の判断**：2026-07-28、close 済み PR #260 の時点でオーナーが同じ非移植を確定していた。ただしその記録は PR #260 の branch の `.claude/tailoring-registry.md` にしか無く、main には入っていない。上の再確定は、この記録を main 上で辿れない状態を解消するためのものである。
- **理由**：本スキルを読み込む予定の委譲系の資産（`agy-delegate`・`codex-review`）がいずれも Copilot 非移植であり、Copilot 側に利用者がいない。

`asset_parity` は `user-invocable: false` の skill を Copilot 列で構造的 `exempt` として扱うため、`MISSING` は出ない。ただしその判定は「Copilot から参照できる」ことの根拠ではない（`asset_parity` はインライン内容を検査しない）。非移植決定の一次情報源は `.claude/tailoring-registry.md` の該当行である。

非移植の記録は、PF 個別管理リスト（`.ai/Individually-managed-lists.md`「個別配置・非移植」）と Copilot 向け常駐 guidance の原稿（`.ai/guidance/platforms/copilot.md`「Copilot 固有の非移植」。生成物は `.github/copilot-instructions.md`）の両方に載せ、一致させる。「`copilot-instructions.md` へ展開しない」は本文（D0〜D8 の規律）をインラインしないという意味であり、非移植一覧に名前を載せることは含まない。配置テスト（`tests/unit/test_silent_failure_diagnosis_layout.py`）もこの定義に合わせ、名前の記載は許し、本文の展開だけを禁じる。

### 3. 適用範囲の境界文を正本にだけ置く（セッション記憶へ追記しない）

PR #260 では、`asset-auditor` が「D3 の再現要求が既存のセッション記憶（冗長な実証確認の禁止）と字面上ぶつかる」と指摘し、オーナー確定で境界文（権威ある静的な主張は再検証しない／外部プロセスのランタイム挙動は実測する）を本文に入れ、**同じ境界文をセッション記憶側にも相互参照として追記した**。後者は `.claude/rules/03-operational.md`「セッション記憶と正本の使い分け」（Issue #484）に反するので、再実装では境界文を共通本文にだけ置き、セッション記憶は変更しない。境界文の意味は維持し、Claude 固有の語（`claude-code-guide` の結論）は PF 中立の表現（公式ドキュメント・仕様書・確定した設計判断）へ置き換えた。

### 4. スキル一覧は `.claude/rules/05-skills-agents.md` へ

PR #260 は `CLAUDE.md` 本体のスキル一覧へ1行を足していた。スキル一覧は `.claude/rules/05-skills-agents.md` へ移っているので、そちらに追記した。`CLAUDE.md` 本体は変更しない。あわせて、どちらのシステムにも含有されない汎用ハーネスとして、`.claude/rules/02-decision-process.md` の起票先判定表（外部委譲の補助）にも名前を足した。

### 5. 一般則とツール固有事象の分担を本文で明示した

PR #260 の分担（ツール固有事象は各ツール資産が正本、本スキルは一般則のみ）は PR 本文と registry に書かれていただけで、スキル本文には責務境界表の1行しかなかった。再実装では本文に「一般則とツール固有事象の分担」節を置き、次を明記した：特定ツールの兆候・フィールド名・回復手順は持たない、ツール資産が停止側に厳しいときはツール資産に従う、記載の無い兆候はツール資産の改訂として報告する。

### 6. D0 の例外リストの置き場所をツール資産へ移した（承認要件は維持）

PR #260 の D0 は「例外は本スキルのリストに事前記載され、かつオーナーの明示承認が記録されたものだけ」とし、リストに `codex-review` の rollout 回収（自分の `thread_id` に束縛された1ファイルに限る・オーナー確定 2026-07-28）を1件載せていた。あわせて「flag 後の再提出（同一セッションの言い換え・新規セッションでの流し直し）は例外に含まれない」としていた。

再実装では例外の**置き場所**だけをツール資産へ移し、**オーナー承認の記録を要するという要件は残した**。D0 で許される3つ目の行為は「そのツール資産に、D0 の例外としてオーナー承認の記録がある回復手順を、記載の範囲で実行する」であり、手順が書かれているだけでは例外にならない。あわせて、迂回として列挙した行為（flag 後の再提出を含む）は例外として記録されていても許されないこと、既存の証拠を読む範囲は例外でも当該実行に束縛された範囲を超えないことを D0 本文に明記した。

この形はオーナー判断（2026-10-12・PR #615 レビュー round 1 の F-605-01 に対する選択肢 B）による。理由：

- 特定ツールの回復手順を一般則の側に列挙すると、分担（ツール固有事象はツール資産が正本）に反し、ツール側の手順と二重の正本になる。そこで列挙はツール資産側に置く。
- 一方で、初版の再実装（承認要件を外し「文書化された回復手順」だけを条件にした形）は、ツール資産に記載があるだけで、D0 が迂回として挙げた行為（別セッション・言い換えでの再提出、範囲を絞らない記録の読み取り）を許可と読める余地を作った。PR #260 の承認要件はこの余地を塞ぐためのものなので外さない。
- 「その場で例外を新設しない」「承認→記載→適用の順」という核は維持した。

**実際の効果（現行の `codex-review` 手順との関係）**：本スキルは 2026-07-28 にオーナーが確定した `codex-review` 側の判断（rollout 回収を自分の `thread_id` の1ファイルに限る・flag 後の再提出は迂回とみなす）を、一般則と事例として D0 に取り込んでいる。round 1 の時点の `.ai/troubleshooting/codex-review.md`「cyber フィルタで最終応答が置き換わった」節は、新規セッションでの防御形式への言い換え再提出と、直近の日付ディレクトリの rollout 読み取りを回復手順としており、D0 の例外としての承認記録も持たなかった。本スキルの D0 の下では、前者は迂回に、後者は束縛の無い読み取りに当たる。round 1 ではこの食い違いを本 PR で直さない方針だったが、round 2 の F-605-06 に対するオーナー判断（2026-10-12）で本 PR で直すことになった。同節は、flag 後の再提出を迂回として禁じ、rollout 回収を自分の `thread_id` の1ファイルに限り、D0 の例外としての承認記録（承認者＝オーナー・承認日 2026-07-28）を持つ形へ改訂した。経緯は `.ai/rationale/codex-review.md`。`codex-review` の安全実行契約の再実装は行っていない（Issue #575 の Out of scope）。

### 7. D2 を「成功シグナル全般」へ広げた

PR #260 の D2 は診断コマンドの総合判定（`Overall: OK` 等）だけを扱っていた。agy 1.2.1 の実測で、終了コード 0 と `status: SUCCESS` も同じ形で誤ることが分かったため、終了コード・status 表示を含む成功シグナル全般に広げ、副チャネル（構造化出力の拒否欄・stderr・タイムアウト通知）を読むことと、中身の妥当性（空・前置き1行・途中切れ）を確かめることを足した。見つけた拒否は D0 として扱い、権限を広げて再試行しない（D8 と接続する）。診断の順序では D2 を D1 の直後へ移した。隠れた拒否は D0 に戻る入口なので、早く確かめるほど無駄なプローブが減るためである。

PR #260 の D2 は「総合判定をゲート条件にしない」とも書いていた。現行の `agy-delegate` は `Overall: OK` を移譲の前提条件（fail-close）にしており、PR #260 ではこれを同時に外す PR #259 が前提だった。#259 の再実装は兄弟 Issue #606 の範囲なので、本スキルは「ツール資産がゲート条件として定めているなら従って止まる。ただし通過を用途の可否の証拠にしない。偽陽性の疑いはツール資産の改訂として報告する」とした。ゲート条件を外すかどうかは `agy-delegate` 側（#606）で決める。
