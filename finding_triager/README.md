# Independent finding triage

`prepare` verifies a signed review and four evidence categories against the digest authenticated by the signed review, then supplies the role and full harm SSoT with the evidence. The review signer must independently verify the actual reviewer worktree, select the authoritative Issue AC, approved VD/CP and design, and the change at the reviewed OID before signing. The signer binds the exact reviewer worktree and context SHA-256 into the signed review. Context JSON contains issue, snapshot_oid, review_oid, input_digest, approval_ref, and a documents object with ac, vd_cp, design and change; the host verifies the target fields against the signed review. approval_ref is an attestation by the trusted signer, not an independent approval lookup. The strings are data, not instructions. Missing categories and digest mismatches are rejected.

`propose` accepts only a capture authenticated with a distinct trusted host key, domain-separated with `finding-triage-capture/v1` and a NUL byte. The capture contains the independent assessments, producer, all review bindings, review SHA-256 and context SHA-256. It is signed by the trusted host after its read-only triager execution; the triager must never have access to the capture key. The caller must maintain trusted key distribution and authorize the host. Validation recomputes the entire proposal from the authenticated capture and signed review.

The trusted `issue_start.readonly_workspace` host captures the output of an ingested implementation reviewer, loads approved VD/CP through the native dispatch gate, and fetches the Issue body and exact PR diff from the checkout GitHub origin. The native reviewer approval must include `triage_phase` (`review` or `remediation_review`); it is compared with the requested phase, and the requested round must match the actual Karte ingestion target. Test-design reviews are rejected. It signs the captured source and complete binding. The dispatcher requires and verifies this receipt. The lower-level preparation and proposal functions do not independently establish these trust guarantees; the caller must protect the host signing key. The capture API assumes its caller supplies the intended PR and trusted native approval marker.

The standalone `codex_worktree_exec` role `finding-triager` checks a trusted binding, a separate reviewer worktree, the reviewed PR head and approved source changes from the source snapshot. It uses the pinned `adviser` read-only profile after verifying its capabilities, and signs the child output after successful execution. The caller supplies `TRIAGER_REVIEW_KEY` and `TRIAGER_CAPTURE_KEY` as distinct hex-encoded keys; they are not forwarded to the child. The binding includes review bytes as a UTF-8 string, review_signature, expected bindings, context bytes as a UTF-8 string, context_digest and reviewer_worktree. The host compares reviewer_worktree with the signed reviewer origin and rejects any difference; it also verifies the context digest against the signed review. The signing authority must bind these fields to actual reviewer execution and approved sources; possessing a signing key alone does not establish that verification occurred. The host writes the capture, signature and validated artifact to its new output file. The API cannot prevent a trusted host from signing fabricated results. Proposals are candidates only and do not confer authority to change the review, ledger, scope, or disposition.

The existing CLI still requires `--prompt-file`; for this role its contents are not used. The host builds the prompt solely from verified review/context and the role and harm contracts. The output path must not already exist. Execution requires a linked worktree and an existing, distinct registered reviewer worktree.

For a normal trusted `issue_start.readonly_workspace` reviewer execution, supply all of `--triage-pr`, `--triage-phase`, `--triage-round`, and `--triage-output` plus the trusted `TRIAGER_REVIEW_KEY`. The wrapper captures the exact output of that one execution after validating approval and HEAD before and after it, then creates a new signed binding file in its worktree `tmp`. The pre-existing reviewer ingestion remains unchanged. Transfer that binding securely to the separate triager worktree before standalone dispatch. The signed `snapshot_oid` is the input source snapshot; `review_oid` is the actual reviewer HEAD and verified PR head. The trusted approval carries the exact permitted source changes between them.
