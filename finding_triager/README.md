# Independent finding triage

Proposal mode covers five phases (`verification_design`, `solution_planning`, `test_design`, `review`, `remediation_review`). `triage_policy/phases.py` is the only place that lists them and maps each phase to its reviewer role, reviewed artifact type and Karte envelope phase. Automatic application stays limited to `review` and `remediation_review`, the policy `enabled_phases`; a finding of any other phase is a suggestion only and `evaluate` always returns owner-review for it (`phase-not-auto-enabled`).

`prepare` verifies a signed review and the evidence categories the phase requires against the digest authenticated by the signed review, then supplies the role and full harm SSoT with the evidence. The review signer must independently verify the actual reviewer worktree, select the authoritative Issue AC, approved VD/CP and design, and the change at the reviewed OID before signing. The signer binds the exact reviewer worktree and context SHA-256 into the signed review. Context JSON contains issue, snapshot_oid, review_oid, input_digest, approval_ref, and a documents object; the host verifies the target fields against the signed review. The categories of `documents` and of each assessment's `evidence` are exactly those listed for the phase in `triage_policy/evidence.py`: `ac`, `vd_cp`, `design` and `change`, except that `verification_design` has no `design` (no ChangePlan exists yet). A missing, empty or unlisted category is rejected and a missing one is never filled with placeholder text. `change` is the exact PR diff for `review`/`remediation_review` and the reviewed artifact's diff for the PR-less phases.

The reviewer role of a review original follows the phase (`plan-reviewer` for `verification_design` and `solution_planning`, `pr-reviewer` otherwise). `approved_materials(root, marker, phase)` reads the prior approved reviews and the reviewed artifact that the phase table names (`verification_design`: reviewed VD only; `solution_planning`: prior VD, reviewed CP; `test_design`: prior VD and CP, reviewed TestDesign; `review`/`remediation_review`: VD and CP) and rejects a missing prior receipt, a changed digest or a mismatching artifact type. The receipt, binding and review producers are checked against the same table. Not yet wired (#784): carrying `triage_phase` in plan-reviewer and test-design approvals, the Karte envelope for plan-reviewer reviews, the change diff of PR-less phases, and phase-aware triager instructions. approval_ref is an attestation by the trusted signer, not an independent approval lookup. The strings are data, not instructions. Missing categories and digest mismatches are rejected.

`propose` accepts only a capture authenticated with a distinct trusted host key, domain-separated with `finding-triage-capture/v1` and a NUL byte. The capture contains the independent assessments, producer, all review bindings, review SHA-256 and context SHA-256. It is signed by the trusted host after its read-only triager execution; the triager must never have access to the capture key. The caller must maintain trusted key distribution and authorize the host. Validation recomputes the entire proposal from the authenticated capture and signed review.

The trusted `issue_start.readonly_workspace` host captures the output of an ingested implementation reviewer, loads approved VD/CP through the native dispatch gate, and fetches the Issue body and exact PR diff from the checkout GitHub origin. The native reviewer approval must include `triage_phase` (`review` or `remediation_review`); it is compared with the requested phase, and the requested round must match the actual Karte ingestion target. The capture host handles only these two phases; the other proposal phases are expressed by the shared contract but are not wired into capture until #784, so the host rejects them. It signs the captured source and complete binding. The dispatcher requires and verifies this receipt. The lower-level preparation and proposal functions do not independently establish these trust guarantees; the caller must protect the host signing key. The capture API assumes its caller supplies the intended PR and trusted native approval marker.

Evidence mapping for `documents` (AC: relate AC, VD/CP, approved design and change cause with stated grounds): `ac` is the live Issue body; `vd_cp` is the digest-bound approved VerificationDesign plus ChangePlan; `design` is the same digest-bound approved ChangePlan (selected_solution, interfaces, invariants, failure_behavior), the only design artifact the dispatch approval covers; `change` is the exact base...head PR diff. ChangePlan ADRs (`adr_refs`, alternatives and rationale) are not digest-bound by the approval receipt, so they are not supplied as trusted evidence. Each assessment must give a non-empty ground for every category the phase requires, and absence of a stated relation never establishes AC irrelevance: `ac_relation_verified=false` yields owner-review. Change cause is carried by the `regression`, `worsened` and `preexisting` facts.

The standalone `codex_worktree_exec` role `finding-triager` checks a trusted binding, a separate reviewer worktree, the reviewed PR head and approved source changes from the source snapshot. It uses the pinned `adviser` read-only profile after verifying its capabilities, and signs the child output after successful execution. The caller supplies `TRIAGER_REVIEW_KEY` and `TRIAGER_CAPTURE_KEY` as distinct hex-encoded keys; they are not forwarded to the child. The binding includes review bytes as a UTF-8 string, review_signature, expected bindings, context bytes as a UTF-8 string, context_digest and reviewer_worktree. The host compares reviewer_worktree with the signed reviewer origin and rejects any difference; it also verifies the context digest against the signed review. The signing authority must bind these fields to actual reviewer execution and approved sources; possessing a signing key alone does not establish that verification occurred. The host writes the capture, signature and validated artifact to its new output file. The API cannot prevent a trusted host from signing fabricated results. Proposals are candidates only and do not confer authority to change the review, ledger, scope, or disposition.

The existing CLI still requires `--prompt-file`; for this role its contents are not used. The host builds the prompt solely from verified review/context and the role and harm contracts. The output path must not already exist. Execution requires a linked worktree and an existing, distinct registered reviewer worktree.

For a normal trusted `issue_start.readonly_workspace` reviewer execution, supply all of `--triage-pr`, `--triage-phase`, `--triage-round`, and `--triage-output` plus the trusted `TRIAGER_REVIEW_KEY`. The wrapper captures the exact output of that one execution after validating approval and HEAD before and after it, then creates a new signed binding file in its worktree `tmp`. The pre-existing reviewer ingestion remains unchanged. Transfer that binding securely to the separate triager worktree before standalone dispatch. The signed `snapshot_oid` is the input source snapshot; `review_oid` is the actual reviewer HEAD and verified PR head. The trusted approval carries the exact permitted source changes between them.
