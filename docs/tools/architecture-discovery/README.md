## F1 に渡す図・根拠の規則

1. 起点の `main` SHA と対象パス、関係する Issue/PR を固定する。入口から入力読取・検証・分岐・状態更新・外部副作用・終了を追跡し、コード、テスト、一次資料を紐づける。予定の契約・古い資料と基準実装に差があれば、両方の出典と影響を示す。
2. PFD は actor／責任主体の swimlane、動詞＋対象の処理名、判定条件、正常終了・失敗・保留/再開を示す。DFD は名詞のデータ名で入口・出口・読み書きの向き、正本・生成物・自己申告と検証済みの区別、保存先と更新主体を示す。両図は Mermaid `flowchart` を使い、処理とテストへの接続は名称・ID で照合できるようにする。[図の表現規約](../../../.ai/skills/orchestration-design/SKILL.md) · [DFD と実装対応の規約](../../../.ai/skills/architecture-design/SKILL.md)
3. Level 0 の `P0`（工程全体）と `D0`（システム境界）を基準に、Level 1 は対応する境界と責任を詳述する。必要な検証・復旧・状態遷移だけを Level 2 に分解する。Level 2 を Level 0 の節点へ直結せず、各段で上位の入出力、失敗時に更新できる範囲と責任を対応表で保つ。ID は節・図をまたいで再利用できるよう `P1-D2-01`（工程）、`D1-D2-01`（データ処理）のように図種・レベル・担当・連番を付ける。ファイル内のアンカーと併用し、ADR の ID 体系は流用しない。
4. 重要な節点・データ・不変条件に、基準 SHA、リポジトリ相対パスと関数/設定キー、確認できるテスト名と観測した条件、必要なら Issue/PR・ADR/FBK/rationale の ID を添える。実装事実と一次資料で確定した判断、推定、不明を明示する。推定/不明には確認先・担当・根拠不足の理由を添える。歴史的判断日や却下案は一次資料が揃うまで確定しない。
5. D1 [#838](https://github.com/hiratashinnya/review-system/issues/838) で Skill の出力と誤認防止を試す。後続 D2〜D5 は各 Issue の受入キューと固定 SHA を照合して図と索引を更新する。差分吸収と独立レビューで残件を確認し、文書出典 SHA と最終照合 SHA を記録する。[C06 追従手順](refactor-handoff.md)
