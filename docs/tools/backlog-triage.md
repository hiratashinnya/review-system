# バックログ棚卸し運用（backlog triage）

> 対象＝**GitHub Issue のバックログ**（doc-system-v2 コーパスの FND/Q/DD は対象外＝`dsv2 dashboard` の担当）。
> オーナー専権の判断（処置要否・据え置き・優先順位）を、**1件ずつではなくまとめて処分できる形**で
> 呈示するための運用。起源＝Issue #376（親 #368）。呼び出し元＝[`/issue-pipeline`](../../.claude/skills/issue-pipeline/SKILL.md) ①。

## 0. 何を変え、何を変えないか

**変えるのは呈示の仕方だけ**：1件ずつ `AskUserQuestion` を積むのをやめ、**クラスタ単位で1回の判断**が
効く処分表を出す。オーナーが1回の判断で N 件を処分できれば、規律を一切緩めずに処理量だけが上がる。

**変えないもの（弱めない）**：

- **判断主体はオーナー**。AI は「対応不要」「繰り越し」を結論として書かない（CLAUDE.md 独断禁止）。
- **起票そのものは抑制しない**。WIP 上限・バックログ凍結はオーナー却下済み（2026-08-16・#368）。
  本運用は**在庫側の処理効率**であって、流入側の対策（#370）ではない。
- **意見なき停止の禁止（PR7）**。表には必ず選択肢と理由付き推奨を添える。

## 1. 契機（trigger）

次のいずれかに該当したら、主文脈がオーナーへ**棚卸しの実施を提案**する（実施可否はオーナー判断）。

| 種別 | 条件 | 備考 |
|---|---|---|
| 定期 | 前回棚卸しから **1 暦月** 経過 | 前回日付は最新の実施記録（§5）から引く |
| 件数 | 前回棚卸しから open が **純増 +15 件**、または open 総数が **70 件** 超 | |
| 起動時 | `/issue-pipeline` ① の冒頭で上2条件を判定し、該当時のみ提案 | **判定は1行**。該当しなければ黙って ① を続ける |

- **閾値は暫定値**（2026-08-16 の実測＝open 74 件・15日で純増 +21 件を起点に置いた）。
  オーナーの明示指示で上書きしてよく、上書き値は実施記録に残す。
- **`/issue-pipeline` 起動のたびに全件棚卸しはしない**。74 件規模では ① の триage が破綻し、
  #368 が問題にしたトークン浪費をむしろ増やす。

## 2. 手順

### S1 収集（スナップショット）

open Issue の一覧を1回だけ取得する。**取得するフィールドを絞る**（本文は取らない——1件あたりの
情報量規定 §3.2 を超え、74 件分の本文はそれだけでコンテキストを食い潰す）。

- 取得項目：`number` / `title` / `labels` / `created_at` / `updated_at` / `state`
- 親子関係：`type:tracking` の Issue についてのみ子を引く（全件に親を問い合わせない）。
- **取得手段は環境で変わる**（§6）。取得できた手段と取得時刻をスナップショットに記録する。

### S2 クラスタ化（機械的事実だけで束ねる）

**同じ判断をまとめて適用できる単位**へ分割する。クラスタ軸は**機械的に確認できる事実に限る**——
「重要そう」「関連が深い」といった AI の主観で束ねない。

| 軸 | 束ね方 | 一括処分が効く理由 |
|---|---|---|
| **T. 親 tracking 配下** | `type:tracking` の子として API で確認できた群 | 親の優先順位が決まれば子は連動する |
| **B. 依存（blocked-by）** | `blocked-by` 辺で連結した群 | 上流が動かない限り下流は動かせない |
| **A. 同一資産** | 同じファイル/モジュール群を触る（本文の対象 path・`area:*` ラベルで判定） | 1 PR にまとめられる／衝突する |
| **D. 重複候補** | 同じ成果・同じ root cause を扱う候補 | 統合するか片方を閉じるかの1判断 |
| **S. 停滞（stale）** | 齢が閾値超（既定 30 日）で更新もない独立 Issue | 「まだ要るか」を1回で問える |
| **L. 独立葉** | 上のどれにも属さない単独 Issue | 個別判断が要る＝件数を絞って残す |

- **1つの Issue は1クラスタにだけ属させる**（多重計上すると一括処分が二重適用になる）。
  複数軸に該当したら **T → B → D → A → S → L** の優先順で先に立つ軸へ入れる。
- クラスタ根拠は**3行以内**で書く。書けないなら束ね方が主観に寄っている。

### S3 処分表の提示（§3 の形式で）

チャットに処分表を出す。**1件ずつ全文を読ませない。**

### S4 オーナー処分（一括）

オーナーはクラスタ単位で処分語彙（§3.3）を選ぶ。**クラスタ内の個別 Issue だけ別扱いにしたい場合は
例外として明示**してもらい、例外は行単位で記録する。

- 回答が無い／重複した項目は**未処分**として次回へ持ち越す（AI が代わりに決めない）。
- オーナーが「AI の推奨どおりでよい」と明示した場合はそれが判断であり、**判断者はオーナー**として記録する
  （推奨を書いた AI ではない）。

### S5 記録（§5 の縮退ラダー）

処分結果を記録して初めて棚卸しは完了。**記録されていない判断は、次回に同じ判断を繰り返させる。**

## 3. 提示形式＝処分表

### 3.1 構造

```markdown
### クラスタ T1: 親 #368（issue-pipeline 再設計）配下 8 件
根拠: #368 の sub-issue として API で確認（2026-08-16 取得）。
推奨: NOW（理由: 親がトークン効率の是正で、遅らせるほど後続 Issue の処理コストが上がる）
選択肢: NOW / NEXT / LATER / SPLIT / HOLD

| # | type | area | 齢 | 親・依存 | 要旨 | 推奨 |
|---|---|---|---:|---|---|---|
| 369 | docs | harness | 0 | ←368 | 実害定義とエスカレーション条件を SKILL.md へ反映 | NOW |
```

### 3.2 情報量の規定（**1件あたり全角 120 字以内**）

| 列 | 規定 |
|---|---|
| `#` | Issue 番号のみ |
| `type` / `area` | ラベルから `type:` / `area:` 接頭辞を落とした値。複数 area は主たる1つ＋`+n` |
| `齢` | `created_at` からの経過日数（整数） |
| `親・依存` | `←親番号` / `⊣blocked-by番号`。無ければ空欄 |
| `要旨` | **全角 40 字以内**。タイトルの要約であって評価ではない |
| `推奨` | 処分語彙（§3.3）1つ |

- クラスタ見出し＋根拠＋推奨理由は**クラスタあたり3行以内**。
- **本文の引用・再掲は禁止**。判断に本文が要るなら、その Issue はクラスタから外して `HOLD` にし、
  次段（`/issue-pipeline` ①）で個別に読む。

### 3.3 処分語彙（固定・これ以外を使わない）

| 語 | 意味 | 後続処置 |
|---|---|---|
| `NOW` | 現行スプリントで処置する | `/issue-pipeline` ① の対象へ入れる |
| `NEXT` | 次の処置バッチの候補 | `Horizon=Next` 相当を記録 |
| `LATER` | 時期未確定で残す | `Horizon=Later` 相当を記録 |
| `MERGE:#N` | #N へ統合し、この Issue は閉じる | 統合先へ内容を移してから close |
| `SPLIT` | 単一成果になっていないので分割する | 分割の起票は別途 `/gh-create-issue` |
| `CLOSE` | 成果が不要・陳腐化したので閉じる | **理由を必ず記録**して close |
| `HOLD` | この場では判断せず持ち越す | 次回棚卸しへ繰り越し（未処分として明示） |

`MERGE` / `CLOSE` / `LATER` は**オーナーが選んだときだけ**成立する。AI は推奨欄に置けるが、
選ばれていない値を記録・実行してはならない。

## 4. AI の線引き

| AI が用意してよい | AI が用意してはいけない |
|---|---|
| スナップショット（件数・齢・ラベル） | 「対応不要」「現時点不要」という**結論** |
| クラスタ化と、その機械的根拠 | 「繰り越す」という**決定**（推奨としてなら可） |
| 依存グラフ・親子関係の要約 | Project field / 本文への**確定値の書き込み**（オーナー処分前） |
| 重複候補の指摘（「同じ root cause に見える」まで） | **close の実行**、重複と断じての一方的な統合 |
| **理由付き推奨**（PR7 の様式・選択肢と併記） | 推奨を既定値として無回答時に適用すること |

**推奨と結論の違い**：推奨は「選択肢の1つに付いた評価」であり、**選ばれるまで何の状態も変えない**。
結論は状態を変える。AI が書けるのは前者だけで、後者はオーナーの選択があって初めて記録される。

## 5. 記録先（環境で段階的に縮退する）

**上から順に、その環境で可能な最上位を使う。** 縮退したときは「どこまでできたか」を必ず残す。

| 段 | 記録先 | 成立条件 |
|---|---|---|
| ① | **棚卸し取りまとめ Issue**（`type:tracking`）に処分表と判断結果。前例＝#261 | Issue の作成・更新ができる |
| ① | **各 Issue 本文末尾の判断ブロック**（下記）に個別の判断 | 同上 |
| ② | **Project fields**（`Horizon` / `Review date` / `Priority`）を①に併設 | Projects v2 (GraphQL) が使える |
| ③ | ②が不能なら**本文の判断ブロックを正**とし、`project_fields: 未反映` を残して後続セッションで転記 | Issue write のみ可 |
| ④ | Issue write 自体が不能なら `docs/backlog-triage/<YYYY-MM-DD>.md` に一次記録し、write 可能なセッションで転記 | repo への commit のみ可 |

**③が既定になる環境がある**：Claude Code on the web（クラウドセッション）では Projects v2 が
GraphQL 専用であるのに対し GraphQL が遮断されるため、**Project fields は読みも書きもできない**
（2026-08-16 実測＝`gh api graphql` が 403 "only the pinned set of PR-review operations"、
`gh api repos/...` が 403 "GitHub access is not enabled for this session"、`GH_TOKEN` invalid）。
このとき **Issue 本文の判断ブロックがフォールバックの正本**になる。
`/gh-create-issue` 側（Project field 設定を前提にした手順）の手当ては本運用の範囲外で、別途行う。

### 判断ブロックの形式（Issue 本文末尾に追記）

```markdown
<!-- backlog-triage/v1 -->
## 棚卸し判断（2026-08-16）
- 判断者: <オーナーの GitHub ログイン名>
- 判断: LATER
- 理由: <1〜2文。オーナーの言葉を要約する。AI の推奨理由で代替しない>
- 次回レビュー: 2026-09-16
- 取りまとめ: #<棚卸し取りまとめ Issue 番号>
- project_fields: 未反映（クラウドセッションのため。転記後に「反映済み (YYYY-MM-DD)」へ更新）
```

- **`判断者` と `理由` は必須**。どちらかが書けないなら、それは判断が取れていないということで、
  `HOLD` として未処分に戻す。
- 追記であって書き換えではない（PR8 消さない）。過去の棚卸し判断ブロックは残し、下に積む。
- `次回レビュー` は `LATER` / `NEXT` / `HOLD` のとき必須（放置の再検出点）。

## 6. 集計手段（既存の流用可否・2026-08-16 確認）

| 候補 | 流用可否 | 根拠 |
|---|---|---|
| `dsv2 dashboard`（#108） | **不可** | 対象が `doc-system-v2/nodes/04-verification/**` のノードグラフ。データ源も スキーマも GitHub Issue と別物で、共有できるのは「未決を集計する」という発想だけ |
| `blocker_gate`（GitHub REST/GraphQL リーダ） | **部分的に参考** | Issue と blocked-by/parent を読む実装は既にある（read-only）。ただし目的が dependency gate であり、棚卸しの集計 API ではない |
| GitHub MCP `list_issues`（`fields` 指定） | **可**（既定手段） | 本文を落として `number/title/labels/created_at` だけ取れる。§S1 の情報量規定に合う |
| `gh issue list` | 環境依存 | ローカルの認証済みセッションでは可。クラウドセッションでは 403（§5） |

**専用 CLI は今回作らない**（A14 再利用優先）。まず本運用を手順として回し、
実測で「毎回同じ整形に手間がかかる」ことが示せてから新規要否をオーナー判断へ上げる。
選択肢は (a) 作らない＝現状 / (b) `backlog_triage` を新設 / (c) `blocker_gate` のリーダを
共有ライブラリへ切り出して再利用、で、**推奨は (a) → 実績を見て (c)**（新規モジュールを増やさず
既存の GitHub リーダを再利用でき、`asset_parity` の管理対象も増えないため）。

- [ ] スナップショットの取得時刻・取得手段・件数が記録されている。
- [ ] クラスタ軸が**機械的事実だけ**で、各クラスタに3行以内の根拠がある。
- [ ] 1件あたりの情報量が §3.2 の規定内（全角 120 字以内・本文の再掲なし）。
- [ ] 推奨は書いたが、**結論（対応不要・繰り越し）は書いていない**。
- [ ] オーナーの処分が語彙（§3.3）で記録され、**判断者と理由**が残っている。
- [ ] 未処分（`HOLD`・無回答）が**未処分として明示**され、次回へ持ち越されている。
- [ ] 記録先が §5 のどの段まで到達したか、未転記があればその旨が残っている。
