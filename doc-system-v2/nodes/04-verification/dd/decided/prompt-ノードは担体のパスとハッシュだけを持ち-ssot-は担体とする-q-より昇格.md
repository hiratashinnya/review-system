## 論点（昇格元 Q より・要約）

含有ハーネス（著作・検証エージェントと `prompt_coverage_targets` の 14 スキル）の担体から、行動を決めない記述（経緯・フック説明など）を `.ai/rationale/` へ移すとき、
- (A) 何を規範として担体に残すかをどの基準で決め、規範の SSoT を在グラフの PROMPT ノードと担体のどちらに置くか。
- (B) その変更を PROMPT ノードの本文・`version`／`ref_version`・RULE-032（`prompt-coverage`）・RULE-004（`drift`）・自己完結要件（NFR-3／SPEC-46-1）にどう反映するか。

Q の観測事実の要点は次の 3 つである。
- RULE-032 も RULE-004 も担体の内容を見ない。そのため、担体を編集しても機械検査には何も現れない。
- PROMPT ノード本文の規範要約は担体とすでにずれている（下記「既存 FND との関係」の FND 群）。
- DD-22 の版方針は「本文変更」が PROMPT ノードの本文を指すのか担体の本文を指すのかを定めていない。

## 決定（オーナー確定・内容を改変せずに記録する）

1. **規範の SSoT は担体（実体の本文）とする。** PROMPT ノードは実体の**パスとハッシュだけ**を持ち、実体の本文の内容に関することは書かない。本文の内容を書けば SSoT 違反になる。PROMPT ノードは実行時に読まれる対象ではないので、そこに本文を書いてもドリフトするだけである。担体のハッシュが変わったら drift として検知し、本文を読みに行く。ハッシュの不一致は「規範が変わったかを判定できない」という欠陥ではなく、読みに行くべき合図である。
2. **版のルール**（主文脈が示した推奨案をオーナーが承認）:
   - 入出力契約・制約・責務（scope／out of scope）が変わったら **MAJOR**。
   - 行動を変える変更は **MINOR**。
   - 行動を変えない変更（経緯の rationale への移設・誤字・リンク修正）は**ハッシュの再固定だけ**とする（z 相当で、drift を起こさない）。

   DD-22 の版方針でいう「本文」は、PROMPT ノードが本文を持たなくなるので、**担体の変更**を指す。
3. **rationale（経緯）に版は付けない。**
4. **論点 B は B-2 とする。** 担体の本文から rationale へのリンクを置かない。これにより SPEC-46-1 の `\.\./` パターンは変えずに済む。rationale の置き場と命名則は、CLAUDE.md か README に書けば足りる。担体を読む実行時に rationale は要らない（作業に不要である）。
5. **NFR-3／SPEC-46（自己完結要件）は、ずれていて見直す必要があるという FND があれば足りる。** 本 DD では要件を改版しない。
6. **適用範囲は現在の PROMPT ノード 22 件だけとする。** 22 件のノードを実際に書き換える実装作業は Issue #562 側の別作業であり、本 DD は決定の記録にとどめる。

## 本 DD の整理（著作者による分析であり、決定の追加ではない）

### Q の選択肢との対応

決定は、Q が示した選択肢 ①〜④ のどれとも字義どおりには一致しない。いちばん近いのは ③（同期を機械検査にする）だが、SSoT の置き場を ② とは逆に担体へ置き、PROMPT ノードから規範の要約を外している。Q は ③ について 3 つの欠点を挙げていた。決定のもとでは、それぞれ次のように扱われる。
- **サイドカースキーマの変更が要る**: ハッシュをサイドカーに持たせるなら、この変更は残る。決定のコストとして受け入れる（置き場は下記「未決事項」U1）。
- **DD-8／FND-104 が廃止した out-of-graph の版を事実上復活させる**: 当たらない。担体には版を付けない。ハッシュは在グラフの PROMPT ノード側が持つ。rationale にも版を付けない（決定 3）。DD-8／FND-104 が廃止したのは「out-of-graph ファイルが自分で版を持つこと」であり、本決定はそれを復活させない。
- **ハッシュでは規範が変わったかを判定できず、偽陽性が常に出る（PR2）**: 決定 1 はハッシュに「規範が変わったか」の判定を求めていない。機械が判定するのは、ハッシュが一致するかどうかという順序のある属性だけである。変更を MAJOR／MINOR／再固定の 3 区分に振り分けるのは、人が担体を読んで行う運用ルールである。機械判定と運用ルールが分かれているので、PR2 に沿う。経緯の移設でハッシュが変わるのは偽陽性ではない。「読んで、行動を変えないと確かめ、再固定する」という予定どおりの手順の起点である。

② を採らなかったことの意味も記録しておく。② は PROMPT ノードを規範の SSoT として要約を持たせ、担体をその要約に照合する案だった。決定 1 は、この要約自体が実行時に読まれない二重記述であり、ドリフトの発生源になると判断した。

### 判定基準（論点 A 前半）の扱い

決定 2 は、版を「行動を変えるか／変えないか」で分ける。これは、既存の out-of-graph の判定軸、すなわち `.claude/rules/01-principles.md`「PR8「消さない」の適用範囲」の区分 1／区分 2（読み手の行動を決める文か、なぜそう決めたかを説明する文か）と同じ軸である。本 DD は、担体に残すか rationale へ移すかの判定について新しい基準を立てない。在グラフに明文化されるのは、その判定結果を版にどう写すか（決定 2 の 3 区分）である。判定は人（またはレビュー）が担体の差分を読んで行う。機械が担うのは、変更が起きたことの検知（ハッシュの不一致）だけである。

### 未決事項（決定に含まれていないもの。推測で埋めない）

各項の「推奨」は著作者の分析であり、決定ではない。

- **U1 ハッシュをどこに持つか**: サイドカーの新キー（例：`carrier_ref.file`／`carrier_ref.sha256`）に持つか、本文に書くか。`schema/sidecar.schema.json` は未知のキーを禁じている（`additionalProperties: false`）ので、サイドカーに持つならスキーマの変更が要る。推奨はサイドカーである。理由は 2 つある。機械で比較する値を本文の散文に置くと、パースが脆くなる。また、`source.file`（SRC）・`test.file`（TC）という、パスをサイドカーに持つ先例がある。
- **U2 どのファイルのパスを持つか**: 共通本文（`.ai/skills/<name>/SKILL.md`／`.ai/agents/<name>.md`）か、PF wrapper か、その両方か。`doc-system-config-operator` は toml と補助手順 skill の 2 ファイルからなり、`.ai/` に対応物が無い。複数ファイルをどう扱うかも決まっていない。上記 FND `prompt-ノード-22-件の実体が-…` の決定に従う。
- **U3 ハッシュの算法と正規化**: 算法（sha256 等）、改行コードや末尾改行の正規化の有無。
- **U4 drift 検知の実現と要件化**: 担体のハッシュの不一致を、どの検査で検知するか。候補は、`dsv2 drift` の拡張、新しい RULE、CI 上のテストである。決定 1 の「drift として検知」を機械で実現するには、doc_system の新しい機能要件（SPEC）とその実装が要る。要件を追加することになるので、暫定では進めない（`.claude/rules/02-decision-process.md`「判断の仰ぎ方」の要件定義フェーズ）。SPEC の起票先（どの FR の下に置くか）と RULE 番号は、オーナーの判断を要する。
- **U5 22 件を書き換えるときの PROMPT ノードの版**: 書き換えでは、規範の要約を外し、パスとハッシュを持たせる。これは担体の変更ではなく、PROMPT ノード自身の表現の変更なので、決定 2 の 3 区分には直接当てはまらない。推奨は **MINOR** である。理由は、これらのノードに入ってくる辺（上記 FND 群からの forward 辺）が要約の中身を指摘していたからである。MINOR にすれば drift で依存元の再確認を促せる。z にすると、その促しが働かない。いずれにしても、FND `prompt-ノード-22-件の実体が-…` の処置と同じ 1 回の版遷移にまとめる。
- **U6 キャリア属性の変更の版**: DD-22 の「キャリア変更＝MINOR」は残っている。決定 2 の 3 区分の中でこれをどう位置づけるかは決まっていない。たとえば skill→agent の変換は、AskUserQuestion が使えなくなるので、入出力契約の変更として MAJOR に当たる可能性がある。
- **U7 troubleshooting へのリンク**: 決定 4 が対象にしているのは rationale へのリンクである。担体には troubleshooting（`.ai/troubleshooting/`）へのリンクもある（例：`.ai/agents/verification-author.md`）。troubleshooting は失敗から復旧するときに読まれうるので、rationale と同じ扱いにするかどうかは決まっていない。
- **U8 DD-9（`PROMPT←SRC`）との関係**: implementation 段で発火する SRC の `source.file` と、PROMPT ノードが持つ担体のパスが二重になるかどうかは決まっていない。関連する既存ノードは、open FND `src_symbol_eligibility-が担体軸を持たず非-python-担体の-mod-prs-orc-を被覆しない` と open PEND `非-python-担体-prompt-cfg-の内容が当該資産である意味判定の完全機械化` である。

## 覆る場合の影響範囲

本決定を覆して Q の ②（PROMPT ノードを規範の SSoT とし、要約を持たせる）に戻す場合の影響は次のとおり。
