## 選択肢

① **本文のコマンド文字列を実コマンドへ書き換える**。L5 を「E-1（CLI 実行 `python3 doc-system-v2/validate.py`）をトリガに…」、L28 を `START([E-1: python3 doc-system-v2/validate.py])` へ差し替える。
  - 利点: 変更量が最小（2 行）。本文を読んだ読者が即座に実行できる状態になり、実害 1 が直ちに解消する。
  - 欠点: 実行コマンド文字列という**担体の事実**を設計ノード本文に残すため、実装のリファクタ（サブコマンド化・エントリ移動）のたびに本文が陳腐化する。今回の乖離そのものが「本文にコマンドを埋め込んだ結果の陳腐化」であり、同型の再発を構造的に防げない。加えて書き換え先の特定に判断が必要（後述の論点）。

② **コマンド文字列を本文から撤去し、担体の事実は SRC ノードに一元化する**。L5 を「E-1（点検要求・CLI 実行）をトリガに…」、L28 を `START([E-1: 点検要求（CLI 実行）])` へ改め、実行担体（ファイル・qualname）は #160 で著作する SRC ノードの `source.file` / `qualname` だけが持つ。
  - 利点: 担体情報の二重管理が消え、パス・コマンドの陳腐化が構造的に起こらなくなる（担体の正しさは SRC ノードの `_validate_identifier_ref()` が機械検査する）。既存 FND の推奨（担体宣言を設計ノードから外し SRC へ一元化）と同一方針で、コーパス全体の担体表現が揃う。実害 1・2 の双方が解消する。
  - 欠点: 本文だけを読んでも実行コマンドが分からなくなる（SRC ノードまたは README を辿る必要がある）。SRC が未著作の期間は担体情報がグラフ上どこにも無い空白期間が生じる。

③ **実装側に `spec_inspector` エントリポイントを新設して設計に合わせる**。`spec_inspector/__main__.py` を作り、`python -m spec_inspector` が検査パイプラインを起動するようにする。
  - 利点: 既存の設計記述をそのまま正にできる。
  - 欠点: 稼働・テスト済みの `validate.py` / `dsv2` に別名の入口を足すだけの重複であり、実体のない設計名に実装を寄せる後追いになる。既存 FND の推奨（②設計を実装の分割に合わせて再編）と逆行し、コーパス全体で方針が割れる。価値経路を止める代償が大きい（PR6）。

④ **現状維持＋注記のみ**（本文に「`spec_inspector` は未実装の設計上の名称」と注を足す）。
  - 利点: 変更量ゼロに近い。
  - 欠点: 実害 1（実行不能コマンドの提示）も実害 2（SRC との矛盾）も解消しない。#160 で SRC を張った時点で本文と SRC が矛盾したまま確定する。**推奨しない**。

**② を基軸とし、SRC 著作までの空白を埋めるために ① を暫定併用する。**

根拠:

- 本件の直接原因は「実行コマンド（＝担体の事実）を設計ノード本文に文字列で埋め込んだこと」であり、①だけでは同型の陳腐化を再生産する。実際、既存 FND（MOD/DM/PORT/PRS/TERM 32 件の担体宣言）でも同じ構造の乖離が発生しており、コーパス規模で再発している。担体は SRC ノードへ一元化するのが二重管理回避の筋（PR2: 機械判定と運用ルールを混ぜない／機械検査できる事実は機械検査できる場所に置く）。
