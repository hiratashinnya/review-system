## 深刻度の判定根拠（実害で判定する）

**WARNING** と判定した。

- **ERROR にしない理由**: 回復不能な損失も、live な RULE 違反も無い。SPEC-46 を検査する主体が現在いない（別 FND `spec-46-の検査主体-asset-auditor-が外部参照検査を持たず検査が不在`）ので、CI も機械検査も鳴らない。skill 自体は正常に動いている。さらに NFR-3 の**趣旨**（コンテキスト汚染の回避）は、実質的にはおおむね保たれている。wrapper が読ませるのは、その skill 自身の本文（移行前は wrapper の位置に直接書かれていた内容）であり、07-authoring-guide のような追加のガイドではないからである。
- **INFO にしない理由**: 在グラフの要件を字義どおりに実装・適用すると、誤った成果物が出る経路がある。
  - SPEC-46-1 を字義どおりに実装すれば、22 件すべてが違反として報告される。これを字義どおりに「是正」すると wrapper に本文をインライン化することになり、Issue #406 の「共通本文を PF ごとに複製しない」に反する二重正本ができる。
  - 逆に Issue #406 側を正として wrapper を増やし続ければ、在グラフの要件は偽の記述のまま残る。
  - FND-99／FND-104／FND-106 が WARNING とされたのと同じ類型（字義どおりに従うと誤る）である。
- **実害が現れている箇所**: 在グラフの NFR は、システムが満たす性質の宣言である。その宣言が 22/22 で成り立っていないのに、どこにも記録が無い。トレーサビリティの観点では、NFR-3 は「満たされている」とも「免除された」とも読めない状態になっている。

## 選択肢（排他）

**選択肢 1: NFR-3 と SPEC-46-1 を改版し、「スキルファイル」を共通本文と定義する。wrapper から自身の共通本文への 1 本のリンクは、ローダーの機構として除外する。**

- NFR-3 の本文に「スキルの本文（共通本文 `.ai/skills/<name>/SKILL.md`）が著作に必要な情報をすべて内包する。PF wrapper から自身の共通本文への参照は、本文の所在を示すローダー機構であって外部ファイルに当たらない」旨を加える。
- SPEC-46-1 の前提条件・例を、この定義に合わせて直す。
- **覆す根拠**: NFR-3 の字義を覆す根拠は、NFR-3 が書かれた時点には無かった要件、すなわち Issue #406 の多 PF 共通 SoT（Claude／Codex／Copilot が同じ本文を読む）である。NFR-3 の趣旨（追加ガイドを読ませない）はそのまま保たれる。
- **利点**: 両方の意図的設計を保ったまま、字義のずれだけを解消できる。改版は MINOR にとどまる。
- **欠点**: 「スキルファイル」の定義が 2 層（wrapper／共通本文）になり、SPEC-46-1 の判定条件を少し書き足す必要がある。

**選択肢 2: SPEC-46-1 を正とし、wrapper に共通本文を生成物としてインライン化する。**

- `guidance_sync` が `AGENTS.md` を生成しているのと同じ方式で、wrapper に本文を展開し、marker と hash による同期検査を付ける。
- **利点**: 在グラフの要件を変えずに済む。実行時の読み込みが 1 ホップ減る。
- **欠点**: Issue #406 が退けた「PF ごとの複製」を、生成物の形で復活させることになる。4 ツリー × 22 件の生成と同期の機構を新たに作る必要がある。覆すための新しい根拠（Issue #406 の判断を否定するもの）は現時点で無い。

**選択肢 3: 現状を追認し、NFR-3／SPEC-46 に「PF wrapper を除外する」例外を記録するだけにとどめる（定義は変えない）。**

- **利点**: 改版量は最小で済む。
- **欠点**: 共通本文（`.ai/skills/`）側が SPEC-46 の検査対象に入るのかどうかが決まらないまま残る。係属中の Q 素案 `含有ハーネスの担体から経緯を-rationale-へ移す基準と-prompt-ノードとの-ssot` の論点 B-3 が指摘した「スキルファイルがどちらを指すか未決」を解消できない。

## 推奨（決定ではない。決定はオーナーが行う）

**選択肢 1 を推奨する。** 根拠は 3 点である。

1. 両側とも意図的な設計なので、一方を覆す選択肢 2 は立証責任を果たせない。選択肢 1 は NFR-3 の趣旨を保ったまま、字義を多 PF という新しい前提に合わせるだけである。覆す根拠（Issue #406 の多 PF SoT）も明示できる。
2. 選択肢 3 は、検査対象がどこなのかという判定の根幹を未決のまま残す。検査主体を置き直す別 FND（`spec-46-の検査主体-…`）の処置で、何を検査するかが決まらない。
3. SPEC-46-1 の改版は、係属中の Q 素案の論点 B（rationale などの非規範ポインタの除外・推奨 B-1）でも必要になる。本件と Q 素案論点 B を**同じバッチで処置し、SPEC-46-1 の MINOR 改版を 1 回にまとめる**ことを推奨する。同じ PR の中で版を二度上げないためである（`.ai/guidance/common.md`「正本・実装規約」）。

**処置の順序**: 本 FND（何を検査するか）→ 別 FND `spec-46-の検査主体-…`（誰がいつ検査するか）の順に決めることを推奨する。検査主体を先に決めて機械検査を入れると、現状のままでは 22 件が即時に違反となり、偽陽性だけを出し続けることになる。

「対応不要」との判断はしていない。採否と実施時期はオーナーが決める（`scheduled: sprint-1`＝現行スプリント。繰り越しはオーナーの明示指示がある場合に限る）。

## 統合・分割の理由

- 呼び出し元の観測 3 は「wrapper のリンクが NFR-3／SPEC-46-1 と衝突」と「SPEC-46 の検査主体が不在」の 2 つを含んでいた。本 FND は前者だけを扱い、後者は別 FND `spec-46-の検査主体-asset-auditor-が外部参照検査を持たず検査が不在` に分けた。
- 分けた理由は、指摘対象の「もの」も処置も違うからである（PR1）。前者は要件の定義（何を満たすべきか）と実装（wrapper）の食い違いで、処置は NFR-3／SPEC-46-1 の文言である。後者は検証の機構（誰が観測するか・PR4）の欠如で、処置は SPEC-46-1／46-2 の入力/トリガと、検査を実装する資産である。既存 open FND の `reconciliation-の-tmp-掃除ガードが-…`（実体）と `tmp-掃除ガード追従テストの検査対象探索が-…`（機序）を分けた先例と同じ扱いにした。
- **Q 素案の論点 B との関係（重複ではない）**: Q 素案の論点 B は「読まなくてよいことを明示した非規範ポインタ（rationale へのリンク）」を扱う。本件は「必ず読め」と**読み込みを要求する**リンクである。Q 素案は、自身の推奨の中で本件を「性質が違うので別 FND に切り出す」としている（PR1）。本 FND がその切り出し先に当たる。処置の対象ノード（SPEC-46-1）は重なるので、処置は同じバッチにまとめることを推奨する（上記）。
