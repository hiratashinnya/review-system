1. **逸脱は latent ではなく現に発生した** — 本 PR（#326 の対象ブランチ）の確定書込時、主文脈は `reconciliation-validator` が返した `VALIDATION_OK` ブロックを**そのまま渡さず、dispatch prompt に散文で要約して渡した**。`reconciliation` はそれを信頼して書込を実施し、自らのハンドオフ（`tmp/_handoff/reconciliation--fnd-sprint-1-batch-ab.yaml`）に「⚠️ 本エージェントは validation_ok ブロックを reconciliation-validator から直接受け取っておらず、主文脈の Goal 指示内の記述をそのまま信頼して書込を実施した。通常運用（validator→reconciliation の2段呼び出し）からの逸脱であり…今後同様の省略が常態化しないよう申し送る」と明記している。**writer 自身が逸脱を検知して申告できたのは偶然ではなく、writer には検証手段が無いのに「渡されたものが validator 由来かどうか」を判別する必要があるという構造そのものの帰結**である。
2. **宣言している保証と実際に成立している性質が食い違う（誤った保証）** — CLAUDE.md／DD-22 は「validator に Write/Edit を与えないことで**構造的に本ファイルへ書けない fail-close** を保証する」と述べる。しかしこの保証が担保しているのは「validator 自身が書かないこと」だけであり、**「writer が書く根拠が validator の判定であること」は何も担保していない**。判定は自然言語のブロックとして主文脈を経由し、writer 側にその真正性・完全性を確かめる手段が無い。要約・言い換え・（極端には）捏造を writer は区別できず、**2 段分離の fail-close が主文脈経由で迂回できる**。コーパス保全の要が、機構ではなく主文脈の規律に依存している。
3. **混入時の発見契機が無く、回復に人手照合を要する** — 誤った（あるいは実在しない）判定に基づいて書き込まれたノードは、コーパス上は正常に見える。事後に気づく契機は「別途 `validate.py` を回して ERROR が増えていることに気づく」しかなく、warning 止まりの不整合・slug 衝突・ref_version ドリフトは baseline のノイズに紛れる。今回は validator を実際に走らせており結果も正しかった（`pr-reviewer` が独立に機械検査で裏付け済み）ため**コーパスの内容は壊れていない**が、それは運用が正しかったからであって機構が守ったからではない。

**内容**: 著作パイプラインは `*-author`（tmp 著作）→ `reconciliation-validator`（read-only 検証・`VALIDATION_OK`/`ROLLBACK`）→ `reconciliation`（`self_fix` 適用＋本ファイル書込）の 2 段で確定する（DD-22）。このうち**検証段から書込段への判定の受け渡しが、型のない自然言語ブロックを主文脈が中継する形**になっている。

- `.claude/agents/reconciliation.md` の入力仕様は `validation_ok: <reconciliation-validator が返した VALIDATION_OK ブロック（parent_ids・validated_by_parent・self_fix を含む）>` であり、**呼び出し元（主文脈）がプロンプト変数として渡す文字列**である。
- 同ファイルは「`validation_ok` が渡されていない場合は**エラーとして主文脈に返す**（検証前の書き込みは禁止）」「`validation_ok` に ROLLBACK が含まれていないことを確認する」と定めるが、**いずれも受け取った文字列の内容を見るだけ**であり、その文字列が validator の出力そのものであることを確かめる手段が無い。

4. **PROMPT `reconciliation 調停支援プロンプト（検証＋本ファイル転記）`** — `validation_ok` を呼び出し元から受け取る契約を定めている当のノード。受領物の検査を課すならここが変わる。

**選択肢**

1. **validator の判定をファイル（`tmp/_handoff/reconciliation-validator--<batch_id>.yaml`）に落とし、writer はそのパスを読む** — 受け渡しが成果物になり、主文脈は「パスを渡す」だけになるので要約・言い換えの余地が消える。CLAUDE.md のハンドオフ規約（write 権限のあるエージェントはファイルに書き、パスと 1 行要約を返す）とも整合する。**ただし validator に Write を与えることになり、DD-22 の「構造的に本ファイルへ書けない」保証が機構から規律へ格下げになる**（`agent-command-gate.sh` は `matcher: "Bash"` であって Write を見ないため、書込先を tmp に限る強制はフック側の手当てが要る）。
2. **writer が受領ブロックの形式を検査し、不備なら拒否する** — `VALIDATION_OK` に必須キー（`layer` / `sprint` / `validated_by_parent` / `self_fix`）が揃い、`validated_by_parent` の slug 集合が tmp の実在ファイルと一致することを writer 側で確認する。散文要約は形式検査で落ちるため、今回の逸脱は確実に止まる。実装は writer プロンプトの数行で済み、権限構成は一切変えない。**捏造（形式を整えた偽の判定）は止められない**。
3. **主文脈を介さず validator → writer で受け渡す** — 受け渡し経路から中継者を除く。最も直接的だが、現在のエージェント機構では subagent が別の subagent を起動する経路が無く、**この案は機構の変更（オーケストレータの再設計）を要する**。短期には採れない。
4. **writer が決定論ツールを自ら再実行してゲートにする** — 書込直前に `python3 doc-system-v2/validate.py <tmp>`・`python3 -m dsv2 check-slug --from-dir <tmp> --update <既存 slug>`・`python3 -m dsv2 drift` を writer 自身が回し、**その実測結果が合格でなければ書かない**。判定の出所に依存せず「壊れたものは書けない」を機構で担保できる（捏造にも耐える）。writer は既にこれらのコマンドを実行できる（Bash 許可用途に含まれる）。**懸念は「検証ロジックを二重実装しない」という現行の規律との緊張**だが、writer が回すのは**決定論ツールそのもの**であって LLM による判定の再実装ではないため、ドリフトの原因にはならない。
5. **現状維持＋運用注意** — 「判定はブロックのまま貼り付ける」を規約に明記するに留める。コストはゼロだが、今回の逸脱は**その規約が既にある状態で**起きている（`.claude/agents/reconciliation.md` は「validation_ok が渡されていない場合はエラーとして返す」と定めていた）。PR2 の観点でも、機械判定にできるものを運用ルールに留める方向になる。

**推奨**: **選択肢 4 を基軸に、選択肢 2 を併用する。選択肢 1 はフックで書込先を限定できる場合に限り上乗せする。** 根拠は 4 点。

- (a) **守るべきものはコーパスの健全性であって判定文字列の真正性ではない**。選択肢 4 は「誰が何と言ったか」に依存せず「壊れたものは書けない」を直接担保するため、要約・省略・捏造のいずれにも耐える。決定論ツールの実行結果は LLM の判断を経ないので、再実行がドリフトを生まない。
- (b) 選択肢 2 は単独では捏造に無力だが、**`self_fix` の脱落**（今回の逸脱で最も現実的な損害）を確実に止める。選択肢 4 は「書いてよいか」を見るが `self_fix` の適用漏れは見ないため、両者は補完関係にある。
- (c) 選択肢 1 は経路としては最も筋が良いが、**DD-22 の保証の性質を変える**のが代償である。validator に Write を与えるなら、書込先を `tmp/_handoff/` に限定する強制（PreToolUse フックの Write 対応）を**先に**用意すべきで、それ抜きに採ると本指摘が指す「機構が規律に置き換わる」問題を validator 側で再生産する。
- (d) いずれの案を採っても、**分析層の担体不在（P-7-2-1 の出力に対応する D ノードが無い）は別途是正が必要**である。選択肢 1 を採れば「検証結果ファイル」が D として自然に立つ。選択肢 2・4 を採る場合も「検証判定」という中間成果を D として置き、P-7-2-1 → D → P-7-2-2 の経路をモデル上つなぐ必要がある（PR6）。

**採否の決定はオーナー判断を仰ぐ**（実施スプリントは `scheduled: sprint-1`＝現行スプリントのまま。繰り越しはオーナーの明示指示がある場合のみ）。**「対応不要」とは判断していない。**
