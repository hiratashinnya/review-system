**タイトルの数詞について（改題しないことの判断・v0.2.1）**

本ノードのタイトルは起票時点の列挙数を含む「dsv2 実装 **6** モジュール…」のままであり、v0.2.1 で対象が 7 本になったこととタイトルの数詞は一致していない。**改題（title 変更）を行わないことを著作時の判断として選択した**。理由は 3 点。

1. **id = `slugify(title)` であるため、改題は slug 変更（＝ノード同一性の変更）を伴う**。`edges[].to` は `python3 -m dsv2 rename` で機械的に張り替えられるが、**散文中の参照は張り替えられない**。本ノードを散文で参照している箇所は現時点で少なくとも 5 つある（Q ノード `深刻度の判定基準是正を既存 FND 全件へ遡及適用するか` の §5 表・選択肢②本文・**訂正履歴（v0.1.1/v0.1.2）**・末尾の「指摘時 ref_version」行、および `00-dashboard.md` の注記と一覧行）。
2. **そのうち Q ノードの「指摘時 ref_version」行と訂正履歴は DD-3／PR8 により凍結された過去の記録**であり、事後に書き換えると「その時点で何をどの版で参照したか」という証跡の性質が損なわれる。改題は、書き換えれば証跡を壊し、書き換えなければ宙に浮いた参照を残すという二者択一を強いる。
3. 同時期に著作済み・未書込の FND 2 件（段落粒度・段落選定条件）も本ノードを旧タイトルで参照しており、それらは本作業の変更対象外（オーナー指示）である。

代わりに、**数詞は起票時点の列挙数であって現在の対象数ではないこと**を本節と改訂履歴に明記し、対象の正本を上表とする。数詞を含まないタイトルへの改題（例：「dsv2 実装モジュール群に対応する設計ノード（MOD/P）が存在しない」）は将来の再拡張に強く、**オーナーが改題を選ぶ場合の手順は本 FND のハンドオフに記載した**（`dsv2 rename` の実行と、散文参照の扱いをどうするかの決定が必要）。**本判断は「対応不要」の結論ではなく、著作時の選択であり、オーナーの上書きを妨げない。**

**forward 辺の張り先と選定理由**

本指摘は「対応する設計ノードが存在しない」こと自体が内容であるため、指摘対象そのもの（欠落しているノード）に辺を張ることが原理的にできない。そこで、**欠落を受け止めるべき最も近縁の既存ノード**を各層 1 件ずつ選び、便宜上そこへ forward 辺を張る（本来の張り先は当該 7 本に対応する未著作の MOD/P である旨をここに明記する）。

1. **MOD `__main__`** — 設計層側の受け皿。責務が「合成ルート ＋ CLI エントリポイント（DI 結線・コマンドライン引数解析）」であり、**モジュール構成の集合を定義する唯一の MOD** である。モジュールが 7 本増減すれば必ずこのノードの結線記述が変わるため、「MOD 一覧に 7 本が無い」という指摘の自然な受け皿になる。個々の MOD（`reporter` 等）に張ると、その 1 モジュールの責務不足という別の指摘に読み替えられてしまうため採らなかった。`cleantmp` も `dsv2 clean-tmp` サブコマンドとして CLI に結線されているため、この受け皿の射程に収まる。
2. **P `ノード著作・反映プロセス`（P-7）** — 分析層側の受け皿。`rename` / `reverse` / `dashboard` / `yamledit` / `gitutil` / `cleantmp` はいずれも「ノードの著作から本ファイル反映まで」の活動（reconciliation が実行する機械処置）に属するが、P-7 の子は `著作・tmp-出力`（P-7-1）と `調停・本ファイル反映`（P-7-2）の 2 つのみで、改題・辺逆転・dashboard 集計・**tmp 掃除**に相当する子プロセスを持たない。すなわち **P-7 の分解漏れ**として指摘が成立する唯一の既存ノードである。`cleantmp` は P-7-2 の Step 3-3 として実行されるため、P-7 の射程に収まる（P-7-2 へ辺を増やさない理由は、既存の 2 辺で受け皿として足りており、v0.2.1 を辺の変更を伴わない z バンプに保つため）。
3. `viewer` については上記のいずれにも自然な親が無い（P の L1 にビューア生成系の親プロセスが存在しない）。3 本目の指摘辺は張らず、本記述をもって欠落の所在の記録とする（v0.2.2 で追加した DD への辺は指摘辺ではなく決定スパインの backref である）。

**選択肢**
1. **7 本それぞれに対応する MOD を新設し、必要な P も併せて起票する**（`viewer` は L1 プロセスの新設、`rename`/`reverse`/`dashboard`/`cleantmp` は P-7 配下の子プロセス、`gitutil`/`yamledit` は基盤ユーティリティ MOD として位置づけ）。設計層が実装の現況に追随し、`#160` の SRC materialize が 7 本について直ちに可能になる。一方、C1 側の 26 件（`spec_inspector/*` 前提）が未処置のまま残ると、MOD 一覧に「実装のある新設 7 件」と「実装のない既存 18 件」が併存し、モジュール分割の正本が二重化する。
2. **既存 MOD の責務記述を改訂して 7 本を包含させる**（例: `gitutil`/`yamledit` を `adapters-fs` へ、`rename`/`reverse`/`dashboard`/`cleantmp` を `reconciler` へ、`viewer` を `reporter` へ）。新設ノードが増えずグラフは小さく保たれるが、`adapters-fs` は `FileSystemPort` 実装、`reporter` は違反レポート整形という別責務を既に負っており、包含は単一責務の希薄化（PR1 違反）を招く。また `src_symbol_eligibility: mod: [module]` の下で 1 MOD に複数の Python モジュールを紐づける形になり、SRC の担体対応が 1:1 でなくなる。
3. **C1 と同じ処置単位で、MOD 一覧そのものを dsv2 の実モジュール構成へ再定義する**（`spec_inspector/*` 前提の 18 MOD を `dsv2/*` ＋ `doc-system-v2/validate.py` の実構成へ再マップし、その再マップの中で本 7 本を位置づける）。設計・実装の乖離を C1/C2 まとめて解消でき、正本の二重化も起きない。反面、影響範囲が MOD 18 件 ＋ DM 6 件 ＋ PORT 1 件 ＋ PRS 1 件に及び、`#160` の作業量が最大になる。
4. **設計層を正とし、実装側を設計に合わせる**（7 本を既存 MOD の分割に沿って再編する）。設計の一貫性は保たれるが、7 本はいずれも稼働中の機械処置（`dsv2 reverse` は CLAUDE.md 規約上の必須ツール、`dsv2 clean-tmp` は Issue #276／#307 で TOCTOU 再検査・保護名ガードまで作り込まれた掃除ツール）であり、実装の作り直しコストと退行リスクが大きい。

**推奨**: **選択肢 3 を基軸に、その内側で選択肢 1 を実施する**。根拠は 3 点。(a) 本指摘と C1 は「`spec_inspector/*` を前提にした設計層」対「`dsv2/*` として育った実装」という**単一の乖離の表裏**であり、C2 だけを先に処置すると MOD 一覧が二重化して再乖離を招く。(b) 選択肢 2 の包含は PR1（もので分ける）と `src_symbol_eligibility` の 1:1 担体対応の両方に反する。(c) 選択肢 4 は稼働中ツールの作り直しであり、オーナー方針（2026-07-26・乖離は `#160` のスコープ内で設計実装の整合を取る）が「設計変更」も選択肢に含めている以上、実装追随より設計側の再定義が先に検討されるべきである。ただし `reverse` は既に DD 3 件の決定を持つため、再マップ時にその DD からの派生として MOD/P を導出できるか（決定→設計→実装の連鎖が復元できるか）を先に確認することを併せて推奨する。**`cleantmp` の追加は推奨を変えない**——追加された 1 本も同じ乖離（`dsv2/*` として育った実装）に属し、選択肢の構成にも各選択肢のトレードオフにも影響しないためである。むしろ「対象が起票後に増える」という事実自体が、個別ノードを都度追加する選択肢 1 単独ではなく、MOD 一覧を実構成へ再定義する選択肢 3 を支持する材料になる。**いずれの選択肢を採るかの決定はオーナー判断を仰ぐ**（実施スプリントは `scheduled: sprint-1`＝現行スプリントのまま。繰り越しはオーナーの明示指示がある場合のみ）。

**接続規則変更の伴否**: 本指摘は `doc-system-v2/config.yml` の `must_link_to` / `must_be_linked_from` の追加・変更・削除を含まない（欠落しているのはノードであって規則ではない）。したがって接続マトリクス・ドキュメント一覧・各 author エージェント/スキルへの伝播同期は不要と判断した。本改訂（v0.2.1／v0.2.2）でもこの判断に変更はない（v0.2.1 は対象実装の列挙が 1 本増えただけ、v0.2.2 は DD-016 の既存運用に従った backref 付与のみで、いずれも規則には触れていない）。
