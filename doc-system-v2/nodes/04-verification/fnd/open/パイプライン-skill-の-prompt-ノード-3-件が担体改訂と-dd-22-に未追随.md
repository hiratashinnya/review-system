## 意図的設計かの確認（`.claude/rules/01-principles.md`「意図的設計の尊重」）

PROMPT ノードを旧手順のまま据え置いたのは、意図的な設計ではないと判断した。根拠は次の 2 点である。

1. DD-22 は ①-C の fan-out 実装を「本 DD の後続作業（skill/agent 実体＝`.claude/` の再編）」とし、その在グラフ反映についても「必要なら ORC への追記（在グラフ反映は別途 design-author で判断）」と書いている。在グラフに反映**しない**と決めたのではなく、反映の判断を先送りしている。しかも、この記述が名指ししているのは ORC であって、PROMPT ノードの手順を旧来のまま保つことを定めた記述は DD-22 のどこにも無い。先送りされた判断を記録した DD・Q・FND も、コーパスに無い。
2. DD23 の「影響範囲」にある「in-graph 義務辺は持たない（`.claude/` 資産運用への反映）」は、DD23（review_system 側の `docs/design/decisions.md`）が在グラフのノードに義務辺を張らない、という意味である。PROMPT ノードの内容を旧手順のまま保て、という決定ではない。DD23 の目的は「並列著作の実体を作る」ことにあり、旧手順を正とする根拠は含まれていない。

したがって、これは既存決定を覆す指摘ではない。先送りされた在グラフ反映が実施されていない、という未追随の指摘である。

## 深刻度の判定根拠（実害で判定する）

**WARNING** と判定した。

- **ERROR にしない理由**: 回復不能な損失は無い。パイプラインは主文脈が担体（skill）を読んで実行するので、PROMPT ノードの旧手順が実行時に読まれることは無い。`prompt-coverage`・`drift` などの live な RULE 違反も無い。
- **INFO にしない理由**: 次の 3 点から、被覆や均一性のギャップ（INFO の類型）ではなく、字義どおりに従うと誤る類型（WARNING）に当たる。
  - **在グラフの設計を字義どおり実装すると、壊れた手順が出る**。PROMPT ノードを設計の正本として（SPEC-61／DD-22 の構図）担体を作り直すと、廃止済みの `/io-event-ledger` を呼ぶ手順ができあがる。また、Issue #121 で「欠落」と判定されて是正された設計層ノードの著作段が消える。
  - **在グラフの内部に矛盾がある**（DD-22 と PROMPT ノード 2 件）。
  - **「skill 化の理由」を誤って記録している**。将来 DD-22 が想定する「skill→agent 変換」（`carrier` の変更）を検討するとき、判断材料が誤る。「呼べないから skill」が正しいなら agent 化の余地は無いことになるが、実際の制約は対話性であり、非対話部分の agent 化は DD-22 がすでに採用している。
- 既存 open FND `reconciliation-の-tmp-掃除ガードが-in-graph-prompt-と-copilot・codex-ミラーに未同期` は、同じ「PROMPT ノードと担体の規範の未同期」を ERROR としている。ただし ERROR の主たる根拠は「削除主体の読む規範にガードが無く、回復不能な損失が起きうる」ことである。本件にはその要素が無いので、WARNING に留める。

## 選択肢（排他）

**選択肢 1: 3 件の本文を担体に合わせて書き換える（内容の是正のみ）。**

- `spec-pipeline`: 手順②を「I/O 台帳＋イベントリスト→analysis-author で ACTOR/I/O/E を著作（2段確定）」に、手順を 7 段（fan-out 段を追加）に直す。skill 化の理由を「対話段は skill・非対話 fan-out は `authoring-fanout`（DD-22 ①-C）」に直す。
- `asset-pipeline`: skill 化の理由を、同じく DD-22 ①-C に沿って直す。
- `impl-design-pipeline`: 段 2.5 と、出力形式の「設計層ノード」を追加する。
- **利点**: 在グラフの内部矛盾と、設計と実装の乖離が、すぐに消える。
- **欠点**: 同期の機構は増えないので、担体を次に改訂したときにまたずれる（既存の `reconciliation` FND と同じ再発の型）。

**選択肢 2: 選択肢 1 に加え、Issue #562 の照合バッチ（Q 素案 論点 A ②）の中で処置する。**

- Q 素案 `含有ハーネスの担体から経緯を-rationale-へ移す基準と-prompt-ノードとの-ssot` の ② は、「担体の各記述を PROMPT ノードへ辿れるかで振り分け、辿れない行動規定は PROMPT ノードへ先に反映する（(b)）」手順である。本件の 3 件は、この (b) にそのまま当たる。
- **利点**: 22 件全体の照合と同じ手順で処理でき、ほかの PROMPT ノードに同種のずれがあれば一緒に洗い出せる。
- **欠点**: Q の決定を待つので、是正の着手が遅れる。

**選択肢 3: 手順の列挙を PROMPT ノードから外し、「手順は担体を正とする」と書き換える。**

- **利点**: 二重記述そのものが無くなり、今後ずれない。
- **欠点**: PROMPT ノードが「何をする prompt か」を在グラフで表す、という SPEC-61 の目的が弱まる。パイプライン skill にとって段の構成は機能そのものなので、外すと機能軸の表現が空になる。PR1・PR8（論理設計を完全に作る）の観点からも後退する。

**選択肢 2 を推奨する。** Q 素案が ① や ④ に決まった場合（照合バッチを行わない場合）は、選択肢 1 を単独で実施することを推奨する。根拠は 3 点である。

2. どちらの場合も、選択肢 1 の内容の是正は必ず行う。廃止済み skill を指す手順と、DD-22 との内部矛盾は、機構の議論とは独立して誤りだからである。
3. 選択肢 3 は、機能軸を在グラフで表すという SPEC-61 の目的を損なう。二重記述の問題は、Q 素案の論点 A で「PROMPT ノードは要約粒度とし、全文は複製しない」と整理されており、手順の段の構成（要約）まで外す理由は無い。

「対応不要」との判断はしていない。採否と実施時期はオーナーが決める（`scheduled: sprint-1`＝現行スプリント。繰り越しはオーナーの明示指示がある場合に限る）。

## 統合・分割の理由

- **3 件を 1 FND にまとめた理由**: 3 件は、指摘対象の「もの」（パイプライン skill の PROMPT ノードの規範の要約）も、発生源（DD-22 ①-C の実装として 2026-06〜07 に行われた担体改訂が在グラフへ未反映）も同じである。処置の手順も同じ（本文を担体と DD-22 に合わせて MINOR 改版）なので、PR1 に照らして 1 件として扱うのが妥当と判断した。呼び出し元の観測は `spec-pipeline` の `/io-event-ledger` 1 件だったが、同じ発生源をたどると `impl-design-pipeline`（Issue #121 補遺で是正された著作段の欠落）と `asset-pipeline`（DD-22 と矛盾する skill 化の理由）も同じ状態だったので、含めた。
- **`test-strategy` PROMPT（v0.1.2）を対象外にした理由**: 担体には Issue #121 補遺で追加された TD 著作 fan-out 節があるが、PROMPT ノードの出力形式はすでに「TD（`doc-system-v2/nodes/04-verification/td/…`）」を成果物として挙げている。欠けているのは委譲の経路（`authoring-fanout`／`verification-author`）という手段の記述だけで、機能（何を出すか）は食い違っていない。これを指摘に含めるかどうかは PROMPT ノードの要約粒度の問題であり、Q 素案の論点 A で決まる。そのため、本 FND の対象には含めなかった。**「対応不要」と判断したのではなく**、判定を Q 素案に委ねたという意味である。
- **FND `prompt-ノード-22-件の実体が-pf-wrapper-を指し共通本文を指さない` と分けた理由**: あちらは「どのファイルを実体と呼ぶか」（指し先）、本件は「PROMPT ノードの規範内容」（中身）の指摘である。処置の版区分も違う（あちらは z か MINOR か未決、本件は MINOR）。PR1 に従い分けた。

**接続規則変更の伴否**: 本指摘は `doc-system-v2/config.yml` の `must_link_to`／`must_be_linked_from`／`fnd_lifecycle` を追加・変更・削除しない（対象は PROMPT ノード本文）。したがって、接続マトリクス・ドキュメント一覧・author 資産への伝播チェックは不要と判断した。
