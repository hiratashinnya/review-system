実害の判定根拠は次のとおり。

1. **削除を実行する主体が読む規範そのものにガードが無い** — `.github/agents/reconciliation.agent.md`（Copilot 版）と `.codex/agents/reconciliation.toml`（Codex CLI 版）は、どちらも Step 3-3 を「**全ファイルの書き込みが完了してから `tmp/<sprint>/<parent-id>/` を削除する。**」の 1 文で済ませており、`dsv2 clean-tmp` の使用義務・`rm -rf` の禁止・保護名（`_handoff`・`_karte`）の存在のいずれにも触れていない。これは `.claude/agents/reconciliation.md` が K-11 → R-06 → OOS-1 → N-01 → N-02 の 5 ラウンドで積み上げた是正内容が、**同じエージェントの他プラットフォーム版に一度も伝わっていない**ことを意味する。前 FND 2 件（段落粒度・段落選定条件）を WARNING に留めた根拠は「取りこぼした記述が削除主体の読む規範ではない」ことだったが、**本件は規範そのもの**であり、その物差しで ERROR に当たる。
2. **失われるものが回復不能** — Copilot 版の frontmatter `description` は "…, then clears tmp." と述べており、「tmp を掃除する」の対象範囲が `tmp/<sprint>/<parent-id>/` に限られることも、`tmp/_handoff/`・`tmp/_karte/` が掃除対象外であることも読み取れない。実際に削除されれば、未回収のハンドオフ（後続工程の入力）と是正ループの診断カルテ（Issue #307・ループ状態そのもの）が失われる。どちらも `.gitignore` 済みで git から復元できない。
3. **in-graph の設計ノードが実体と現に矛盾している（トレーサビリティの損害）** — PROMPT ノード `reconciliation 調停支援プロンプト（検証＋本ファイル転記）`（v0.1.2・本文に「SPEC-39 の実体＝`.claude/agents/reconciliation.md`」と明記）は、**「注意事項」の Bash 許可用途を `dsv2 reverse` / `git mv` / `dsv2 deps/dependents` の 3 つに限定**しており、実体側 L94 が明示的に許可している **`python3 -m dsv2 clean-tmp [--apply]` を欠く**。すなわち in-graph の設計を字義どおり実装すると、掃除は「許可されていない手段」でしか行えない。さらに「出力形式」は掃除対象を **`tmp/<sprint>/` と記述**しており、実体（`tmp/<sprint>/<parent-id>/`）と粒度が食い違う。`dsv2 clean-tmp` は `tmp/<sprint>` を**階層違反として拒否する**（`tests/unit/test_dsv2_cleantmp.py::test_rejects_wrong_depth`）ため、設計ノードの記述どおりの操作はツール上そもそも実行できない。設計と実装の乖離が現に存在する状態であり、これは将来リスクではなく現時点の損害である。

**内容**: `tmp` 掃除ガード（`dsv2 clean-tmp` の使用義務・保護名 `_handoff`／`_karte`・`rm -rf` 禁止）は、`.claude/agents/reconciliation.md` と `CLAUDE.md`・`dsv2/README.md`・`dsv2/*.py` にのみ反映され、**同じ `reconciliation` を表す他の 3 つの正規表現体（in-graph の PROMPT ノード・Copilot ミラー・Codex ミラー）には一度も同期されていない**。単一の是正が 1 ツリーだけに適用され、残りが取り残されたドリフトである。

**なぜ機械的に検出されなかったか**

1. `tests/unit/test_dsv2_cleantmp.py::TestGuardDocsMatchProtectedNames` の検査対象は `_candidate_guard_docs()` の固定候補（`.claude/agents/reconciliation.md` / `CLAUDE.md` / `dsv2/README.md` / `dsv2/*.py`）に限られ、**4 ツリーのミラーと in-graph ノードは初めから候補にない**。加えて `_discover_guard_docs()` は `clean-tmp`／`PROTECTED_DIRNAMES` の語を含むファイルだけを採るため、ガード記述を持たない上記 3 件は仮に候補に加えても選定から外れる。この**検査対象探索の欠陥そのもの**は、別 FND `tmp 掃除ガード追従テストの検査対象探索がガード記述の消滅とミラー文書を見落とす` として同時に起票した（本 FND は「記述が未同期である」実体、別 FND は「見つけられない」機序＝処置対象ファイルも処置方法も異なるため分離）。

**forward 辺の張り先と選定理由**

**PROMPT ノード `reconciliation 調停支援プロンプト（検証＋本ファイル転記）` の 1 辺**とする。これは便宜的な受け皿ではなく、**指摘対象そのもの**である（同ノード本文が上表のとおりガードを持たず、Bash 許可用途と掃除対象粒度で実体と矛盾している）。

`.github` / `.codex` の 2 ミラーには対応する in-graph ノードが存在しない。PROMPT ノード本文が「実体＝`.claude/agents/reconciliation.md`」と 1 ツリーのみを宣言しており、**ミラー 2 本が in-graph に表現されていないこと自体が本ドリフトを許した構造**である。この事実は本文に記録し、辺は張らない（張り先が存在しない）。

同時起票の別 FND（検査対象探索）とは張り先を分けた。あちらは P `調停・本ファイル反映`（掃除という活動の受け皿）、本件は PROMPT ノード（記述の所在）である。1 つのノードに対する 2 つの異なる指摘を同じ辺で表現しないための分離。

**選択肢**

1. **3 件へ手作業で同期する（内容の是正のみ）** — PROMPT ノード本文に `clean-tmp` の使用義務・保護名・掃除対象粒度（`tmp/<sprint>/<parent-id>/`）を追記（z バンプ）、`.github`/`.codex` の Step 3-3 と注意事項を `.claude` 版に合わせる。即座に穴が塞がり、コストは最小。反面、**同期の機構は増えないため次の是正でまた取り残される**（本件がまさにその再発である）。
