## 実害が既に現れていること

別 FND `pf-wrapper-の共通本文読込要求が-nfr-3-と-spec-46-1-の字義に全件抵触` のとおり、Issue #406 の `.ai/` 移行によって、`.claude/skills/*/SKILL.md` の 22 件すべてが SPEC-46-1 の字義に抵触する状態になった。しかし移行時には、この衝突がどこにも打ち上げられていない（コーパスに記録 0 件）。検査主体が機能していれば、少なくとも最初の wrapper 化の時点で WARNING が出て、PR7 に従った起票の契機になったはずである。**検査の不在は将来のリスクではなく、在グラフ要件の大規模な未追随をすでに見逃させた**。

## 意図的設計かの確認（`.claude/rules/01-principles.md`「意図的設計の尊重」）

- **検査主体を asset-auditor と定めたこと自体は意図的な設計である**。FND-90（`検証手順の観測-実行主体が二者択一で一意でない-再現性・観測可能性`・resolved 2026-06-15）が、「reconciliation または asset-auditor」の二者択一を一意化するために選んだ（PR4）。
- **しかし、その決定が asset-auditor の契約に実装された形跡は無い**。FND-90 の処置記録にあるのは SPEC の文言の変更だけで、asset-auditor 側の変更は記録されていない。asset-auditor の現行の責務境界（上記）とも両立していない。
- したがって本 FND は FND-90 の選択を無根拠に覆すものではない。まず「決定が実装されていない」ことを指摘する。そのうえで、検査主体を置き直す選択肢（下記選択肢 2）を示し、覆すための新しい根拠を明記する。

## 深刻度の判定根拠（実害で判定する）

**WARNING** と判定した。

- **ERROR にしない理由**: 回復不能な損失は無い。検査の不在で見逃されたのは要件と実装の食い違い（別 FND）であり、データや成果物は失われていない。live な RULE 違反も無い。
- **INFO にしない理由**:
  - 被覆のギャップにとどまらず、上記のとおり**見逃しがすでに実際に起きている**。
  - 在グラフの SPEC を字義どおりに運用しようとすると、SPEC が指定した主体（asset-auditor）を呼んでも検査は行われない。「SPEC-46 を検査した」という報告が、実行しても何も観測しない形で成立してしまう。

## 選択肢（排他）

**選択肢 1: FND-90 の決定どおり、asset-auditor の契約に SPEC-46 の検査を追加する。**

- **利点**: 在グラフの SPEC を変更せずに済む。FND-90 の決定がそのまま実装される。
- **欠点**:
  - asset-auditor の起動は新しい資産を作る前に限られるので、既存スキルの退行（本件の Issue #406 のような一括変更）は検査の契機に入らない。観測が保証されないので、FND-90 がめざした PR4 は実質的に満たされない。
  - asset-auditor の責務境界（資産の重複・競合の監査であり、要件の充足検査はしない）と矛盾する。wrapper の `description` と rationale の書き換えが必要になる。
  - 正規表現の照合は機械的に判定できる検査である。これを LLM エージェントに実行させるのは、PR2（機械判定と運用判断を混ぜない）に照らして過剰で、再現性も劣る。

**選択肢 2: 検査主体を CI 上の決定論的な機械検査に置き直し、SPEC-46-1／46-2 の入力/トリガを「CI が」に改版する。**

- **覆す根拠**: FND-90 が asset-auditor を選んだ目的は、主体の一意化（PR4）だった。一意化は CI でも満たせる。そのうえ CI なら、起動の契機がすべての変更に及ぶので、観測が構造的に保証される。asset-auditor では起動時機のせいで既存資産の退行を観測できない、という事実（本件ですでに見逃しが起きた）は、FND-90 の時点では検討されていない**新しい根拠**である。また、FND-90 は同じ処置の中で SPEC-45 を「CI が」に一意化しており、CI を主体とすることは同じ FND の中に先例がある。
- **利点**: 観測が保証され、再現性がある。PR2 に沿う。asset-auditor の責務境界を崩さずに済む。
- **欠点**:
  - 検査の実装（テストまたは lint）を新設する必要がある。
  - その実装が doc_system の SPEC を実現するものである以上、在グラフの設計ノード（MOD／SRC）でモデル化するかどうか、そして起票先の区分（`.claude/rules/02-decision-process.md`「起票先はプロジェクト区分で決める」）を決める必要がある。
  - SPEC-46-1／46-2 の MINOR 改版が要る。

**選択肢 3: 検査主体を spec-inspector に置き直す（DD-22 の背景の記述に合わせる）。**

- **利点**: DD-22 の背景の記述とは一致する。
- **欠点**: spec-inspector の責務は I/O・イベント・DFD・schema の仕様整合性であり、ファイル内容の正規表現検査は範囲外である。LLM であり、起動がオンデマンドなので、観測の保証と PR2 の問題は選択肢 1 と同じく残る。

## 推奨（決定ではない。決定はオーナーが行う）

**選択肢 2 を推奨する。** 根拠は 3 点である。

1. 本件の本質は、観測が保証されていないことである（PR4）。起動の契機がすべての変更に及ぶのは、3 案のうち選択肢 2 だけである。選択肢 1・3 では、今回と同じ見逃しが再発しうる。
2. FND-90 の目的（主体の一意化）は選択肢 2 でも満たされる。覆す対象は「どの主体か」という手段だけであり、その根拠（起動時機が既存資産の退行を覆わない・本件で実際に見逃した）も明示できる。
3. 正規表現の照合は、機械で判定すべき検査である（PR2）。選択肢 1・3 は、機械判定を LLM の運用に載せることになる。

**処置の順序（重要）**: 本 FND は、別 FND `pf-wrapper-の共通本文読込要求が-nfr-3-と-spec-46-1-の字義に全件抵触` の決定**の後に**処置することを推奨する。何を検査対象とし、何を除外するか（wrapper から自身の共通本文へのリンク・rationale へのポインタ）が決まる前に機械検査を入れると、22 件がすぐに違反となり、偽陽性だけを出し続けて検査の信頼を損なうからである。SPEC-46-1 の MINOR 改版は、あちらの FND と係属中の Q 素案 `含有ハーネスの担体から経緯を-rationale-へ移す基準と-prompt-ノードとの-ssot` の論点 B と同じバッチにまとめ、版を 1 回だけ上げることを推奨する（`.ai/guidance/common.md`「正本・実装規約」）。

「対応不要」との判断はしていない。採否と実施時期はオーナーが決める（`scheduled: sprint-1`＝現行スプリント。繰り越しはオーナーの明示指示がある場合に限る）。

## 統合・分割の理由

呼び出し元の観測 3 のうち、「検査主体が不在」の部分を本 FND として切り出した。「wrapper のリンクが要件と衝突」の部分は、別 FND `pf-wrapper-の共通本文読込要求が-…` が扱う。分けた理由は、指摘対象の「もの」と処置が違うからである（PR1）。あちらは要件の定義と実装の食い違い（処置は NFR-3／SPEC-46-1 の文言）、本件は検証機構の欠如（処置は SPEC-46-1／46-2 の入力/トリガと、検査を実装する資産）である。既存 open FND の実体（`reconciliation-の-tmp-掃除ガードが-…`）と機序（`tmp-掃除ガード追従テストの検査対象探索が-…`）を分けた先例と同じ扱いにした。

## 辺の張り先と選定理由

SPEC-46-1 と SPEC-46-2 の 2 本とした。どちらの入力/トリガも「asset-auditor が」と主体を定めており、選択肢 2・3 を採る場合の改版の対象になるからである。傘の SPEC-46（`スキルファイルは外部ファイル参照なしに自己完結`）は、本文が子 SPEC への分割を述べるだけで主体を定めていないので、張り先にしなかった。`asset-auditor` は在グラフのノード（PROMPT 等）を持たないので、辺を張れない。この事実は本文に記録するにとどめる。DD-22 は食い違いの根拠として参照しただけで、指摘対象ではない。

**接続規則変更の伴否**: 本指摘は `doc-system-v2/config.yml` の `must_link_to`／`must_be_linked_from`／`fnd_lifecycle` を追加・変更・削除しない（対象は SPEC の入力/トリガの文言と、検査を実装する資産）。したがって、接続マトリクス・ドキュメント一覧・author 資産への伝播チェックは不要と判断した。ただし選択肢 2 で検査を実装する資産を新設する場合は、着手前に `asset-auditor` による重複・競合の点検（A14）が必要である。
