**発火条件（いつ実害化するか）**

本指摘の直接の対象は `tests/unit/test_dsv2_cleantmp.py`（TC 相当）とその守る対象 `dsv2/cleantmp.py`（MOD 相当）であるが、**どちらも in-graph に対応ノードを持たない**。確認内容は次のとおり。

**forward 辺の張り先と選定理由**

指摘対象そのもの（未著作の MOD/P/TD/TC）には辺を張れないため、先例（open FND `dsv2 実装 6 モジュールに対応する設計ノード（MOD/P）が存在しない`）と同じ方針で、**欠落を受け止めるべき最も近縁の既存ノードを各層 1 件ずつ**選んで便宜上の forward 辺とする。本来の張り先が未著作である旨をここに明記する。

1. **PROMPT `reconciliation 調停支援プロンプト（検証＋本ファイル転記）`** — 設計層側の受け皿。本ノードの実体は `.claude/agents/reconciliation.md` であり（同ノード本文に「SPEC-39 の実体＝`.claude/agents/reconciliation.md`」と明記）、**本指摘が問題にしている借用の余地が現に成立している文書そのもの**である。ガード記述がここで腐れば、掃除を実行する当のエージェントが誤読する。個々の実装モジュール MOD に張る案は、担体が `spec_inspector/*.py` であって `dsv2/cleantmp.py` を含意しないため採らなかった。
2. **P `調停・本ファイル反映`（P-7-2）** — 分析層側の受け皿。`clean-tmp` による tmp 掃除は本プロセス（reconciliation Step 3-3）の一部として実行されるが、P-7-2 の子は `草案スキーマ検証`（P-7-2-1）と `本ファイル転記`（P-7-2-2）の2つのみで、掃除に相当する子プロセスを持たない。すなわち**掃除という活動を受け止められる唯一の既存ノード**である。

**選択肢**

1. **`_paragraphs()` を Markdown 構造に合わせた単位へ分割する** — 空行に加えて、箇条書き・番号付きリストの項目行（`- ` / `* ` / `N. `）と表の行（`|` 始まり）を段落境界として扱い、インデントされた継続行は直前の項目に属させる。判定単位が「1つの規範文」に近づき、3文書すべてで N-02 の借用防止が実効化する。反面、簡易 Markdown パースを回帰テストに持ち込むことになり、テスト自体の複雑度と、サブ項目の切り離しによる偽陽性リスクが増える。
2. **判定単位を「行」に落とす** — `clean-tmp`/`保護名` と保護名を含む**行**ごとに全保護名を要求する。実装は最小で借用を完全に排除できるが、word-wrap で1文が複数物理行に分かれる本文（`.claude/agents/reconciliation.md` L64–65 が実例）で偽陽性が出るため、既存本文をそのままにしては採れない。`_paragraphs()` の docstring が明示しているとおり、word-wrap 対策こそが段落化の当初の動機であり、これを捨てる案である。
3. **ガード記述の書式規約を先に定める** — 「ガード記述は箇条書き・表の中に置かず、前後に空行を持つ独立段落で書く」を著作規約化し、テストは規約違反（ガード段落がリスト・表の内側にあること自体）を検出する。テスト側の Markdown パースを増やさずに借用を構造的に排除できるが、`dsv2/README.md` のフォーマット依存マップのように**表であること自体に意味がある**文書には適用しにくく、少なくとも1件は文書側の書き替えが必要になる。
4. **現状維持＋発火条件の運用カバー** — 「保護名を追加・変更する PR では全ガード文書の該当記述を目視確認する」をチェックリスト化する。コストはゼロだが、K-11 → N-01 → N-02 の3ラウンドが示すとおり**この種の追従は目視では落ちる**（だからテストにした）ので、機構化の趣旨に逆行する。PR2「機械判定と運用ルールを混ぜない」の観点でも、機械判定にできるものを運用ルールへ差し戻す方向になる。

**推奨**: **選択肢 1 を基軸に、`dsv2/README.md` の表に対してのみ選択肢 3 の考え方を併用する**。根拠は3点。

- (a) 借用が現に成立しうる3文書のうち2件（`.claude/agents/reconciliation.md`・`CLAUDE.md`）は箇条書き・番号付きリストであり、行頭マーカーによる分割は機械的に判定でき、継続行のインデント規約も両文書で一貫している（実測）ため、選択肢 1 の偽陽性リスクは低い。
- (b) 表（`dsv2/README.md`）は「行＝レコード」なので行を段落境界にするだけで大半は解決するが、**1行に複数セルがあるためセル間借用（規範セル ↔ 補助アンカー列）は残る**。ここまでテストで潰すとパースが重くなるので、「規範記述は1セルに閉じる」を書式規約として明示し、テストは行単位で止めるのが費用対効果に見合う。
- (c) 選択肢 2 単独は既存本文の word-wrap を壊す前提になり、選択肢 4 は本テストの存在意義そのものを否定する。

**いずれの選択肢を採るかの決定はオーナー判断を仰ぐ**（実施スプリントは `scheduled: sprint-1`＝現行スプリントのまま。繰り越しはオーナーの明示指示がある場合のみ）。

**本指摘の対象外（留保）**

- **段落選定条件（`_guard_paragraphs` の条件1）由来の取りこぼし**は、段落粒度ではなく選定述語の問題であり機序が異なるため、別 FND `保護名追従テストの段落選定条件が実装 docstring の単一保護名記述を取りこぼす` として同時に起票した（そちらは**現に見逃しが発生している**点でも本指摘と状態が異なる）。両者を1件に統合すべきかはオーナー判断を仰ぐ。
- **`_discover_guard_docs` の探索母集合の問題** — ガード記述を丸ごと削除した文書は `clean-tmp`・`PROTECTED_DIRNAMES` の両語を失って GUARD_DOCS から外れるため、「ガード説明が見つからない」を検出する `assertTrue(guard_paragraphs, ...)` にも到達しない（文書が黙って検査対象から抜ける）。これは段落粒度でも選定条件でもなく**対象集合**の欠陥であり、本指摘・別 FND のいずれとも機序が異なる。現時点で3文書とも両語を保持しているため実害は無い。独立した指摘として起票すべきか、上記2件のいずれかに統合すべきかを含めてオーナー判断を仰ぐ（**「対応不要」とは判断していない**）。
- **`dsv2/cleantmp.py` に対応する MOD/P が存在しない**件は、先例 open FND `dsv2 実装 6 モジュールに対応する設計ノード（MOD/P）が存在しない` と同根だが、同 FND が列挙する対象6本（`viewer` / `rename` / `reverse` / `gitutil` / `yamledit` / `dashboard`）に `cleantmp.py` は**含まれていない**（同 FND 起票後に追加された実装のため）。同 FND のスコープを拡張して扱うか、別途起票するかはオーナー判断を仰ぐ。本指摘では forward 辺を張らず、事実の記録に留める。

**接続規則変更の伴否**: 本指摘は `doc-system-v2/config.yml` の `must_link_to` / `must_be_linked_from` の追加・変更・削除を含まない（対象はテストコードの判定粒度であって接続規則ではない）。したがって接続マトリクス（`docs/doc-system/03-connection-matrix.md`）・ドキュメント一覧（`docs/doc-system/01-document-items.md`）・各 author エージェント／スキルへの伝播同期は不要と判断した。
