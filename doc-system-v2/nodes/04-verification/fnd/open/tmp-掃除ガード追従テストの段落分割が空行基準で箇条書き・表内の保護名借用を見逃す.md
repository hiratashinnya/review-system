実害の判定根拠は次のとおり。

1. **現時点で「誤ったガード記述」は無い** — `_guard_paragraphs()` が**選定した**段落については、`PROTECTED_DIRNAMES`（`_handoff`・`_karte`）の両方が現に書かれていることを実測で確認した。**借用そのものは現に成立している**（`dsv2/cleantmp.py` L30–37 は L32 が `_handoff` のみ・L33 が `_karte` のみの別 bullet で、段落全体としてのみ両方を満たす）が、その 2 行はそれぞれ別個の参照先（CLAUDE.md のハンドオフ規約／Issue #307 の診断カルテ）を述べた**内容として正しい記述**であり、いま誤った説明が置かれているわけではない。したがって「現に損害が進行している」型の指摘ではなく、ERROR には当たらない。なお、選定から漏れた段落に単一保護名記述が現存する件は別 FND `保護名追従テストの段落選定条件が実装 docstring の単一保護名記述を取りこぼす` の指摘対象であり、本ノードの判定には含めない。

3. **見逃しは静かに起きる** — 借用による偽陰性はテストが緑のまま成立するため、乖離が入っても誰も気づかない。これは深刻度を下げる理由にはならないが、「今まさに壊れている」ではないため WARNING に留める。

> **深刻度を据え置いた判断（v0.1.1）**: v0.1.1 で「`.py` にも借用の余地がある」という事実が加わったが、これは**機序の適用範囲が広がった**ことを意味するのであって、現に誤った記述が生じたことを意味しない（上記 1）。したがって WARNING を維持する。**ERROR へ引き上げる余地があるとすれば**、借用が成立している段落が「削除を実行する主体が読む規範」であるときだが、`cleantmp.py` の `依存仕様:` ブロックは実装者向けのアンカー記述であり、掃除を実行する `reconciliation` が読む規範は `.claude/agents/reconciliation.md` 側である。この評価軸は別 FND `tmp 掃除ガード追従テストの検査対象探索が…`（ERROR）が採ったものと同一で、そちらは「取りこぼしている 3 件がいずれも削除実行主体の読む規範そのもの」であるため 1 段重い。**深刻度の最終判断はオーナーに委ねる**（「対応不要」とは判断していない）。

**内容**: `tests/unit/test_dsv2_cleantmp.py::TestGuardDocsMatchProtectedNames` の `_paragraphs()` は**空行区切り**で段落を作る。しかし Markdown の箇条書き・番号付きリスト・表は**項目間に空行を置かない記法**であり、**Python docstring の箇条書き（`  * ` / `  N. `）も同様に項目間に空行を置かない**ため、これらの中では**ブロック全体が1つの「段落」**になる。`_guard_paragraphs()` はその粗い単位に対して `PROTECTED_DIRNAMES` の充足を判定するので、**同一ブロック内の別の記述から保護名を借用**でき、N-02（`dsv2/cli.py` の独立した2 docstring 間の借用）と**同型の偽陰性**が残っている。

**forward 辺の張り先と選定理由**

指摘対象そのもの（未著作の MOD/P/TD/TC）には辺を張れないため、先例（open FND `dsv2 実装 6 モジュールに対応する設計ノード（MOD/P）が存在しない`）と同じ方針で、**欠落を受け止めるべき最も近縁の既存ノードを各層 1 件ずつ**選んで便宜上の forward 辺とする。本来の張り先が未著作である旨をここに明記する。

1. **PROMPT `reconciliation 調停支援プロンプト（検証＋本ファイル転記）`** — 設計層側の受け皿。本ノードの実体は `.claude/agents/reconciliation.md` であり（同ノード本文に「SPEC-39 の実体＝`.claude/agents/reconciliation.md`」と明記）、**本指摘が問題にしている借用の余地が現に成立している文書そのもの**である。ガード記述がここで腐れば、掃除を実行する当のエージェントが誤読する。個々の実装モジュール MOD に張る案は、担体が `spec_inspector/*.py` であって `dsv2/cleantmp.py` を含意しないため採らなかった。
2. **P `調停・本ファイル反映`（P-7-2）** — 分析層側の受け皿。`clean-tmp` による tmp 掃除は本プロセス（reconciliation Step 3-3）の一部として実行されるが、P-7-2 の子は `草案スキーマ検証`（P-7-2-1）と `本ファイル転記`（P-7-2-2）の2つのみで、掃除に相当する子プロセスを持たない。すなわち**掃除という活動を受け止められる唯一の既存ノード**である。

**選択肢**

1. **`_paragraphs()` を記述単位へ分割する（Markdown と Python docstring の双方に適用）** — 空行に加えて、箇条書き・番号付きリストの項目行（Markdown の `- ` / `* ` / `N. ` および docstring のインデント付き `* ` / `N. `）と表の行（`|` 始まり）を段落境界として扱い、さらにインデントされた継続行は直前の項目に属させる。**適用対象を Markdown 3 文書に限定しないことが要点**で、`cleantmp.py` L30–37・L9–21 が示すとおり `.py` の docstring でも同じ借用が成立しているため、`.py` を除外すると是正が現存の実例を素通りする。判定単位が「1つの規範文」に近づき、4 種すべてで N-02 の借用防止が実効化する。反面、簡易 Markdown／docstring パースを回帰テストに持ち込むことになり、テスト自体の複雑度と、サブ項目の切り離しによる偽陽性リスクが増える。
2. **判定単位を「行」に落とす** — `clean-tmp`/`保護名` と保護名を含む**行**ごとに全保護名を要求する。実装は最小で借用を完全に排除できるが、word-wrap で1文が複数物理行に分かれる本文（`.claude/agents/reconciliation.md` L64–65 が実例。`cleantmp.py` L13–19 の項目3 も 7 行にわたる）で偽陽性が出るため、既存本文をそのままにしては採れない。`_paragraphs()` の docstring が明示しているとおり、word-wrap 対策こそが段落化の当初の動機であり、これを捨てる案である。
3. **ガード記述の書式規約を先に定める** — 「ガード記述は箇条書き・表の中に置かず、前後に空行を持つ独立段落で書く」を著作規約化し、テストは規約違反（ガード段落がリスト・表の内側にあること自体）を検出する。テスト側のパースを増やさずに借用を構造的に排除できるが、`dsv2/README.md` のフォーマット依存マップのように**表であること自体に意味がある**文書や、`cleantmp.py` の `依存仕様:`／ガード項目のように**箇条書きであること自体が記述様式として定着している** docstring には適用しにくく、少なくとも複数件は文書側の書き替えが必要になる。
4. **現状維持＋発火条件の運用カバー** — 「保護名を追加・変更する PR では全ガード文書の該当記述を目視確認する」をチェックリスト化する。コストはゼロだが、K-11 → N-01 → N-02 の3ラウンドが示すとおり**この種の追従は目視では落ちる**（だからテストにした）ので、機構化の趣旨に逆行する。PR2「機械判定と運用ルールを混ぜない」の観点でも、機械判定にできるものを運用ルールへ差し戻す方向になる。

**推奨**: **選択肢 1 を基軸に、`dsv2/README.md` の表に対してのみ選択肢 3 の考え方を併用する**。根拠は3点。

- (a) 借用が現に成立しうる文書のうち `.claude/agents/reconciliation.md`・`CLAUDE.md`・`dsv2/cleantmp.py` の 3 件は箇条書き・番号付きリストであり、行頭マーカーによる分割は機械的に判定でき、継続行のインデント規約も 3 文書で一貫している（実測）ため、選択肢 1 の偽陽性リスクは低い。**とくに `.py` を対象に含めることが必須**である——現に借用が成立している唯一の実例が `.py` 側にあるため、Markdown 限定の是正では実例が残る。
- (b) 表（`dsv2/README.md`）は「行＝レコード」なので行を段落境界にするだけで大半は解決するが、**1行に複数セルがあるためセル間借用（規範セル ↔ 補助アンカー列）は残る**。ここまでテストで潰すとパースが重くなるので、「規範記述は1セルに閉じる」を書式規約として明示し、テストは行単位で止めるのが費用対効果に見合う。
- (c) 選択肢 2 単独は既存本文の word-wrap を壊す前提になり、選択肢 4 は本テストの存在意義そのものを否定する。

**いずれの選択肢を採るかの決定はオーナー判断を仰ぐ**（実施スプリントは `scheduled: sprint-1`＝現行スプリントのまま。繰り越しはオーナーの明示指示がある場合のみ）。**「対応不要」とは判断していない。**

**本指摘の対象外（留保）**

- **段落選定条件（`_guard_paragraphs` の条件1）由来の取りこぼし**は、段落粒度ではなく選定述語の問題であり機序が異なるため、別 FND `保護名追従テストの段落選定条件が実装 docstring の単一保護名記述を取りこぼす` として同時に起票した（そちらは**選定から漏れた段落に現に単一保護名記述が残っている**点でも本指摘と状態が異なる）。両者を1件に統合すべきかは引き続きオーナー判断を仰ぐ。なお DD `FND 起票単位は機序で分け対象集合が同型の指摘は既存 FND のスコープ拡張とする` の判定手順に照らすと、両者は**機序が異なる**（判定単位の粗さ／選定述語の狭さ）ため分離が既定であり、統合しない側に倒すのが整合的である旨を申し添える（決定はオーナー）。

  - **v0.1.0 の「現時点で3文書とも両語を保持しているため実害は無い」との関係**: 同 FND は同じ対象を **ERROR・現に 3 件取りこぼし**と判定しており、字面上ぶつかる。両者は**機序が異なるため評価も異なる**——本ノードが「実害なし」と述べたのは**穴①（ガード記述の消滅を検出できない）**についての評価であり、現に 3 文書とも両語を保持している以上その穴はまだ発火していない。同 FND が ERROR とした根拠は**穴②（候補リストが固定で 4 ツリー資産・in-graph ノードを初めから含まない）**であり、こちらは候補集合の外に未同期 3 件が現存する＝**既に発火済み**である。v0.1.0 は穴②を観測していなかったため「実害は無い」と総括していた。以後の正本は同 FND とする。
