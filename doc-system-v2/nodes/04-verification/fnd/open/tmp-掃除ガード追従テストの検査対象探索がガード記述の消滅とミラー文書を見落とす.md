**深刻度**: ERROR（**実害で判定する**。テストが現に落ちるか否か・機械検査規則の有無は判定根拠にしない）

実害の判定根拠は次のとおり。

1. **検出漏れは現に存在する（latent ではない）** — 本指摘の起票過程で候補集合の外を手作業で確認したところ、**掃除ガードを持つべき記述でありながら一度も検査されていない文書が 3 件**現存した（`.github/agents/reconciliation.agent.md` / `.codex/agents/reconciliation.toml` / in-graph の PROMPT ノード `reconciliation 調停支援プロンプト（検証＋本ファイル転記）`）。3 件はいずれも「`tmp/<sprint>/<parent-id>/` を削除する」旨だけを述べ、`clean-tmp` にも保護名（`_handoff`・`_karte`）にも触れていない。**このドリフトは K-11 → R-06 → OOS-1 → N-01 → N-02 の 5 ラウンドを生き延びている**。
2. **失われるものが回復不能** — 見落としの下流損害は、ガードを知らない `reconciliation` が `tmp/_handoff/`（未回収のハンドオフ）・`tmp/_karte/`（是正ループの診断カルテ・Issue #307）を削除することである。どちらも `.gitignore` 済みで git から復元できない。
3. **誤った保証を与えている** — 本テストは「保護名を増やしたら記述も増やす、を機械的に固定する」と docstring で宣言しているが、実際に固定できているのは**自分が数え上げた 6 件だけ**である。緑であることが「全ガード記述が追従している」ことを意味しないにもかかわらず、5 ラウンドの是正はいずれもこのテストの緑を根拠に打ち切られてきた。前 2 件（段落粒度・段落選定条件）を WARNING と判定したのは「現に誤ったガード記述が無い」「取りこぼした記述が削除主体の読む規範ではない」ためであるが、**本件で取りこぼしている 3 件はいずれも削除を実行する主体が読む規範そのもの**であり、同じ物差しで測ると 1 段重い。

**内容**: `tests/unit/test_dsv2_cleantmp.py::TestGuardDocsMatchProtectedNames` は、検査対象文書（`GUARD_DOCS`）を **`_candidate_guard_docs()`（固定の候補リスト）→ `_discover_guard_docs()`（語の出現による絞り込み）** の 2 段で決める。この**対象集合の決め方**に、次の 2 つの穴が同時に開いている。段落の分割単位（別 FND）・段落の選定条件（別 FND）とは異なり、**そもそも検査対象に入るかどうか**の欠陥である。

**穴① 動的絞り込みが「語の出現」に依存する（消滅を検出できない）**

`_discover_guard_docs()` は候補のうち `clean-tmp` または `PROTECTED_DIRNAMES` の語を含むファイルだけを `GUARD_DOCS` に採る。したがって**ある文書からガード説明を丸ごと削除すると、その 2 語も同時に失われ、当該文書は `GUARD_DOCS` から静かに外れる**。結果、「ガード説明が見つからない」を検出する砦である `assertTrue(guard_paragraphs, f"clean-tmp のガード説明が見つからない: {doc}")` にも到達しない。

このテストは「説明が**誤っている**（保護名が足りない）」は検出できるが、「説明が**消滅した**」は検出できない。しかも消滅のほうが損害は大きい（誤った説明はまだ手掛かりを残すが、消滅は痕跡を残さない）。

**穴② 候補リストが固定で 4 ツリー資産・in-graph ノードを初めから含まない（現に取りこぼしている）**

`_candidate_guard_docs()` は `.claude/agents/reconciliation.md` ／ `CLAUDE.md` ／ `dsv2/README.md` ／ `dsv2/*.py` の 4 種のみを候補とする。しかし本リポジトリの資産は**4 ツリー（`.claude` 正本 ↔ `.github` Copilot ↔ `.codex` Codex CLI ↔ `.agents`）に多重化**されており、`reconciliation` の定義は `.claude` 以外に 2 本存在する。さらに doc_system では同エージェントが **in-graph の PROMPT ノード**としてもモデル化されている。これら 3 件は候補リストに無いため、穴①の判定に到達する以前に対象外である。

**発火条件（いつ実害化するか）**

1. **穴①**: ガード担当文書がリライトされ、ガード節ごと消える／別ツールへの言及に置き換わる。当該文書は黙って対象から外れ、以後どのラウンドでも検査されない。
2. **穴①**: 保護名の変数名が変わる（`PROTECTED_DIRNAMES` → 別名）／コマンド名が変わる（`clean-tmp` → 別名）。**全ガード文書が一斉に対象から外れ、`assertTrue(self.GUARD_DOCS, "ガード対象文書が1件も見つからない")` だけが最後の砦になる**（1 件でも残れば PASS するため、実際には砦にならない）。
3. **穴②**: 新しいプラットフォームツリーが増える／既存ミラーが更新される。`asset_parity` は presence/absence のみを見て内容 staleness ではビルドを止めない（CLAUDE.md 明記）ため、内容同期を機械的に見る主体がどこにも居ない。
4. **穴②**: 掃除手順が新しい資産（別の agent 定義・skill）に書かれる。候補リストに追加されない限り検査されない。

**in-graph 根拠の不在と forward 辺の選定理由（前 2 件から再検討した結果）**

本指摘の直接の対象は `tests/unit/test_dsv2_cleantmp.py`（TD/TC 相当）であり、対応する検証層ノードは in-graph に存在しない（`nodes/**` を `cleantmp`/`clean-tmp`/`clean_tmp` で検索して 0 件・前 2 件の起票時に実測済み）。そのうえで、同時期に著作した前 2 件（PROMPT ＋ P の 2 辺）とは**張り先を変える**。理由は 3 点。

1. **`dsv2/cleantmp.py` の MOD/P 欠落は既に別 FND が引き受けた** — オーナー判断（2026-08-04）により、open FND `dsv2 実装 6 モジュールに対応する設計ノード（MOD/P）が存在しない` のスコープが `cleantmp` を含む 7 本へ拡張された（同 FND v0.2.1・決定の記録＝DD `FND 起票単位は機序で分け対象集合が同型の指摘は既存 FND のスコープ拡張とする`）。したがって本指摘は「設計ノードが無い」ことを重ねて指摘しない（重複起票の回避）。
2. **PROMPT ノードは同時起票の別 FND の“真の”指摘対象である** — 同ノード本文がガードを持たないこと自体が別 FND の内容であり、本指摘から同じノードへ**便宜的な**辺を張ると、1 つのノードに対して性質の異なる 2 つの指摘が同じ形の辺で表現され、辺からはどちらの処置が要求されているのか読めなくなる。便宜的な受け皿より、意味の通る 1 辺を選ぶ。
3. **残る受け皿は P `調停・本ファイル反映`（P-7-2）** — `clean-tmp` による掃除は本プロセス（reconciliation Step 3-3）の一部として実行される。本テストが守っている対象（掃除手順の記述の追従）はこの活動に属するため、分析層側の受け皿として成立する。**本来の張り先＝本テストに対応する TD/TC が未著作である旨をここに明記する。**

**決定スパインのバックリファレンス（v0.1.1 で付与）**

本ノードが**独立した 3 件目の FND として起票された**こと自体が、2026-08-04 のオーナー決定に基づく（既存 2 件へ統合せず分離する、という起票単位の決定）。その決定は DD `FND 起票単位は機序で分け対象集合が同型の指摘は既存 FND のスコープ拡張とする` に記録した。決定は本ノードの存在という形で**既に反映済み**であるため、DD-016 の義務辺モデルに従い `DD → 本ノード` の義務辺は張らず、**反映先である本ノードから `→ DD` のバックリファレンス辺を張る**（RULE-001 の義務辺残存を生まない形）。この辺は provenance を辿るための被参照アンカーであり、指摘内容・指摘対象・深刻度のいずれにも影響しない。

**選択肢**

1. **候補リストを廃し、リポジトリ全体を走査して「掃除・削除を指示する文書」を動的に集める** — 取りこぼしは原理的に無くなる。反面、走査対象が全ファイルに広がり、判定述語（何をもって「掃除を指示する文書」とするか）を語の出現で決める限り穴①が形を変えて残る。誤検出も増える。
2. **`GUARD_DOCS` を「必須リスト（MUST）＋動的候補（MAY）」の 2 層にする** — 「ガード説明を必ず持つべき文書」を**明示的な固定リスト**として持ち、そこに載った文書が語を失ったら **`assertTrue(guard_paragraphs)` が発火して落ちる**（＝消滅の検出が成立する・穴①の解消）。必須リストに 4 ツリーのミラー（`.github/agents/reconciliation.agent.md`・`.codex/agents/reconciliation.toml`）を含めれば穴②も同時に閉じる。動的絞り込みは本来の目的（無関係な `dsv2/*.py` を巻き込まない）に限定して残す。コストは必須リストの保守（文書を増やしたら足す）だが、**保守漏れは「足し忘れ＝検査されない」であって「消滅を見逃す」ではない**ため、現状より悪化しない。
3. **4 ツリーの内容同期は `asset_parity` 側に持たせる** — ミラーの内容ドリフトは本来 `asset_parity` の守備範囲（現行は presence/absence のみ・staleness はビルドを止めない）。掃除ガードに限らず全資産のミラー同期を一般に検査できる。反面、`asset_parity` に「意味のある同期」の判定を持ち込むことになり、対象を絞る仕組み（どのセクションを同期必須とみなすか）を別途設計する必要がある。単独では in-graph の PROMPT ノード（4 ツリーではない）を被覆しない。
4. **現状維持＋運用チェックリスト** — 「ガード文書を編集する PR では全ミラーを目視確認する」を規約化する。コストはゼロだが、K-11 → N-02 の 5 ラウンドが示すとおりこの種の追従は目視で落ちる（だからテストにした）。PR2「機械判定と運用ルールを混ぜない」にも逆行する。

**推奨**: **選択肢 2 を基軸に、4 ツリー分は選択肢 3 と分担する。**根拠は 3 点。

- (a) 穴①は「消滅の検出」であり、これは**明示的な必須リストなしには原理的に成立しない**（対象を対象自身の内容から決める限り、内容が消えれば対象でなくなる）。選択肢 1 は母集合を広げるだけで、この自己参照を断ち切れない。
- (b) 必須リストは**一覧できる保守対象**であり、暗黙の語彙依存より監査しやすい（前 FND の選択肢 1 で採った判断と同じ論理）。
- (c) 4 ツリーのミラー同期は掃除ガード固有の問題ではなく、`asset_parity` に一般解を置くほうが同型の再発（他エージェント定義のドリフト）まで止められる。ただし in-graph の PROMPT ノードは 4 ツリーの外にあり `asset_parity` では被覆できないため、そこは選択肢 2 の必須リスト（または別途 in-graph 検査）で拾う必要がある。

**採否の決定はオーナー判断を仰ぐ**（実施スプリントは `scheduled: sprint-1`＝現行スプリントのまま。繰り越しはオーナーの明示指示がある場合のみ）。**「対応不要」とは判断していない。**

**本指摘の対象外（留保）**

- **`.github`/`.codex` ミラーおよび PROMPT ノードが現に未同期である件**は、記述そのものの是正であって検査対象探索の問題ではないため、別 FND `reconciliation の tmp 掃除ガードが in-graph PROMPT と Copilot・Codex ミラーに未同期` として同時に起票した。
- **段落の分割単位**（箇条書き・表・docstring でブロック全体が 1 段落になる）と**段落の選定条件**（語の出現依存で実装 docstring を取りこぼす）は、いずれも「対象に入った文書の中でどう判定するか」の問題であり機序が異なる。別 FND 2 件として同時期に起票済み。
- **`tests/unit/test_dsv2_cleantmp.py` に対応する TD/TC が未著作である件** — オーナー判断（2026-08-04）でスコープ拡張された FND `dsv2 実装 6 モジュールに対応する設計ノード（MOD/P）が存在しない` は **MOD/P に限った指摘**であり、検証層ノード（TD/TC）の欠落は含まない。同 FND をさらに TD/TC まで拡張するか、別途起票するかはオーナー判断を仰ぐ（**「対応不要」とは判断していない**）。なお DD `FND 起票単位は機序で分け…` の判定手順に照らすと、TD/TC の欠落は同 FND と**対象集合が同型（設計外実装に対応する in-graph ノードの欠落）**である一方、**欠落しているノードの層が異なる**ため、既存 FND のスコープ拡張と別途起票のどちらにも寄せうる境界事例である旨を申し添える（決定はオーナー）。
- 本指摘は `karte/paths.py`（`tmp/_karte` のパスガード実装）を対象に含めない。同ファイルは保護名を扱うが `clean-tmp` の掃除ガードを説明する文書ではなく、候補に含めるべきかは選択肢 2 の必須リスト設計の中で判断すべき事項である。

**接続規則変更の伴否**: 本指摘は `doc-system-v2/config.yml` の `must_link_to` / `must_be_linked_from` の追加・変更・削除を含まない（対象はテストの検査対象探索であって接続規則ではない）。したがって接続マトリクス（`docs/doc-system/03-connection-matrix.md`）・ドキュメント一覧（`docs/doc-system/01-document-items.md`）・各 author エージェント／スキルへの伝播同期は不要と判断した。本改訂（v0.1.1）でもこの判断に変更はない（バックリファレンス辺の付与は `config.yml` の規則ではなく DD-016 の既存運用に従った操作である）。
