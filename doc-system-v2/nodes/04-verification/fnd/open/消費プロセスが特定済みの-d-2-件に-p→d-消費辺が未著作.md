**判断事項②: 辺追加のみの版バンプ種別（z か MINOR か）**

判断材料（DD `ノードバッジをノード固有バージョン x.y.z に正式化・ファイルフロントマター version 廃`＝DD-8 §4）:

- DD-8 §4 の明文 — 「構造変更（YAML キー追加・型変更・**辺の追加**/削除/変更）→ MINOR バンプ（x.Y）」「内容のみ（本文修正・バックリファレンス辺追加・suppress 追加）→ z バンプ（x.y.Z）」「z バンプは伝播不要（依存元ノードの ref_version 更新不要）」。
- DD-21 の先例 — 辺逆転・backref 付与は「参照先の意味内容を変えず downstream の再レビューを要さない provenance/lifecycle 操作」として z に確定済み。本件が同類（欠落辺の補完＝意味内容は本文で既に確定済み）と解せるかが論点。
- ドリフト影響の実測 — `検査ビュー射影` への入辺は MOD `projector`（`ref_version: "0.1"`）の **1 件のみ**。MINOR（v0.1.0→v0.2.0）にすると当該辺が RULE-004 ドリフト 1 件になり、`projector.yaml` の ref を `"0.2"` へ同期する必要がある。`設定スライス組立` への入辺は **0 件**のため、いずれの選択でもドリフトは生じない。

選択肢:

1. **両ノードとも MINOR（v0.1.0 → v0.2.0）＋ `projector` の ref_version を `"0.2"` へ同期** — DD-8 §4 の「辺の追加＝MINOR」を字義どおり適用。既存 DD の改訂は不要。付随作業は projector 1 件の ref 更新のみ。
2. **両ノードとも z（v0.1.0 → v0.1.1）** — DD-21 の類推で「本文に既述の事実を辺として明示するだけ＝意味内容は不変」と解する。ドリフト 0 で付随作業なし。ただし DD-8 §4 の明文（辺の追加＝MINOR）と衝突するため、DD-8 §4 に「規則充足のための欠落辺補完」例外を追記しない限り運用が曖昧化する。
3. **ノードごとに使い分ける**（入辺のある `検査ビュー射影` は z、入辺のない `設定スライス組立` は MINOR 等） — ドリフト回避を優先する場当たり。同一処置内で版バンプ規準が割れ、以後の判断根拠にならないため非推奨。
