## 観測事実（2026-09-29 実測）

### 1. 対象の在グラフ表現には偏りがある

- PROMPT ノードは `doc-system-v2/nodes/05-design/prompt/` に **22 件**ある。内訳は、`carrier` を持つもの 15 件（14 件が `carrier: "skill"`＝`prompt_coverage_targets` の 14 スキル、1 件が `carrier: "agent"`＝`doc-system-config-operator`）と、`carrier` を持たない著作エージェント PROMPT 7 件（`requirements`/`spec`/`analysis`/`design`/`verification-author`・`reconciliation`・`reconciliation-validator`。SPEC-27 系）。
- `.claude/rules/02-decision-process.md` が含有ハーネスとして列挙していながら **PROMPT ノードを持たない**ロールがある。`spec-inspector`・`structured-analysis`・`dsv2-lookup`・`authoring-fanout`・`doc-system-v2-authoring`（著作エージェント共通契約）の 5 件である。これらの担体を変えても、在グラフには受け皿が無い。同じ構造的な不足は、既存の open FND `dsv2-lookup.md-の手順に統制下で必ず-deny-される-python3-c-例が残っている`（隣接観測 2）が `dsv2-lookup` について既に記録している。

### 2. `prompt-coverage`（RULE-032）は担体の内容を見ない

`dsv2/query.py` の `prompt_coverage_gaps()`（L326–349）は、`type == "prompt"` かつ `carrier ∈ {skill, agent}` のノードの id が `"{skill}-"` で始まるかどうかだけを判定する。担体ファイルは読まない。**したがって担体内で記述を移しても、PROMPT ノードの本文を直しても、RULE-032 の結果は変わらない。** 同じ事実は既存 open FND `reconciliation-の-tmp-掃除ガードが-in-graph-prompt-と-copilot・codex-ミラーに未同期` が「なぜ機械的に検出されなかったか」3 で記録済みである。

### 3. `drift`（RULE-004）は在グラフのサイドカー間でしか働かない

`_drift()`（L218–222）と `drift()`（L352–367）は、辺の `ref_version` と参照先サイドカーの `version` の x.y を比べるだけである。担体（`.claude/**`・`.ai/**`）は in-graph の版を持たない。そのため**担体を編集しただけでは drift は 0 のまま**になる。drift が起きるのは PROMPT ノード自身を MINOR 以上で改版したときだけである。現時点で PROMPT ノードへの入辺は、open FND 6 件から出ている **7 本**に限られる（`reconciliation` 宛て 4 本・`verification-author` 宛て 2 本・`reconciliation-validator` 宛て 1 本）。z バンプならこれらは drift しないが、MINOR バンプなら 7 本とも drift として検出される。

### 4. PROMPT ノードと担体の内容を同期させる機構は無く、現にずれている

- PROMPT ノード本文は規範の要約（目的／入力変数／出力形式／注意事項）であり、経緯はほぼ書かれていない。したがって**経緯の純粋な移設だけなら、PROMPT ノードの本文は変わらないはず**である。
- ただし、**PROMPT ノードと担体の対応はすでに崩れている**。
  - **実体の指し先**: 22 件中 20 件が本文で「実体＝`.claude/skills/<name>/SKILL.md`」または `.claude/agents/<name>.md` と記述している。現在の `.claude/skills/*/SKILL.md` と `.claude/agents/*.md` は、共通本文 `.ai/skills/<name>/SKILL.md`／`.ai/agents/<name>.md` への参照だけを持つ薄い PF wrapper である（`.ai/rationale/README.md` の表：「共通規範本文の SoT」は `.ai/`、wrapper は「共通本文の編集正本ではない」）。在グラフのノードで `.ai/` を担体として指すものは **0 件**である（コーパス grep）。
  - **規範内容**: `spec-pipeline-仕様設計パイプラインskillプロンプト-オーケストレータ`（v0.1.0）の「目的」は、手順②として `/io-event-ledger` を挙げている。現在の担体 `.ai/skills/spec-pipeline/SKILL.md` にこの語は無い（grep 0 件）。`.ai/rationale/spec-pipeline.md` は同スキルの廃止（2026-06-11）を経緯として記録している。
  - `reconciliation` については、同種の規範の未同期が既存 open FND（観測 2 で挙げたもの）で ERROR として係属中である。
- 観測 2・3 のとおり RULE-032／RULE-004 はどちらもこのずれを検出しない。`asset_parity` も presence／absence しか見ない。

### 5. 規範か経緯かの判定基準は out-of-graph にしか無い

- 判定の軸は 2 か所に書かれている。1 つは `.claude/rules/01-principles.md`「PR8「消さない」の適用範囲」の区分 1／区分 2（「この文は読み手の行動を決めるか／なぜそう決めたかを説明するか」）。もう 1 つは `.ai/rationale/README.md`「何が入るか（分離の判定軸）」（規範＝責務境界・入出力契約・実行規律・停止条件、rationale＝設計判断の理由・却下案・既知の限界・変更経緯）。どちらも out-of-graph で、版を持たない。機械検査は `tests/unit/test_contract_split.py` だけで、見ているのは rationale へのリンクがあるか、rationale ファイルが存在するか、非規範と宣言しているかである。**移した文が本当に行動を決めない文かどうかは見ていない**。
- **先例**: `.ai/rationale/` には、含有ハーネスの rationale がすでに **15 件**ある。スキル 5 件（`architecture-design`・`spec-pipeline`・`test-strategy`・`docidx`・`impl-design-pipeline`）と、エージェント／共通契約 10 件（`*-author` 5 件・`reconciliation`・`reconciliation-validator`・`authoring-fanout`・`dsv2-lookup`・`doc-system-v2-authoring`）である。これらの移設に対応する在グラフのノード（Q/FND/DD）は **0 件**である（コーパスを `rationale`・`#372` で grep した結果、ヒットは観測 1 の `dsv2-lookup` FND だけ）。つまり、これまでの移設は「規範は不変」という前提を在グラフで照合しないまま行われてきた。

### 6. 自己完結要件（NFR-3／SPEC-46）の字義と、rationale への導線が衝突する

- NFR-3 `スキルは-self-contained`（v0.2.0）は「スキル実行時に外部ファイルの読み込みを要求しない（コンテキスト汚染の回避）」と定める。その葉 SPEC `スキルファイルに外部参照パターンが存在しない`（SPEC-46-1・v0.2.0）は、`\.\./`・`^include:`・`^source:`・`@import` に一致する行が 0 件であることを判定条件にしている。これは NFR→SPEC 導出の DD に基づく、意図的な設計である。
- `.ai/rationale/README.md` の規律 3「規範側から 1 行で辿れる」は、規範側に `../../rationale/<name>.md` 形式のリンクを置くよう求めている（`test_contract_split.py` が強制する）。**このリンクは SPEC-46-1 のパターン `\.\./` に字義どおり一致する。**
- ただし、この字義上の不一致は rationale 移設で初めて生じるものではない。14 対象スキルの `.claude/skills/*/SKILL.md` は、**14 件すべてがすでに `](../` を含んでいる**（共通本文 `.ai/skills/...` へのリンク）。しかもこちらは「必ず共通本文を読め」という読み込みの要求であり、NFR-3 の趣旨に照らしても rationale へのリンクより強く衝突する。著作エージェント側でも、`.ai/agents/*-author.md` が「共通契約を必ず読む」として `doc-system-v2-authoring.md` を参照しており、SPEC-27「外部参照なしに著作規約を提供」と同じ形の緊張がある。なお `.ai/agents/asset-auditor.md` には SPEC-46-1 の検査記述が無い（grep 0 件）ので、SPEC-46 の検査を実行する主体は現状いない。
- rationale へのリンクは「読まなくてよい」ことを明示した非規範のポインタである。NFR-3 の趣旨（実行時に読み込みを**要求しない**）とは両立しうるが、SPEC-46-1 の字義（パターン 0 件）とは両立しない。

### 7. PROMPT ノードの版方針は「本文変更」の指し先を定めていない

DD-22（`doc-system-設計層モデリングの-skill-展開方針を確定-…`・v0.1.0）は PROMPT ノードの版方針を「キャリア／本文変更＝MINOR・役割契約／IO 構造変更＝MAJOR」と定める。しかしここでいう「本文」が PROMPT ノードの本文なのか担体の本文なのかは書かれていない。そのため、担体の規範を変えない経緯移設が版方針上どの扱いになるのか（改版不要か、z か、MINOR か）は決まっていない。

## 論点 A の選択肢（排他）

### ① 在グラフに反映しない（これまでの移設の運用を追認する）

判定基準は out-of-graph（PR8 区分と `.ai/rationale/README.md`）のまま使う。担体での経緯移設は「規範不変の実装側の変更」とみなし、PROMPT ノードも版も変えない。

- **利点**: 作業量が最小で、Issue #562 の移設だけで完結する。観測 2・3 のとおり RULE-032／RULE-004 の結果は変わらず、FND 7 辺の drift も起きない。既存 15 件の移設と扱いがそろう。
- **欠点**: 「移した文が規範ではない」ことを、移設する本人が out-of-graph の基準だけで判断することになり、照合先が無い。観測 4 の PROMPT ノードと担体のずれ（実体の指し先・`/io-event-ledger`）は残り、全担体に触る今回のバッチで洗い出す機会を逃す。含有ハーネスの改修なのに在グラフに痕跡が残らない状態が続く（観測 5）。

### ② PROMPT ノードを設計上の規範 SSoT とし、担体側の文を「PROMPT ノードへ辿れるか」で判定する

- **SSoT の定義**: PROMPT ノードが「そのプロンプトが何をするか」の設計上の正本で、担体（`.ai/` 共通本文）はその実現である。DD-22 と、implementation 段で発火する DD-9 の `PROMPT←SRC`（「プロンプト資産は実装（skill/agent ファイル）で実現される」）の構図に合わせる。**PROMPT ノードに担体の全文を複製することは求めない**（要約粒度を保ち、二重正本を作らない）。
- **判定手順**: 担体の各記述を次の 3 つに振り分ける。
  - (a) PROMPT ノードの項目（目的／入力変数／出力形式／注意事項）か、規約本体（`CLAUDE.md`＋`.claude/rules/`）へ辿れる行動規定 → 担体に残す。
  - (b) どこへも辿れないが行動を決めている記述 → **PROMPT ノードへ反映してから**担体に残す。在グラフの規範を先に補う。
  - (c) 行動を決めない経緯 → `.ai/rationale/` へ移す。このうち在グラフの DD/FND と中身が重なるものは、本文を移すのではなく DD/FND の slug 参照に置き換える（二重正本を避ける）。
- **版の扱い**: 純粋な移設だけなら PROMPT ノードは変えない（改版もしない）。観測 4 の実体の指し先を `.ai/` に直すのは z バンプ（本文だけの変更で、辺は不変）。(b) の反映は DD-22 に従い MINOR バンプとする（DD-22 の「本文」は PROMPT ノードの本文と解釈し、その解釈を DD に記録する）。
- **PROMPT ノードを持たない 5 ロール**（観測 1）は照合先が規約本体だけになる。その旨を DD に記録する。これらを在グラフに載せるかどうかは本 Q では扱わない（`dsv2-lookup` FND の選択肢①と同じく、別に決める事項）。
- 判定基準そのものは、本 Q を DD へ昇格させる際に在グラフへ明文化する。
- **利点**: 判定が「PROMPT ノードの項目に辿れるか」という外部の照合先に基づくので、移設する本人の自己判定にならない。全担体に触る今回のバッチで、観測 4 のずれ（既存の移設 15 件の分も含む）を同時に洗い出せる。在グラフの規範が実装より遅れている箇所を、(b) として正規の経路で補える。
- **欠点**: 22 件の PROMPT ノードすべてを照合するため、作業量は①より大きい。(b) が出た PROMPT ノードは MINOR バンプになり、`reconciliation`／`verification-author`／`reconciliation-validator` の PROMPT ノードに入辺を持つ open FND 7 辺が drift する（観測 3）。これを解消するには FND 側の `ref_version` を更新する必要がある。

### ③ ② に加えて、PROMPT ノードと担体の同期を機械検査にする

サイドカーに担体のパスや内容ハッシュを持たせる、または担体に版を持たせ、ずれを検出する検査を新設する。

- **利点**: 観測 4 の型のずれが再発しにくくなる。
- **欠点**: サイドカーは未知キー禁止（`schema/sidecar.schema.json`）なので、スキーマ変更が必要になる。担体に版を持たせる案は、DD-8／FND-104 が意図して廃止した out-of-graph の版を事実上復活させることになり、**覆すための新しい根拠が必要**になる（`.claude/rules/01-principles.md`「意図的設計の尊重」）。本 Q の時点でその根拠は無い。さらに、経緯を移すだけでもハッシュは変わるので、「規範が変わったか」をハッシュでは判定できない。機械判定と運用判断を混ぜることになり（PR2）、偽陽性が常に出る。

### ④ 含有ハーネスを Issue #562 の移設対象から外す

移設は含有されない汎用ハーネスだけで行い、含有ハーネスの担体には手を付けない。

- **利点**: 在グラフへの影響はゼロになる。
- **欠点**: Issue のスコープを縮めることになり、その判断はオーナーのものである。すでに 15 件が移設済みなので、同じ PF 構造の中で含有ハーネスだけ形式がまちまちになる。観測 4 のずれも残る。

## 論点 B（NFR-3／SPEC-46 との関係）の選択肢

論点 A でどれを選んでも、rationale へのリンクは SPEC-46-1 の字義に触れる（観測 6）。

- **B-1 SPEC-46-1 を改版し、非規範のポインタを除外として明文化する**。「実行時に読み込みを要求しない参照（rationale／troubleshooting へのリンク）」は外部参照パターンの対象外とする。NFR-3 の趣旨（コンテキスト汚染の回避）は保たれ、意図的設計の**字義だけを趣旨に合わせる**ので、覆すための根拠は NFR-3 本文そのものになる。ただし葉 SPEC の MINOR 改版と、判定語彙の設計（ポインタをどう見分けるか）が必要になる。
- **B-2 担体からリンクせず、rationale 側からの片方向の参照だけにする**。SPEC-46-1 は変えずに済むが、`.ai/rationale/README.md` の規律 3 と `test_contract_split.py` の強制に反する。そちらは含有されない汎用ハーネス側なので、変更は Issue 運用になる。規範側から経緯へ辿れなくなる。
- **B-3 本 Q では扱わず、既存の `](../` 違反（観測 6）と合わせて別 FND に切り出す**。論点 A を先に進められるが、移設で rationale へのリンクが増える分、字義上の違反が増えたまま係属する。なお、SPEC-46-1 のいう「スキルファイル」が `.claude/skills/*/SKILL.md`（wrapper。例示はこちら）なのか、`.ai/skills/*/SKILL.md`（共通本文。rationale へのリンクはこちらに置かれる）なのかも決まっていない。

## 推奨（決定ではない。決定はオーナーが行う）

**論点 A は ②、論点 B は B-1 を推奨する。あわせて、観測 6 の「wrapper が共通本文の読み込みを必ず求めている」件は、B とは別の FND に切り出すことを推奨する。** 根拠は 4 点である。

1. **SSoT の置き場はすでに決まっている**。DD-22（skill を PROMPT 設計ノードとしてモデル化）と DD-9（`PROMPT←SRC`＝担体は PROMPT の実現）により、設計上の規範は PROMPT ノード、担体はその実装という構図になっている。② はこの構図を判定基準として使うだけで、新しい構造は持ち込まない。① は、この構図があるのに判定を out-of-graph だけで行うことになる。
2. **ずれは現に起きていて、機械検査では見つからない**（観測 2・3・4）。全担体に触る Issue #562 のバッチは、照合コストが最も安くなるタイミングである。① を選ぶとこの機会を逃し、既存 15 件の未照合も残る。
3. **③ は根拠が無いまま意図的設計を覆すことになり、判定の性質とも合わない**。out-of-graph の版を廃止した DD-8／FND-104 を覆す新しい根拠は無い。また「規範が変わったか」は、人の読みによる運用判断（PR2 の運用ルール側）であり、ハッシュで機械判定する対象ではない。④ はスコープの判断であり、起票者が推奨すべきものではない（採るならオーナー判断）。
4. **B-1 は意図的設計の趣旨を保ったまま字義だけを直す**。NFR-3 が守ろうとしているのは「実行時の読み込み要求」であり、読まなくてよいことを明示したポインタはその対象外と読める。B-2 はリンクを外すことで規範側から経緯へ辿れなくなり、PR8 区分 1（経緯を保全し、辿れるようにする）の実効が落ちる。一方で、wrapper が「共通本文を必ず読め」としている件は読み込みを**要求している**ので、B-1 の除外には入らない。性質が違うので、PR1 に従い別の指摘として分ける。

**② を採る場合の実施上の注意**:
- (b) による MINOR バンプで drift する FND 7 辺は、同じバッチで `ref_version` を更新する。z で済む変更を MINOR にしない（DD-8 §4）。
- 判定の記録は、PROMPT ノードごとに (a)(b)(c) の件数と (b) の中身を、DD の本文か各 PROMPT ノードの改訂記録に残す。
- 既存の open FND `reconciliation-の-tmp-掃除ガードが-in-graph-prompt-と-copilot・codex-ミラーに未同期` の選択肢 1（PROMPT ノードへの同期）は、② の (b) と同じ操作である。同じバッチで処置できるが、FND の解消は `dsv2 reverse` で機械的に実行する。
