**論点（1文）**: `must_be_linked_from` の `ds←prs` 規則（reason: "データストアは永続化実装で実現される（DS←PRS・DD-9）"）が言う「永続化実装」の意味を、現行どおり **書き込み（永続化）実装** に限るか、**永続層アクセス実装（読み書き両方）** へ読み替えるか。

**対応 Issue**: #255（必須辺検証ルールの見直し・修正 ③ `ds←prs`）。同 Issue が併記する `d←p` 消費辺の補完は本 Q のスコープ外（単一責務のため分離）。

## 観測事実

**規則（config.yml `must_be_linked_from`・out-of-graph）**:

```
- { node: ds, source: [prs], activate_stage: design, severity: error,
    reason: "データストアは永続化実装で実現される（DS←PRS・DD-9）" }
```

`current_stage: design` のため **live 発火中**（latent ではない）。

**DS 3件・PRS 1件の入出辺 実測（meta.json 全数照合）**:

| DS ノード | PRS からの入辺 | 出辺（利用プロセス） | 性格 |
|---|---|---|---|
| `tmp-ノード草案` | `tmp-草案ファイル書き出し`(PRS) **あり** | → `ノード著作・反映プロセス`(P) | 書き込みあり（規則充足） |
| `config.yaml-ds` | **なし** | → `設定ファイル読み込み`(P) | **読み取り専用** |
| `in-graph-ノードファイル群` | **なし** | → `in-graph-集合決定`(P) | **読み取り専用** |

- 現在の live 違反: `ds←prs` の **ERROR 2件**（`config.yaml-ds`・`in-graph-ノードファイル群`）。
- 読み取り専用であることは DS 本文にも明記されている:
  - `config.yaml-ds`「spec-inspector は読み取り専用で、P-5 が実行のたびに読込・検証するのみ（**書き込まない**）」
  - `in-graph-ノードファイル群`「spec-inspector は読み取り専用で、P-6 が実行のたびに trace_scope を適用して集合を再導出するのみ（**書き込まない**）」
- いずれの DS も**書き込み主体は系外**である（本文のライフサイクル節: ACTOR-1（仕様著者）が config.yaml を作成・更新／`.md` ファイルを作成・編集・削除する）。
- 一方で **読み取り実装は実在する**: `dsv2/meta.py`（`nodes/**/*.yaml` 走査）・`doc-system-v2/validate.py`（config 読込）。したがって「対応する実装が無いから辺を張れない」のではなく、**その実装を PRS として著作すべきか否か**が争点になる。

## 選択肢（排他）

### ① 規則不備とみなし、read-only DS を `ds←prs` の対象から除外する

「永続化実装＝書き込み実装」の現行解釈を維持し、書き込みを持たない DS を規則の適用対象から外す（A1 で観測した `applies_when: condition_present` と同種の適用条件付与、または DS 側に read/write 属性を持たせる等、除外の機械表現方法は付随論点として別途決める）。

- **利点**: DS 本文の記述（読み取り専用・書き込まない）と規則が一致し、ERROR 2件が即時解消する。PRS の責務を「永続化＝書き込み」の単一責務に保てる（PR1）。両 DS の書き込み主体は系外アクター（ACTOR-1）であり、系内に対応する永続化実装が存在しないという事実に規則を合わせられる（PR3: 系外＝非イベント）。読み取り経路は既に `DS→P`（`設定ファイル読み込み`・`in-graph-集合決定`）として分析層に表現済みで、その設計層実現は `p←mod` 側が担うため、読み取りのトレースが失われるわけではない。
- **欠点**: 現行 config.yml には DS の read/write を区別する語彙が無く、**除外条件を表す機構を新設する必要がある**（規則の複雑化）。また `dsv2/meta.py`・`validate.py` の読み取り実装は設計層に対応 PRS を持たないまま残り、設計⇔実装の乖離（Issue #160 系の論点）の一部が未解決で残る。

### ② 未著作とみなし、読み取り実装を PRS として2件著作する

`ds←prs` の「永続化実装」を「**永続層アクセス実装（読み書き両方）**」へ読み替え、`config.yaml-ds` と `in-graph-ノードファイル群` それぞれに対応する読み取り PRS を著作して辺を張る。

- **利点**: 実在する読み取り実装（`dsv2/meta.py`・`doc-system-v2/validate.py` の config 読込）が設計層に現れ、DS→実装のトレースが繋がる（PR6: 価値経路を遮断しない）。config.yml の規則本体（node/source/severity）を変えずに済み、reason 文言の読み替えと PRS 2件の著作だけで ERROR 2件が解消する。除外機構の新設が不要。
- **欠点**: PRS 型の責務が「永続化」から「永続層アクセス」へ広がり、**型の意味が変わる**（DD-9 の reason 文言のほか、PRS 型定義・接続マトリクス・各著作エージェント/スキルの記述など out-of-graph 資産の同期が必要）。DS 本文の「読み取り専用（書き込まない）」記述との整合も取り直しになる。加えて、読み取りは `DS→P` の出辺で既に表現されているため、読み取り PRS を足すと**読み取り経路が P 系と PRS 系で二重に表現される**懸念がある。

## 推奨（決定ではない・決定はオーナー）

現時点では **①** にやや分があると考える。根拠は (a) 両 DS の書き込み主体が系外アクター（ACTOR-1）であり系内に永続化実装が存在しない＝規則の前提が成り立たない、(b) 読み取り経路は既に `DS→P` の出辺で表現済みで、PRS を足すと表現が二重化する、(c) PRS の単一責務（永続化＝書き込み）を保てる、の 3 点。ただし ② には「実在する読み取り実装が設計層に現れる」という無視できない利点があり、PRS 型を「永続層アクセス」と定義し直したうえで `DS→P` 側の表現と役割分担を整理すれば一貫した解にもなり得る。

**本 Q は推奨提示に留め、決定はオーナーに委ねる。**どちらを採っても `config.yml` の機械判定（規則の適用条件、または型の意味）に変更が入るため、決定は DD へ昇格させて記録すること。

**付記（決定後の伝播）**: 本 Q 自体は接続規則を変更しないため、著作資産への同期は**現時点では不要**（同期不要と判断した根拠＝規則変更を伴わない未決論点の起票にすぎない）。ただし ①② いずれで決着しても DD 反映時に接続規則（`must_be_linked_from` の適用条件、または PRS 型の意味）が変わるため、その時点で `docs/doc-system/03-connection-matrix.md`・`docs/doc-system/01-document-items.md`・`design-author`（PRS/DS 担当）・`verification-author` 等への同期チェックが必要になる（FND-99 パターン）。
