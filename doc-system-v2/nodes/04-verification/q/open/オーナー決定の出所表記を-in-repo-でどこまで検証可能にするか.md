**論点（1文）**: ノード本文・改訂履歴・ダッシュボードに恒久記録される「**オーナー判断（YYYY-MM-DD）**」という出所表記について、その指示が実在したことを**リポジトリ内から検証できる形にすべきか**、するならどこまで（外部参照の併記を必須化する／記録形式を規定する／現状のまま自己申告に留める）を決める。

**起票元**: PR #326 のレビュー指摘（R-07）。本 PR は 3 箇所（既存 FND の改訂履歴 v0.2.1／新規 FND 本文／`00-dashboard.md`）に「オーナー判断（2026-08-04）」という出所表記を恒久記録するが、**その指示の実在をリポジトリ内から検証する手段が無い**（根拠はチャットと `.gitignore` 済みのハンドオフのみ）。決定の**内容**は DD `FND 起票単位は機序で分け対象集合が同型の指摘は既存 FND のスコープ拡張とする` として在グラフ化したが、**出所の検証可能性**はそれでは解消しない（DD を書いても「その決定がオーナー由来である」ことは依然として自己申告のままである）ため、残余の論点として本 Q を起票する。**「記録不要」とは判断していない。**

---

## 1. 何が問題で、何が原理的に不可能か

**チャットでのオーナー指示は系外事象である**（PR3）。システム（doc_system の著作パイプライン）を介さずに発生し、顛末をシステムが観測できない（PR4）。したがって：

- **「オーナーがそう言った」ことの証明は、in-repo では原理的に達成できない**。リポジトリに書けるのはすべて AI か人間がキーボードから入力した文字列であり、その出所を repo 自身が保証する手段は無い（コミット署名は「誰がコミットしたか」を示すが、「誰が判断したか」は示さない）。
- **可能なのは「区別できるようにする」ことである**。すなわち①外部に検証可能な痕跡がある決定（GitHub Issue / PR コメント / コミットメッセージ）と、②チャットのみで下された決定（痕跡なし）とを、記録上**取り違えられない形**にする。読み手が「これは追跡できる／できない」を判断できれば、誤った信頼は生じない。

本 Q が問うているのは①と②の**書き分けをどこまで制度化するか**であって、証明手段の発明ではない。

## 3. 選択肢

1. **現状維持（出所表記は自己申告のまま）** — コストゼロ。既存 131 件超の FND・DD の記録様式も変えなくてよい。反面、「オーナー判断」と書かれた記録と AI の暫定決定とが**同じ字面で並ぶ**ため、後から重み付けを誤る余地が残る。とくに DD は「暫定決定」（設計フェーズで AI が推奨案を採る）とオーナー確定が混在する型なので、区別が効かないと影響が大きい。
2. **外部参照（Issue / PR コメント）の併記を必須化する** — 「オーナー判断」と書くときは、その指示が残っている外部 URL（Issue 番号・PR コメント）を必ず併記し、無ければオーナーに Issue 化を依頼してから記録する。検証可能性は最も高い。反面、**チャットで即断される軽い判断（本件のような起票単位の決定）まで Issue 化を強いる**とオーナーの手を煩わせ、起票のリードタイムが伸びる。「一々聞くな」というオーナー方針（CLAUDE.md スケジュール節・違反事例②）と緊張する。
3. **記録形式を規定する（根拠の所在を必須項目にし、「チャットのみ」を明示的に列挙可能にする）** — 出所表記を `**決定**: オーナー / 2026-08-04 / 根拠: チャット（in-repo 痕跡なし）` のように、**日付・決定者・根拠の所在**の 3 点を定型で書く。根拠が外部にあるなら URL を、無いなら「チャット（in-repo 痕跡なし）」と**明示的に書く**。検証可能性そのものは上がらないが、**検証できないことが記録の上で可視になる**ため、読み手が誤った信頼を置かなくなる。コストは著作時の 1 行のみ。
4. **出所表記を弱める（「オーナー判断」と書かず、決定内容だけを記録する）** — 検証できないことを書かなければ誤読も生じない、という考え方。反面、**AI が独断で決めたのかオーナーが決めたのかが区別できなくなり**、CLAUDE.md が繰り返し禁じている「AI の独断」を後から検出できなくなる。PR8（消さない）にも逆行する。**非推奨**。

## 4. 推奨

**選択肢 3 を基軸とし、重要な決定に限って選択肢 2 を併用する。遡及適用はせず、以後の記録にのみ適用する。** 根拠は 4 点。

- (a) **達成可能な目標に合わせる**（§1）。証明が原理的に不可能である以上、機構が目指すべきは「区別できること」であり、選択肢 3 はそれを最小コストで直接達成する。選択肢 2 は検証可能性を上げるが、達成できるのは一部の決定に限られる（チャット即断を全部 Issue にはできない）ので、単独では基準になりえない。
- (b) **オーナーの確認コストを増やさない**。選択肢 3 は著作側の記法の話であり、オーナーに新たな作業を求めない。選択肢 2 を全件必須にすると「一々聞くな」というオーナー方針と正面から衝突する。
- (c) **「重要な決定」の線引きは既存の区分を流用できる**——影響が複数ノード・複数スプリントに及ぶ決定（型の接続規則の変更、スプリントの繰り越し、スコープの確定）は Issue または PR コメントに痕跡を残す。今回の起票単位の決定のような**単一バッチ内で完結する判断**はチャット明示で足りる。この線引き自体もオーナーに確認したい。
- (d) **遡及しない理由**: 既存記録を書き換えると、その記録が「いつ・どの様式で書かれたか」という provenance を壊す（PR8・DD-3 が凍結記録を書き換えない方針を採っているのと同じ理由）。既存分は「旧様式＝根拠の所在の記載なし」として読めばよく、新様式との差自体が時期の情報になる。ただし**遡及の要否もオーナー判断**であり、遡及すべきとの判断であれば対象は「オーナー判断」の語を含む既存ノード（実測が必要）となる。

## 5. 決定に必要な確認事項（オーナーへ）

1. 選択肢 3 の記録形式を採るか（採る場合、書式は上記の 3 点定型でよいか）。
2. 選択肢 2 を併用する「重要な決定」の線引きを、上記 (c) の案でよいか。
3. 既存記録への遡及適用を行うか（推奨は行わない）。
