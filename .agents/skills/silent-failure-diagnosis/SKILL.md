# 静かな失敗の診断（外部プロセスが「動いているのに間違っている」とき）

対象は **外部プロセス**＝委譲先 CLI/MCP エージェント・フック・CI ジョブ・外部サービス。
これらは**落ちてくれない**。成功終了コードと、もっともらしい応答を返しながら、
入力を読んでいない／古いバイナリで動いている／そもそも発火していないことがある。

**最悪の失敗はエラーではなく、自信のある誤答。** エラーは気付ける。誤答は気付けない。
以下は、その気付けない失敗を切り分けるための観測規律。

## ⚠️ 適用範囲（「冗長な実証確認の禁止」との境界）

再現確認・実測を求めるのは**外部プロセスのランタイム挙動に限る**。以下は再検証しない：

| 対象 | 扱い |
|---|---|
| **権威ある静的な主張**（公式ドキュメント・`claude-code-guide` の結論・spec・確定した設計判断） | **再検証しない**。読んで信頼する |
| **外部プロセスのランタイム挙動**（委譲先の応答内容・診断コマンドの総合判定・ローカルバイナリの版・フックの発火有無） | **観測でしか分からず、しかも黙って誤る**ので実測・再現する |

前者を実証で確かめ直すのはトークンの浪費。後者を文書で済ませるのは事故。**混ぜない。**

## D0. まず hard block を確認する（他のどれより先）

**安全側のゲートは診断より先。** 「本当に壊れているのか」を調べ始める前に、
**止まるべくして止まっている**のではないかを確認する。

- **required CI・セキュリティ判定・runbook の停止条件**に該当していないか。
  該当するならそれは誤動作ではなく**正しい拒否**で、迂回してはならない。
- 権限不足・認証切れ・環境非対応（クラウド/ヘッドレス等）も同じ。**先に潰す**。

**D0 に該当したら、D1〜D8 の"新規プローブ"を一切行わない。** 再実行・dry-run・staging での再現・
別経路での試行はすべて禁止（それらは形を変えた迂回になる）。許されるのは
**すでに存在する証拠を読むこと**（ログ・既存の実行記録）と、**停止して報告すること**だけ。
D1 のアンカー取得も「新たに対象へ問い合わせる」なら禁止で、既存の応答から確認できる場合に限る。

> **例外を認める場合は、条件を明文化してから認める。** 「これは実質セーフだから」で個別に緩めない。
> 現在明文化されている唯一の例外は `/codex-review` の rollout 回収で、**オーナー確定（2026-07-28）**：
> **アクセス制御の突破ではなく、自分のマシンに既に書かれた自セッションのログを読む行為**であるため
> 迂回に当たらないと判断した。ただし**自分の `thread_id` に束縛された1ファイルに限る**という条件付き
> （詳細＝`.claude/skills/codex-review/SKILL.md`）。他セッションの探索は例外に含まれない。

## D1. 出力を評価する前に、入力を読んだかを確かめる

外部プロセスの回答の**正しさ**を吟味する前に、**前提**を確かめる。
「そもそも渡したはずの対象を見たのか？」

- **検証可能なアンカーを一緒に取らせる**。ただし**何をアンカーにするかを選ぶ**：
  - 良い：**非機密の nonce/digest**（ファイルの行数・ハッシュ、run ID、コミット SHA、公開シンボル名）。
  - 🛑 **期待値をプロンプトに書いて「これと一致するか」と聞かない。** 対象を読まなくても
    そのまま echo すれば一致してしまい、照合が原理的に成立しない。**期待値は手元にだけ持ち**、
    相手には「その事実を答えよ」とだけ言って、**返ってきた値をこちらで突き合わせる**。
  - **答えられなかった・検証できなかった場合も不一致として扱う**（fail-close）。「たぶん見ている」で通さない。
  - 避ける：**ファイル本文・引用の丸ごと返却**。外部サービスへ内容を送り返させることになり、
    秘密・個人情報が応答やログに残る。**必要最小限の事実だけ照合する。**
- **一致しなければ、それ以降の回答をすべて破棄する。** 部分的に正しく見えても信用しない
  （見ていない相手が偶然それらしいことを言うのは普通に起きる）。
- 対象別の確認先：**委譲エージェント**＝回答内のアンカー／**フック**＝トレースログの発火記録／
  **CI**＝実行 ID とジョブログ／**CLI**＝実行されたコマンドと cwd。

## D2. 総合判定（status）を鵜呑みにしない

`Overall: OK` / `PROBLEMS FOUND` のような**集約された判定は、あなたの用途に対する可否ではない**。

- **偽陽性**：NG と出ているが実は使える（診断項目が本筋と無関係なことがある）。
  一律停止すると、生きている経路まで塞ぐ。
- **偽陰性（より危険）**：OK と出ているが**あなたが必要とする条件を検査していない**。
  status が見ていない前提こそが壊れている、という形が起こる。

→ **status の項目が何を検査しているかを読む**。自分の用途に必要な条件が項目に無ければ、
その条件は**自分で確かめる**（D1）。総合判定は情報として扱い、ゲート条件にしない。

> ⚠️ **これは「ゲートを無視してよい」ではない**。ここで言う総合判定とは、
> **診断コマンドが複数項目を丸めた heuristic な要約**のこと。**D0 の hard block**
> （required CI・セキュリティ判定・runbook の停止条件）は対象外で、**常に優先する**。

## D3. 単発の結果から因果を断定しない

1回の失敗は「その経路が壊れている」ことを意味しない。

- **失敗した経路は最低2回**試す。再現しなければ「再現せず」と正直に書く。
- **1回に1因子だけ変える**。複数変えた比較は因果を特定できない。
- 失敗のエラーメッセージが**別の既知事象と同じ文言**なら、切り分けできていない可能性を疑う。

> ⚠️ **無条件に再実行してよいのは「read-only・冪等・低コスト」な経路だけ。** 次に当たるなら再実行しない：
> **副作用がある**（書き込み・デプロイ・通知・課金・外部への送信）／**クォータや従量課金を消費する**／
> **D0 の hard block に該当している**。その場合は **既存ログ（D5）で代替**し、それでも実再現が要るなら**オーナーの認可を取る**。
> **D0 に該当しているときは dry-run も staging も使わない**（新規プローブは全面禁止）。
> **試行上限を先に決める**（例：2回で再現しなければ「再現せず」として次の手順へ）。無限に叩かない。

## D4. 比較しているものが同一か確かめる（版・更新時刻）

「さっきは動いたのに」の多くは、**比較対象が入れ替わっている**。

- 外部ツールは**調査中に自動更新される**。実際に、プローブ1回目と2回目の間に対象 CLI が
  自動更新され、異なるバイナリを比較していた事例がある。
- バイナリの版・設定ファイルの mtime・ログのタイムスタンプを確認してから比較する。
- 版が変わっていたら、**変更履歴（CHANGELOG・コミットログ）でその版の変更点を読む**。

## D5. 永続ログ・履歴を当たる（時系列が真因を絞る）

ライブのプローブより、**すでに書かれているもの**が強い証拠になることが多い。

- ツール自身のログ、会話履歴、状態 DB、トレースログ。
- 探すのは**回帰の境界日**。「いつから壊れたか」が分かれば、その時期の変更（自動更新・
  設定変更・仕様変更）に候補が絞れる。
- 「**以前は動いていた**」の証拠が出れば、「原理的に無理」という誤った結論を潰せる。

> **探索範囲を絞る**：run ID・時刻・対象 workspace で**当該実行に関係する範囲だけ**を見る。
> 会話履歴や状態 DB には他タスクの内容や秘密が入りうる。**無関係なログを読み漁らない**。
> 読み取った秘密・個人情報を**報告やコミットに転記しない**（必要なら存在の事実だけ書く）。

## D6. 本番で使われている経路を特定してから直す

同じツールに複数の起動経路があると、**直した先が使われていない**ことがある。

- 設定ファイルを読んで、**実際に何が起動されるか**を確認する（パッケージ版か・ローカル
  クローンか・ラッパースクリプト経由か）。
- **設定ファイルだけで確定させない**。可能なら実行側の証拠まで取る：解決済みの実行ファイルパス・
  親プロセス／CI なら workflow の SHA と実行 ID／フックなら登録状況とトレース／サービスなら起動ログ。
  設定と実挙動がずれているのが、まさに疑っている事象。
- ⚠️ **argv・effective config・環境変数を生のまま収集・転記しない**。token / API キー / 接続文字列が
  そのまま報告やコミットに残る。必要なのは**値ではなく事実**なので、
  「どのフラグが付いていたか」「どの設定ファイルが効いたか」といった**秘匿済みの型・出所・安全な識別子**
  だけを記録する（値は `<redacted>` とする）。
- 「たぶんこれだろう」で直すと、変更が無反映のまま「直らない」と誤診する。

## D7. upstream の「修正」が自分の要件を満たすとは限らない

既知の不具合に upstream の修正があっても、**それが何をするかを読む**。

- 実例：ある権限まわりの不具合に対する upstream の修正は、**権限ゲートを無条件で全開放**
  するものだった。不具合は消えるが、要件（最小権限）は満たさない。
- 修正の**副作用**と、自分が本当に必要としている範囲を突き合わせる。

## D8. 目的を最小権限で達する解を選ぶ

「動かすための最短手」は、たいてい**必要以上の権限**を要求する。

- まず「自分の用途に必要な最小の許可は何か」を言語化する。
- 全開放（サンドボックス無効化・全許可フラグ）で解決する前に、**限定的な宣言で足りないか**を試す。
- 権限を広げる判断は**オーナーに委ねる**（AI が独断で危険フラグを有効化しない）。

## 診断の順序（迷ったらこの順）

0. **D0** hard block に該当していないか（**最優先**。正しい拒否を迂回しない）
1. **D1** 入力を読んだか（ここで潰れることが多い・最も安い）
2. **D6** 本番経路はどれか（直す先の特定）
3. **D5** ログの時系列（回帰の境界）
4. **D4** 版・更新時刻（比較対象の同一性）
5. **D3** 再現（因果の確定・**read-only/冪等なら**）
6. **D2** status の項目読み（ゲート条件の見直し）
7. **D7/D8** 対策の選択（副作用と権限）

## 出力（done の条件）

診断を終えたら、次の3点を揃えて報告する。**「たぶん〜だと思う」で終えない。**

1. **原因**：特定できたなら根拠（証拠のパス・行・ログの実行 ID）付きで。**特定できなければ
   「未特定＋絞り込めた範囲＋残る候補」**と正直に書く。
2. **検証マトリクス**：試した条件ごとに `条件 | 試行回数 | 結果 | 実際に使われた値 | 判定`。
   再現しなかったものは「再現せず」と明記する。
3. **対策の選択肢と推奨**：効果・コスト・副作用（特に**権限の広がり**）を併記し、推奨を1つ示す。
   権限を広げる案・課金を伴う案は**独断で採らず**オーナー判断を仰ぐ（PR7）。
