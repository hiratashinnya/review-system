# issue-pipeline 再設計 — 決定台帳（2026-09-21〜）

オーナーとの検討で確定した事項を、**生きている決定（§A）と訂正・置換された決定（§B）に分けて**記録する。
根拠となる実測は §C、未決事項は §D、機械強制を将来へ持ち越した検査項目は §E。

**読み方**

- **§A が現行の正**。ここに載っている内容だけが有効な前提である。
- **§B は無効**。残すのは経緯を再構成するためであって、参照して行動してはならない
  （`.claude/rules/01-principles.md`「PR8「消さない」の適用範囲」区分1＝経緯は保全する）。
- §A と §B は**相互ポインタ**で結ぶ。§A の各項は「何を置換したか」、§B の各項は「何に置換されたか」を持つ。
- **`オーナー逐語` は逐語であり、AI の解釈を混ぜない**（`feedback_ledger` の L4 と同じ規律）。
  解釈は `AI の原案と、オーナーが変えた点` に分けて書く。

記載するのは**決定とその根拠**であって、処置計画・実施予定ではない（それは Issue で管理する
＝`audit/README.md` の「置く / 置かない」）。

| 項目 | 規則 |
|---|---|
| **id の形** | `FBK-<YYYYMMDD>-<slug>`（`feedback_ledger` の `LEDGER_ID_RE` と同形） |
| **slug の作り方** | `doc-system-v2/slugify.py`（唯一実装）で `トピック` を正規化したもの。独自に正規化しない |
| **トピック** | **30字以内で「何を決めたか」を述語まで書く**（例：`リポジトリの目的は…とする`）。論点名ではない |
| **id は不変** | **訂正・置換されても id は変えない。**§A→§B の移動は `置換` ポインタからの導出であって、id の意味ではない |

**決定内容**

```
minimize   C（コスト）, D（リードタイム）
subject to Q >= 閾値      ← 下げられない下限。ここを削って C/D を稼ぐことは禁止
```

**学習の成果 ＝「Q の下限を割らずに、C と D をどこまで下げられたか」。**

**経緯（周辺文脈）**

オーナーが「ハーネスによって QCD を最大化できているか」を測定軸として提示した。
QCD は同時最大化できない（トレードオフ関係にある）ため、AI が「転用先が車載 ECU である以上、
Q は最大化の対象ではなく制約である」として制約付き最適化の形に直した。

この形により2つが同時に排除される——**(a) Q を上限なく追求して C/D を犠牲にする**（点検時点の状態。
制約であるべきものを目的関数にしている）／**(b) Q を落として C を下げる**（そのノウハウは転用先で
使えないため学習成果にならない）。

**オーナー逐語**

> が、学習の成果をどう測る？個人的にはハーネスによってQCDを最大化出来ているか？を測るのがよいと思う。

> 定式化はそれでよい。

**AI の原案と、オーナーが変えた点**

オーナー原案「QCD を最大化」に対し、AI が「Q は制約、C/D が目的関数」へ定式化し直し、オーナーが承認した。

$ ls -R .ai/feedback

```

**#522 で 2,364行＋schema 3本＋テスト792行を実装したのに、台帳は1件も入っていない。**
これは2つの意味を持つ——(a) L6（immutability）が保護すべき既存エントリが無いため、**今ならスキーマを
壊さずに直せる**。(b) **#521 の完了条件「台帳エントリが1件以上、CLI 経由で実際に記録されている
（運用が回ることの実測）」が未達**であり、本議論の決定を投入すればそれが最初の実データになる。

そして**実装済みで1件も使われていない 2,364行は、[必須施策を5項目に定める](#fbk-20260921-必須施策を5項目に定める) の④（YAGNI）の実例そのもの**である。
ここに2つ目の決定台帳を建てれば、④に自ら違反することになる。

**`source` を複数許容にする理由（[決定台帳のsource.issueをoptional化する](#fbk-20260921-決定台帳のsource.issueをoptional化する) からの変更）**

`source.issue` を optional 化する案は、**「紐づけをサボったエントリが通る」ことを許す**変更だった。
複数許容なら `required_nonempty=True` を維持したまま、紐づけの強制を落とさずに済む。

実装方式は2案あり、**repeated table 化（案 ii）を採る**。

| | 案 | 評価 |
|---|---|---|
| i | `source.issue` → `source.issues`（INT のリスト） | 軽いが、`issues=[371,445]` のとき **`pr`/`round` がどちらの Issue のものか表現できない** |
| **ii** | **`source` を repeated table 化（`[[source]]`・`min_items=1`）** | **各要素が `(issue, pr, round, finding_ids)` の1組。対応関係が保たれる** |

ii を採る理由は3点——(a) 原則（null 許容より複数許容）を `issue` 単独ではなく**出所のまとまり全体**へ
一貫して適用できる、(b) #523 が同じ台帳へパイプライン内の捕捉（issue + pr + round + finding_ids が揃う）を
入れてくるため、設計決定（issue のみ）と同居する以上ここで正規化しておく必要がある、
(c) `min_items=1` を実装すれば「1件以上の出所が必須」が機械強制になる。

## §E Jev（判定専用 AI）へ持ち越す検査項目

> [トピックの述語は機械強制しない](#fbk-20260922-トピックの述語は機械強制しない) で「今は強制しない」と
> 決めた項目の置き場。**「対応不要」ではなく、強制する機構が来るまでの保留である。**
>
> **⚠ §E-2 以降は AI の提案であり、オーナーの判断を受けていない。**

### Jev とは何か（2026-09-22 時点の調査結果）

**TypeSafe AI の「System One モデル」。文章を生成せず、型付きの判定だけを返す。** LLM ではない。
2026-09-15 に限定早期アクセス開始（DCVC リードの $40M シードと同時発表）。

| 項目 | 内容 |
|---|---|
| **入力** | `state`（文字列 / JSON / テキスト配列）＋ `questions`（型付きの問い。複数可） |
| **出力** | 型付きの値＋**較正済み確率**＋confidence。**スキーマ外の値を返せない**（型エラーが原理的に起きない） |
| **問いの型** | `Choice`（選択肢から1つ・各選択肢の確率＋confidence）／`Score`（順序付きレベルで採点・各レベルの確率＋confidence）／`Noul`（yes/no 命題の確率 0〜1） |
| **サンプリング** | **非自己回帰・並列**。全ての問いを1パスで同時評価 |
| **学習** | RLCD（Reinforcement Learning for Calibrated Decisions）。合成データのみ。アーキテクチャ・重み・論文は非公開 |
| **速度** | end-to-end 70〜500ms |
| **価格** | **入力 $0.042 / 1M tokens。出力は無料** |
| **不得意** | 文章生成・計算・日付比較 |

リクエストの形（LangChain のガイドより）：

```json
{
  "model": "jev-latest",
  "state": "<判定対象のテキストや構造化状態>",
  "questions": {
    "is_urgent": { "type": "noul", "instructions": "The message conveys urgency or time-sensitivity" }
  }
}
```

```json
{ "is_urgent": { "type": "noul", "noul": 0.999 } }
```

**性能主張には留保が要る**——40〜200倍高速・40〜400倍安価（ピーク 193.6倍 / 444.6倍）という数字は
TypeSafe 自身のモデル能力チームが作ったワークフローでの自社計測であり、同社自身が偏りの可能性と
「実世界の結果は上振れ側の数字より低いだろう」ことを認めている。**採用判断は自前の観測窓で測る**
（[施策ごとに観測窓を切る](#fbk-20260921-施策ごとに観測窓を切る)）。

### なぜこのリポジトリの課題に合うのか

§C-2 の実測では、**記録済み再発欠陥21件のうち14件（67%）がゲート・隔離・権限といった列挙型の機構を
発生源**としていた。列挙型ゲートが壊れる理由は構造的で、「危険な語のリスト」「許可コマンドのリスト」を
人が保守し続けなければならず、**リストの外側は素通りし、リストの内側の誤検知は運用を止める**。

Jev は**リストではなく命題の確率**を返すので、この保守対象そのものが消える。加えて confidence が
返るため、**低 confidence をオーナーへエスカレーションする**という第三の出口を作れる
（現在の機械ゲートは deny か allow の二択しかない）。これは [Issue513のescalate機械強制は必須とする](#fbk-20260921-issue513のescalate機械強制は必須とする)
の escalate 経路と直接つながる。

**本セッション中に実測した具体例**：`pr_merge_gate` の classifier が、read-only の
`ls` / `cat` / `python3 <script>` を含む複合コマンドに対して `CLASSIFIER_UNKNOWN` と
`POST_AUDIT_INTEGRITY_ERROR/RECLASSIFIED_NOT_MERGE` を繰り返し発報し、作業を都度迂回させた
（Issue #533 として起票済み）。**「このコマンドは merge 操作か」は文字列照合ではなく判定の問題**であり、
Jev の `Noul` がそのまま当たる形をしている。LangChain が公開した `AutoModeMiddleware` は、
まさにこのツール呼び出しリスク判定を Jev で行う実装例である。

### §E-1 決定台帳の検査（持ち越し確定）

| # | 検査したいこと | 今どうなっているか | Jev の型 |
|---|---|---|---|
| J-1 | **トピックが「何を決めたか」を述語まで書いているか** | 未検査（本決定で保留） | `Noul` |
| J-2 | **トピックと決定内容が一致しているか**（トピックが本文と違うことを言っていない） | 未検査 | `Noul` |
| J-3 | **`narrative.owner_verbatim` が本当に逐語か**（AI の解釈が混入していない） | **L4 が推測語彙の列挙で代用** | `Noul`＝**置換候補** |
| J-4 | **`narrative.inferred_reason` の `推測：` が実際に推測か** | **L5 が断定語彙の列挙で代用** | `Choice`（推測 / 断定 / 混在）＝**置換候補** |
| J-5 | **`narrative.background` が経緯として成立しているか**（決定内容の再掲で埋めていない） | 未検査 | `Score` |
| J-6 | **生存する決定どうしが実質的に矛盾していないか**（`supersedes` の張り忘れ） | 未検査。**id が日付＋内容由来なので、張り忘れても衝突せず素通りする** | `Noul`（生存ペアの総当たり） |
| J-7 | **`affected_assets` に過不足がないか** | L3 が**参照先の実在**のみ検査（在るものが正しいかは見ない） | `Noul` |

**J-6 は新 id 体系が持ち込んだ穴である。** 旧 `D-0xx`/`D-1xx` は「§B へ物理的に移す」という操作自体が
訂正の証跡だったが、新体系では `supersedes` を書かない限り古い決定が §A に残り続ける。
id 規則では原理的に検出できない。生存 n 件の総当たりは O(n²) だが、n=17・1ペア数百トークンなら
1パス数円に収まらない額にすらならない（後述のコスト試算）。

### §E-2 ハーネス全体の列挙型ゲート置換候補（**AI 提案・未決**）

§C-2 で再発欠陥の発生源と特定された機構のうち、判定の性質が Jev に合うもの。

| # | 対象 | 現在の実装 | Jev の型 |
|---|---|---|---|
| J-8 | **コマンドが merge / push 操作か**（`pr_merge_gate`・`agent-command-gate.sh`） | シェル文字列の静的照合。複合コマンド・heredoc・ループで誤判定（#533） | `Noul` |
| J-9 | **finding の `harm` が real か none か**（`pr-reviewer`） | AI の自己申告。機械検査なし | `Choice` |
| J-10 | **finding が `scope: in` か `out` か**（Issue #495） | AI の自己申告。機械検査なし | `Noul` |
| J-11 | **規範の写し（`governance-directives.md`）が正本と意味的に一致するか** | `check-governance-drift.sh` は**ハッシュ一致のみ**＝意味のズレは見ない | `Noul` |

**J-11 は不変条件型の検査が既に効いている領域なので、優先度は低い**（§C-2 でハッシュ一致型は再発ゼロ）。
逆に **J-8 は再発欠陥の最大の発生源そのものなので、費用対効果が最も高い**と見ている。

### 採用前に片付ける必要がある前提

1. **課金の認可が要る**（`.claude/rules/03-operational.md`「CI/外部サービス連携のコスト方針」）。
   現在の機械検査は全て標準ライブラリのみ・オフラインで動く。Jev は外部 API であり**無課金では実現できない**。
   - **コスト試算**：台帳全21件の1パス検査で state ≈ 3万トークン → **$0.0013**。
     PR ごとのコマンド判定で 1万トークン → **$0.0004**。出力は無料。
     月間の実行回数を多めに見ても**月額は1ドルに届かない**見込み。
   - ただし**金額の多寡に関わらず、実装前にオーナーの明示認可が必要**（規範6）。
2. **CI からネットワークと API キーが要る。** GitHub Actions secrets への登録と、
   **キーが無い環境での挙動**（fail-open か fail-close か）を決める必要がある。
   現在の検査は全てオフラインで完結しているので、これは設計上の性質変化にあたる。
3. **確率をどう判定に落とすか。** Jev は真偽ではなく確率と confidence を返すので閾値が要る。
   列挙型リストの保守は消えるが、**閾値というパラメータが1つ増える**——ただし保守対象は
   「育ち続けるリスト」から「1つのスカラ」に変わるので、§C-2 の再発パターンには乗りにくい。
   低 confidence は deny/allow のどちらでもなく**オーナーへエスカレーション**する設計を推奨する。
4. **限定早期アクセスである。** 2026-09-15 開始で、可用性・レート制限・価格の安定性はまだ実績が無い。
   **撤退条件を持たせる**（[施策ごとに観測窓を切る](#fbk-20260921-施策ごとに観測窓を切る)）。
5. **判定の証跡を残す。** 確率値と confidence をカルテ／台帳に記録しないと、
   「なぜ止まったか／なぜ通ったか」が後から再構成できず、
   [撤退条件をA/B/Cの3種で定める](#fbk-20260921-撤退条件をa-b-cの3種で定める) の条件C（因果が特定できないなら撤退）に抵触する。
