# Issue 全数調査（2026-09-21）— このリポジトリの長所と短所

Claude Code (AI) が実施・作成した。オーナーの指摘により**長所の一部を訂正済み**（後述「訂正」）。

## 1. 目的と範囲

- **対象**：`hiratashinnya/review-system` の GitHub Issue **全 274 件**（open 75 / closed 199）。
  採番は #1〜#535（欠番はすべて PR 番号）。リポジトリ開始 2026-06-03 〜 調査日 2026-09-21（約 3.5 か月）。
- **問い**：この開発体制の長所と短所は何か。
- **対象外**：PR 本体のレビュー内容、`doc-system-v2` のノードグラフの内容妥当性。

## 2. 方法

番号帯で5分割し、5つの調査エージェントへ並列委譲した。番号帯＝ほぼ時系列なので、帯ごとの差が
そのまま体制の変化を示す。全エージェントに**同一の分類軸**を一時ファイルで渡し、帯をまたいだ
集計が突き合うようにした。

| 抽出項目 | 意味 |
|---|---|
| `origin` | どう見つかったか（`design` / `review` / `post-merge` / `incident` / `plan` / `external`） |
| `root_cause_slug` | 何が壊れていたか（kebab-case・帯内で語彙を統一） |
| `resolution` | どう終わったか（`implemented` / `duplicate` / `merged-into` / `rejected` / `stale` / `open`） |
| `mechanized` | 処置が**機械検査・ゲート・テスト**を伴ったか（`yes` / `no` / `partial`） |
| `recurrence_of` / `spawned` | 本文が明示する再発元・派生先 |
| `author_kind` | 本文の attribution で判定した**起票者**（**発見者ではない**。§7 参照） |
| `days_open` | 作成〜クローズ（open は調査日まで）の日数 |

**推測での補完は禁止**し、本文に書かれていない項目は `unknown` とした。
5帯の合計は 49+45+54+60+66＝**274** で母数と一致（open 3+9+27+16+20＝75）。取りこぼしは無い。

一次データは [`data/`](data/) に置いた（274行×12列の分類表と、指標ツールの出力スナップショット）。

## 4. 長所

### ① 自分の失敗率を数値で持っている

`defect_metrics` という計測器を自作し、派生 Issue 率の推移（§3）を実測できる。「良くなった気がする」
ではなく指標で言える。open の純増が +50 → +6 に収束したことも同じ計測で確認できる。

### ② レビューが主要な検出経路として機能している

`review` 起因 94 件に対し `post-merge`（すり抜け）25 件で、**約 3.8 : 1**。欠陥の大半は merge 前に
捕まっている。加えて「merge 後に判明した」という不名誉な事実を **9% も自己申告して記録に残している**
——通常は区別すらされない情報である。

### ③ オーナーの判断を、規範と機械検査まで落とし切る変換能力

オーナーが下した判断が、Issue → 規範テキスト → **機械検査**まで一貫して落ちている。

- `time_fixture_lint`（時刻依存 fixture の機械検査・#302/#339 の再発を受けて）
- `blocker_gate` / `issue_start` / `pr_merge_gate`（#293〜#299 の計画的プログラムで到達）
- `agent-command-gate` のホワイトリスト方式（#227）
- `karte` の verdict ゲート（実害ありで処置方針が未決なら clean にしない）

**この長所は「変換」であって「発見」ではない**（§5-④・§7 参照）。

### ④ 決定の経緯が失われない構造

却下案・決定履歴は `rationale` へ、現行手順は本文書き換え、という区分（`.claude/rules/01-principles.md`
「PR8「消さない」の適用範囲」）が明文化され、実際に archive 化・移設が行われている。
本記録の §8「訂正」もこの規律に従っている。

## 5. 短所

### ① 処置の半分が散文で終わっている（最大の構造的弱点）

判定できた 237 件のうち **`mechanized: no` が 121 件（51%）**。規範を足して終わり、が多数派である。
そして **`contract-vs-mechanism-mismatch`（契約は書いてあるが機械が強制していない）それ自体が
全帯に現れる頻出 root cause**（#103・#107・#181・#534 ほか）。つまり次の自己供給的なループがある。

> 散文で処置する → 契約と実装が乖離する → その乖離が新しい Issue になる → また散文で処置する

帯別に見ると #201-300 が最悪（yes 13 : no 40）で、直近 #401-535 は改善している（yes 30 : no 15）。

### ② 再発が「同型の別箇所」として繰り返される

帯をまたいで再構成した最長チェーンは **#350 → #354 → #426 → #502（4世代・worktree/ブランチ残留）**。
ほかに #412→#428→#430/#431、**#495→#503/#511/#513**、#386→#535、#302→#339、#355→#378、#356→#385。
形はすべて同じ——**locus を1つ直す → 同型の別箇所が残る → 次ラウンドで出る**。

**横睨み（同一クラスの全掃引）が処置の既定手順になっていない。** 調査中に実施した Issue #531 でも
同じ形で4ラウンド要した（F-531-01 → 06 → 07 → 08/09）。

### ③ 止まっているのは「本体」、回っているのは「機構」

60日以上 open の 15 件の内訳。

| 領域 | 件数 | 滞留 |
|---|---|---|
| review_system（製品本体：設計⇔実装ドリフト・テスト3点セット・UI 判断） | 3（#5/#7/#11） | **各104日** |
| doc_system（構築・materialize・PF 同期） | 9（#127/#128/#141/#154/#155/#160/#161/#162/#174） | 73〜76日 |
| Claude review MCP（非同期化） | 3（#217/#221/#229） | 69〜71日 |
| **Issue 運用ハーネス** | **0** | 最長 49日 |

**ハーネスの Issue は1件も長期滞留していない。** 規模でも製品 1,744 行 : ハーネス 32,233 行（18.5倍）。

### ④ 欠陥の検知がオーナーの介入に依存している

規範として永続化された主要な是正は、いずれも**オーナーが AI の挙動を捕まえて指示した**ことが
起点である（本文の一次引用は §8）。

| Issue | 起点 |
|---|---|
| #321（レートリミットを理由にした品質降格の禁止） | オーナー指示（2026-08-03） |
| #379（オーナー報告の握りつぶし防止） | オーナー明示（2026-08-16） |
| #357（PR8 の適用範囲の誤援用） | オーナー指示（2026-08-11） |
| #227（列挙方式 → ホワイトリスト方式への転換） | オーナーとの議論の結果・合意（2026-07-13） |

AI が担ったのは**記録と実装**であって**発見**ではない。`author_kind` は「誰が書いたか」しか
測っておらず（§7）、直近帯の「AI 起票 59/66」は AI が 59 件**発見した**証拠にはならない。
**オーナーが気づかなければ止まらない経路**が、現時点でどれだけ残っているかは本調査では測れていない。

### ⑤ 実体のない計画 Issue の滞留

#201-300 帯では `tracking-no-defect` が最頻 slug（8件）、open 27/54。**#329/#330 は本文が空のまま
46日 open**。計画 Issue が中身を持たないまま残っている。

## 6. 核心：長所と短所は同じ性質の裏表

> **自己言及性が品質を上げ、同時に目的を侵食している。**

doc_system は「仕様策定を支援するツール」なので、自分自身を題材にするのは設計上正しい。
しかし実測では **#301-400 帯の60件中、doc_system / review_system の本体を直接対象とする Issue は 0 件**
——全件がハーネス改修だった。ドッグフーディングが、**食べる対象を作り続ける作業に置き換わっている
期間**が実在する。

品質規律（レビュー 3.8:1、混入率 0.37、5回破られて土台を引き返す判断）は本物である。その規律が
**主に道具に向いていて、製品には 104 日届いていない**、というのが 274 件が示す姿である。

## 7. この調査の限界

- **`author_kind` は「起票者」であって「発見者」ではない。** 本調査で最も重い方法論上の限界。
  §5-④ のとおり、起票者が AI でも発見者はオーナーである例が主要な是正に集中している。
  **「誰が最初に気づいたか」を測る軸を持っていなかった。**
- **起票者の推移は、記録慣習の変化を部分的に見ている可能性がある。** 明示 attribution のあるものだけを
  AI 判定としたため、内容的に AI 主導と見られる #181-199 系列は attribution が無く owner に計上された。
  owner → AI のシフトは**実態より急に見えている**可能性がある。
- **再発チェーンは過小計上。** 本文が明示的に「再発」「同一 root cause」と書いたものだけを連結した
  （#1-100 と #101-200 は明示記述 0 件）。実際の再発はこれより多い。
- **#301-400 帯の起票者内訳は 53/60 しか合計が合わない**（7件不明）。全体比率への影響は小さいが、
  数字としては不正確である。
- **処置方針（何をすべきか）は本記録に含まない。** 調査・検討を詰めたうえで別途扱う（オーナー判断・2026-09-21）。

## 8. 訂正（2026-09-21・オーナー指摘により Claude Code (AI) が実施）

初稿では §4 の長所として「**いたちごっこを検知して土台を差し替えた**」「**AI が自分の失敗を規範に
変換するループ**」の2項を挙げ、**AI の自律的な発見であるかのように記述していた**。オーナーの指摘
（「AI が自力で見つけたのではなく、俺がブチギレて起票させたやつだ」）を受けて Issue 本文を確認した
ところ、**4件すべて発見と方針決定はオーナー側**であることが確認できた。

| Issue | 本文の記述（一次引用） |
|---|---|
| #321 | 「**オーナー指示（2026-08-03）により**絶対規範として永続化する」／オーナー逐語「無駄なことをして品質を下げるな」 |
| #379 | 「**オーナー明示・2026-08-16**」／オーナー原文「チャットに表示していない＝報告せず握りつぶしたのと同じ」 |
| #357 | 「**オーナー指示（2026-08-11）により**…」「**オーナーはこの認知コストを許容できないと明示した**」 |
| #227 | 「**オーナーとの議論の結果**、『列挙による検知』自体が構造的にいたちごっこを生むという診断に至り、根本的にアプローチを転換することで**合意**（2026-07-13）」 |

訂正内容は次のとおり。

1. 長所は「**発見**」ではなく「**オーナーの判断を規範と機械検査へ落とし切る変換能力**」と書き直した（§4-③）。
2. 「検出が AI の自己点検に依存」という短所を、「**欠陥の検知がオーナーの介入に依存している**」という
   より重い形へ書き直した（§5-④）。
3. 方法論上の限界として「`author_kind` は起票者であって発見者ではない」を明記した（§7）。

この誤りは単独の記述ミスではなく、**起票者の集計を発見者の集計として読み替えた**ことに起因する。
