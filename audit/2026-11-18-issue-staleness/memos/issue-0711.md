## 本文内の現状・前提・依存記述（要時点照合）
- > **2026-11-02 再設計（stacked PR の扱い）**：一度導入した「親 PR 更新→子・孫 PR の連鎖自動修復」は撤回する。未マージの親 PR は変更全体の品質が確定していないため、決定論的な生成物修復が可能でも、その状態を前提に子 PR を自動更新するべきではない。また親 PR の自動更新自体が子 PR の base を動かすため、**stacked PR に属する親・子・孫のすべてを自動書き込み対象から除外**する。stacked
- 1. **自動修復対象は単独 OPEN PR のみ**。同一リポジトリ内の PR で、`base.ref` がリポジトリの default branch（現状 `main`）であり、かつ当該 `head.ref` を `base.ref` として使用する別の OPEN PR が存在しないものに限る。
- 2. **stacked PR は自動修復対象外**。`base.ref` が default branch 以外の子 PR、別の OPEN PR の base として head を使われている親 PR、その組み合わせである中間 PR はすべてスキップする。多段・兄弟構成でも同様。手動 `workflow_dispatch` でも書き込みしない。
- 3. stacked の判定と関連 PR 番号は GitHub API の live OPEN PR から取得し、理由を Actions summary に報告する。自動 retarget、base 追従、親子連鎖は実装しない。人手での修復は既存 GitGate/Issue-pipeline 等の通常手順で行う。
- Git 自体の自動マージが成功しても、正本と生成物の hash が不整合になることがある。単独 PR の候補が自動修復条件を満たす場合に限り、再生成して検証する。全 OPEN PR に無条件に base を取り込む仕組みにはしない。修復不要なら commit/push しない。
- - GitHub API で同一リポジトリ内の OPEN PR を **ページングして全件取得**し、各 `base.repo` / `base.ref` / `head.repo` / `head.ref` と commit OID を確認する。default branch はリポジトリ情報から取得する。
-   1. 対象 PR が OPEN で fork ではなく、head が対象リポジトリ内に存在する。
-   3. 他の OPEN PR が対象 `head.ref` を `base.ref` にしていない。
-   4. 同じ head branch を共有する別の OPEN PR がなく、base/head 同名やブランチ消失等の曖昧さがない。
