## スケジュール独断禁止（再発防止・2026-06-14）
**FND/Q/DD で「次スプリント以降」「sprint-N 以降」等の実施スプリントを設定するとき、オーナー確認なしに独断で繰り越すことは厳禁。**

- **既定は現行スプリント。確認は不要**（2026-07-26 オーナー指示で明確化）：新規に起票する FND/Q/DD/PEND の `scheduled` は、**オーナーから明示的な繰り越し指示がない限り、常に現行スプリントを設定する**。起票のたびに実施時期を問い合わせてはならない（`scheduled: ""` は `validate.py` と `dsv2 index` の双方で fail-close するため、空のまま置くこともできない＝issue #152）。
- **禁止されているのは「繰り越しの独断」であって「現行スプリントの設定」ではない**：工数・優先度・実害の小ささを理由にスプリントを**後ろ倒し**する決定だけがオーナー判断であり、必ずオーナーの明示指示を得てから `scheduled: "sprint-N"`（N > 現行）を設定する。
- **「影響なし・実害ゼロ・後でよい」は独断根拠にならない**：自分が軽微と判断しても、スプリント計画はオーナーが決める。軽微と思うなら「今すぐ実施できる。ただし影響 X が小さいため sprint-N 繰り越しも選択肢」と提示して判断を委ねる。
- **違反事例①・繰り越しの独断**（2026-06-14）：FND-35・FND-37 を「現時点実害ゼロ」「推奨のみ起票」として独断で `scheduled: sprint-2` に設定し、DD-8 の `ref_version` 移行・フロントマター廃止も「sprint-2 以降」に繰り越した。オーナー指示により即時実施に変更（DD-8 全実施・FND-37 resolved・FND-35 はオーナー明示承認で sprint-2 確定）。
- **違反事例②・過剰な確認**（2026-07-26）：FND 8 件・Q 1 件を起票した際、`scheduled` を現行スプリントに設定した上で「実施スプリントはオーナー判断」と毎回報告に添え、判断を仰ぎ続けた。オーナーより「明示的な繰り越し指示をしない限り現行スプリントに設定せよ。一々聞くな」と指示され、本節を上記のとおり改訂。**独断禁止は繰り越しにのみ掛かる**。

## PR レビュー・GitHub コメント運用（明示・独断禁止）
- **Claude Code が実施したことを明示する**：PR でレビュー指摘への返信・コメントを投稿するときは、**AI（Claude Code）による対応であること**と、**実際に実施した処置（変更したファイル・コミット・判断の根拠）**をコメント本文に具体的に明記する。「誰が何をしたか」を後から取り違えないため、抽象的な要約だけで済ませず、処置内容を箇条書きで残す。
- **Codex が投稿する場合は Codex AI agent と明示する**：PR 本文、PR コメント、レビューコメント、merge コメントを Codex が投稿する場合は、ユーザーが明示的に別指示した場合を除き、本文冒頭または件名で **Codex AI agent** 由来であることを明記する。
- **レビューと修正の分離指示を守る**：ユーザーが「別コンテキスト」「subagent」「レビューと修正を分離」と指示した場合、レビュー担当 subagent と修正担当 subagent/主文脈を分ける。修正後は別文脈で再レビューし、所見・修正内容・検証・最終判断を PR コメントに残す。
- **「対応不要」を AI が独断で書かない**：指摘の処置要否・スプリント繰り越しは**オーナー判断**。AI が単独で「対応不要」「現時点不要」「将来検討でよい」等と結論づけてコメント・クローズしてはならない（過去に AI が独断で「対応不要」とコメントしオーナー指示に反した事例あり・2026-06-16）。指摘・矛盾を見つけたら **①ノード起票（FND/Q）→ ②ダッシュボード更新 → ③選択肢＋推奨を添えて打ち上げ**（PR7・意見なき停止禁止／独断禁止）。
- **指摘は処置完了まで追う**：レビュー指摘は原則として処置（起票→反映）まで完了させる。据え置くのは**オーナーが明示的に「不要/繰り越し」と判断した場合のみ**で、その旨と判断者をコメントに明記する。AI 同士のコメントを根拠に据え置かない。

## CI/外部サービス連携のコスト方針（2026-07-11）
**CI連携や外部サービス連携を検討・実装するときは、常に無課金（無料）で実現できる方法を優先して検討する。課金が発生する構成でなければ実現できない場合は、実装前に必ずオーナーの明示的な認可を取る（独断厳禁）。**

- **判断材料を確認してから設計する**：例えば GitHub Actions は public リポジトリなら無料枠の制限自体がなく完全無料、private リポジトリは無料枠超過分から課金。実装前に対象リポジトリの可視性・課金体系を確認し、無料枠内に収まる設計（トリガー条件を絞る・軽量ジョブにする等）を優先する。
- **課金必須の場合は選択肢＋推奨を添えて認可を仰ぐ**：なぜ無課金での代替が不可能か・想定コスト規模を明記した上で、PR7の様式（選択肢＋推奨＋根拠）でオーナーに判断を仰ぐ。AI が独断で課金を伴う設定（有料プラン必須の機能・従量課金リソースの有効化等）を選んだり有効化したりしてはならない。

## スコープ拡大禁止（Issue 運用ロール共通・2026-08-18・Issue #392）
**割り当てられた作業単位（Issue 本体のスコープ／レビュー finding／指摘対象）の外にある改善・指摘は、
その場で直さない。** これは各 Issue 運用ロール（`issue-implementer`・`issue-fixer` 等）が個別に運用してきた
規律（`.claude/agents/issue-fixer.md`「是正対象は渡された finding だけ」・`.claude/agents/issue-implementer.md`
「作業中に見つけた無関係な指摘・改善は直さず、呼び出し元への最終報告で列挙するだけに留める」）を
統合・一般化したもの。**新しい制約の追加ではなく、既に運用されている規律の明文化**（Issue #392）。

- **対象**：作業単位が明確に画定されるロール全般（`issue-implementer` のIssue実装、`issue-fixer` の
  レビュー是正、`pr-reviewer` のレビュー中に見つけた別件、その他同種のファンアウトロール）。
- **処置**：作業中にスコープ外の問題（無関係な改善点・別の不具合・別 Issue 相当の指摘）を見つけたら、
  - **自分で直さない**。
  - **構造化された列挙先へ出す**（Issue #495 で経路を一本化した）：
    - `pr-reviewer` は**別セクションやチャットの散文へ逃がさず、通常の finding として同じ列**に入れ、
      `scope: out` と申告する（書式は `.ai/agents/pr-reviewer.md`）。
    - `issue-implementer`/`issue-fixer` はハンドオフの `out_of_scope_findings` に、
      finding と同じキー（`harm`/`harm_detail`/`severity`/`locus`/`summary`/`evidence`/
      `expected`/`recheck`＋`scope: out`）を揃えて記録する。
  - **「スコープ外」は実害判定の免除ではない**：`harm` は必ず付ける。主文脈は
    `python3 -m karte ingest-review` でこれらを**カルテの finding 列へ取り込み**、
    `harm: real` の指摘は処置方針（`disposition: fix-here|deferred|waived`）が決まるまで
    `karte status` の verdict が `clean` にならない（機械ゲート）。
  - 対応要否・別 Issue 化の判断と実行は**呼び出し元（主文脈）に委ねる**
    （`/issue-pipeline` の運用では「スコープ拡張は別 Issue に逃がす」・起票の実行は主文脈が担う）。
    `waived`（処置不要）は**オーナーの明示判断**による。機械が強制するのは**記録**
    （許可者 `waived_by` と理由 `waived_reason` を書かずに `waived` を通せない）までで、
    **記録者がオーナー本人かは検証していない**（`deferred_to` も形式検査だけで Issue の
    実在は見ない）。多層防御の一枚であって sandbox ではないため、本節の運用規律と併用する
    ——既知の限界は `karte/README.md`「既知の限界（多層防御の一枚であって sandbox ではない）」。
  - doc-system-v2 に関わる指摘であれば、FND/Q ノード起票（`verification-author` 経由）の要否も
    主文脈が判断する。
- **理由**：スコープ外の変更が紛れ込むと、レビューアが把握していない差分として PR に混入し、
  次の再レビューで「未レビューの変更」として差し戻されるほか、PR が肥大化して当初の変更意図が
  追いにくくなる。
- **スコープの境界**：Issue 本体（または finding）が最初から複数ファイル・複数観点にまたがる場合、
  それら全体が正当な作業対象であり「拡大」には当たらない。作業対象がスコープ内か外か判断に迷う
  境界事例は、独断で処理せず STOP して報告する（意見なき停止禁止＝PR7 の様式で選択肢＋推奨を添える）。

## レートリミット時の品質降格の禁止と、委譲先 Codex 実行者の上限時の切替（2026-08-03・2026-11-15 改訂）
根拠と経緯（Issue #321 の発端とオーナー判定、Issue #829 で書き換えた理由）は
[rationale](../../.ai/rationale/executor-rate-limit-switch-829.md) を参照。

**レートリミット／セッション上限を理由に、モデル降格・effort 低下・サブエージェントへの委譲の
取りやめ（主文脈による代行）をしてはならない（絶対規範・例外なし）。**「急ぎだから」「軽微だから」は理由にならない。
下の Codex 実行者の切替は「同一構成で再投入する」ことの例外であって、この3つの禁止の例外ではない。
`.ai/guidance/common.md` の「同じ構成で再開する」は PF 共通の原則で、Claude Code 固有のこの例外は
本節と issue-pipeline 本文だけが定める。

- **禁止対象**：①opus 指定のところを sonnet 等へ**モデル降格**する、②同じモデルのまま
  **effort（思考量）を下げる**、③サブエージェントへ委譲すべき作業を**主文脈が直接代行**する
  （委譲の取りやめ）。上限で止まったのが Claude ロールでも、委譲先の Codex 実行者でも、3つとも禁止。
- **Claude ロール自身が上限で止まったとき**：モデル・effort を変えず、委譲もやめず、停止前と
  同一の構成で同じロールを再 dispatch する。主文脈が動けているなら Claude の枠は回復している。
  継続検査の対象（`change-planner`・`test-writer`・`issue-implementer`）では、主文脈が上限の逐語を
  `stop_reason` に入れ `stop_kind: claude-limit` とした receipt を止まったロールの `handoff_path` に書き、
  `collect-worktree` で回収・解放してから再 dispatch する。書くのは、作業ツリーに未 commit の変更・
  未 push の commit が無く、ロールの handoff が無いときだけで、それ以外はオーナーへ打ち上げる
  （主文脈は commit も既存の receipt への書き足しもしない）。手順は `.ai/skills/issue-pipeline/SKILL.md`
  「Claude の role 自身が上限で止まったときの再投入」が正本。
- **委譲先の Codex 実行者が上限で止まったとき（唯一の例外）**：同じロールの Claude サブエージェントへ
  切り替えてよい。主文脈が、同一ロールを Codex 実行者の指定なしで再 dispatch する。
  切替後の層と推論予算は、Codex 実行者に指定していたもの以上にする。
  主文脈が動けていることは Codex の枠の回復を示さないので、同じ Codex 構成での再投入を待つ必要はない。
- **切替の発動には上限の証拠が要る**：条件は、Codex 実行者が上限到達を示した出力の逐語があること。
  主文脈がその逐語を切替の記録に残してから切り替える（逐語による暫定運用・オーナー決定 2026-11-16。
  上限を示す文字列・終了コードは、初回に実測できた出力を共通本文へ追記して定める）。
  逐語で示せない失敗（profile pin 拒否・timeout・権限拒否・起動失敗など）と、遅い・無応答といった
  推測は証拠にならない。切り替えず STOP して報告する。
- **未 commit の部分変更が残っているときは、確かめてから引き継ぐ**（オーナー決定 2026-11-16）：
  ロールが Codex の残した変更を差分とテストで確かめ、依頼範囲内なら、テストが赤くても commit・push
  してから STOP を返す。コミットメッセージは、本文の末尾に `Handover: codex-limit` と、テストの状態を示す
  `Tests: red-unfinished`（未完了のための赤）／`Tests: red-intended`（意図した Red だけ）／`Tests: green` の
  どれか1行を置く。引き継ぎではない意図した Red の commit には `Tests: red-intended` だけを置く。
  主文脈はそのあとで切り替え、切替後の Claude ロールが続きから行う。範囲外の変更が混じる、または
  確かめられないときは、ロールは commit せず STOP し、主文脈は切り替えずオーナーへ打ち上げる。
  証拠があっても、確かめていない未 commit の変更の上では再 dispatch しない。
- **adviser は相談の難度を理由に Claude へ切り替えない**：adviser の層は最上位に固定してあり、
  難しい相談も Codex の最上位で扱う。
- **モデル選定はリスク信号表に従う。実行環境の都合（レートリミット）では変えない**：
  層と推論予算は変更の性質から引く。切替で変わるのは実行者であって、選定した層と推論予算ではない。
- 既定実行者、層の対応、切替の手順と記録項目は `.ai/skills/issue-pipeline/SKILL.md`
  「実行先、モデル、相談」、Claude Code での dispatch の形は
  `.claude/skills/issue-pipeline/SKILL.md`「Codex 実行者経路」が正本。
- **`codex-review`（別モデルファミリ）への切替は「降格」ではなく「追加の第二意見」**：`pr-reviewer` の同一構成での再投入が第一であり、`codex-review` はその再投入を置き換えるものではない。上限を理由に `pr-reviewer` を再投入せず `codex-review` だけで済ませるのは禁止される側に残る。再投入した**上で**別ファミリの第二意見も取ることは品質を下げる行為でなく、本規範に抵触しない（Issue #325 オーナー確定）。上の切替の例外は工程ロールの Codex 実行者だけに適用する。`codex-review` の `codex exec` が上限で失敗したときは、従来どおり同じモデル・同じ構成で再投入する。

## セッション記憶と正本の使い分け（Claude Code 固有・2026-09-06・Issue #484）

**リポジトリ全体に効くべき規則を Claude Code のセッション記憶に置いてはならない。正本（リポジトリ内のファイル）に書く。**

- **なぜ記憶では規則として機能しないか**：セッション記憶（`~/.claude/projects/<encoded-repo-path>/memory/`）は
  **リポジトリ外・バージョン管理外・マシンローカル**であり、次のいずれにも届かない——
  他の実行環境（Codex・GitHub Copilot。これらは `.ai/` 配下の共通本文しか読まない）／他のマシン・他の clone／
  PR レビューと監査（PR に載らないので規則の追加・変更が誰の目にも触れない）／
  機械検査（`tests/unit/test_governance_sync.py` の正本集合にも `asset_parity` の対象にも入らない）。
  届かない以上、そこに置いた規則は「書いてあるのに守られない」状態を作る。
- **リポジトリの作業規則・契約・手順・規範 → 正本に書く。記憶に置かない。** 置き場は内容で決める：
  - `.ai/guidance/common.md` — PF 共通（Claude Code / Codex / Copilot）の意味内容。
  - `.ai/skills/<name>/SKILL.md` — 特定プロセス（`issue-pipeline`・`gh-create-issue` 等）の運用。
  - `.claude/rules/NN-*.md` — Claude Code 固有機構（フック・エージェント権限境界・記憶等）の運用規則。
    サブエージェントにも配送される。
  - `.claude/main-context/*.md` — 主文脈にだけ当てはまる Claude Code 固有の規則（オーナーへの報告・質問の仕方等）。
    主文脈にだけ、SessionStart フックで全文、毎ターンは要約の写しが注入される
    （配送経路・orchestrator-context との併存・既知の限界は `CLAUDE.md`「主文脈専用の規定」）。
  - `docs/methods/*.md` — review_system の方法論。
- **オーナー個人に閉じた事実 → 記憶でよい**：役割・専門性・作業の好み・進行中の私的な関心など、
  リポジトリの成果物や他の実行環境の挙動を規定しないもの。
- **判断に迷ったらリポジトリ側に倒す**：届く範囲が広く、レビューと機械検査に載るため。
  記憶に置いて届かないリスクの方が、正本に書いて冗長になるリスクより大きい。
- **同じ規則を両方に置かない**：正本へ移した項目は記憶側から削除し、索引 `MEMORY.md` からも外す。
  両方に置くと片方だけが古くなる（`.claude/rules/01-principles.md`「PR8「消さない」の適用範囲」区分2
  ＝現行手順は追記で覆わず本文を書き換える、の考え方）。
- **本節を `.ai/` ではなくここへ置く理由**：セッション記憶は Claude Code 固有の機構であり、
  PF 非依存の共通本文（`.ai/guidance/common.md`）へ置くと Codex・Copilot に無関係な記述が混ざるため。
- **先行事例**：Issue #482 / PR #483 が起票先の2軸判断を記憶から `.ai/skills/gh-create-issue/SKILL.md` §3
  へ移設した。本節はその後、記憶の全件を同様に棚卸しして
  移設した Issue #484 の成果である（移設先＝`.ai/guidance/common.md`「言語・対外記録」「作業分離・判断境界」
  「正本・実装規約」、`.ai/skills/issue-pipeline/SKILL.md` ②-d、`.claude/rules/02-decision-process.md`
  「オーナーへの報告はチャットが正本」。同節は Issue #585 で `.claude/main-context/01-owner-communication.md` へ移設）。
